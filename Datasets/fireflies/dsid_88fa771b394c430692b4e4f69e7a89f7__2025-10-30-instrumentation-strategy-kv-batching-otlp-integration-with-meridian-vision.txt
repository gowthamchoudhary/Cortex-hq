[01:51] Liam: Perfect. Can we talk about the span model for token-level traces? We want to maintain a single root span per request and sub-spans for heavy operations.
[02:05] Ethan: Sure — our recommended model is: root span = request lifecycle; child spans for model token generation loops and KV cache lookup spans. Token-level timing is recorded as attributes on generation spans rather than thousands of individual spans to avoid cardinality explosion. We can also emit per-token histogram metrics if you want per-token latency distributions.
[02:35] Priya: Histogram metrics sound promising. How do you correlate a cache miss to a specific token generation step?
[02:45] Ethan: We include attributes like cache.hit=true/false, cache.layer=prefix/kvcache, batch.size, seq.len. Then in OTLP you can filter by cache.hit==false and inspect associated latency histograms. The link between token position and cache event is done via an attribute token.index, but that's optional — we recommend sampled token.index only for debug traces.
[03:10] Miguel: Right, we don't want token.index in prod traces because of cardinality. What about sampling strategy?
[03:20] Ethan: We suggest hierarchical sampling: 1) low-rate full-trace sampling for debug (e.g., 0.1%), 2) event sampling for cache misses (always sample cache.miss), and 3) metric aggregation for p50/p90/p99 per model/route. Most teams rely on metrics for SLOs and sampling for investigatory traces.
[03:45] Liam: How does batching affect observed per-token latency? We need to ensure our SLOs reflect user-facing latency, not batched amortized latency.
[03:55] Ethan: Key point: batching reduces cost but masks tail latency. We provide both 'per-invocation' and 'per-token' metrics. For SLOs tied to interactive latency, use per-invocation p99; for throughput tuning, look at token/sec and batch.size distributions.
[04:20] Priya: Is batch.size exposed as an attribute?
[04:25] Ethan: Yes, batch.size and batch.queue_time_ms are attributes, plus kernel selection id and quantization profile (e.g., fp16, int8-q4).
[04:36] Miguel: Speaking of quantization — we saw different per-token CPU / GPU times across int8 vs fp16. Can Redwood emit the kernel-level timings?
[04:47] Ethan: We can emit optional performance counters: kernel.exec_ms, kv.lookup_ms, kv.deserialize_ms, kv.cache_hit_ratio. For on-prem you can enable more granular counters, but they increase metrics volume.
[05:05] Liam: Can we wire those into Prometheus? We have a pushgateway and long-term storage.

[05:24] Priya: When you say "token-level metrics" — are we talking one metric per token? That's unmanageable.

Token index is optional and only used in debug. The normal flow is aggregated histograms for token latency and counters for cache hits/misses.
[05:52] Miguel: How do we correlate Redwood Console traces and our Tempo traces?

[06:14] Priya: What about volume — if we sample every 1% but still produce many metric labels per model, what's the recommended retention/rollup?
[06:26] Ethan: Typical pattern: keep high-cardinality data for 7–14 days in raw form, then roll up to 1h buckets for 90 days. Token histograms are expensive; we pre-aggregate on the host and export summaries to reduce cardinality.
[06:45] Liam: Let's go through a concrete pipeline: Redwood runtime -> OTLP (local collector) -> Tempo/Prometheus -> Grafana. Any gotchas?
[06:58] Ethan: Watch for batching at the exporter layer. The collector will batch metrics/traces for efficiency; adjust exporter batch sizes so latency-sensitive traces flush quickly. Also ensure your OTLP receiver is sized for peak token throughput — many teams underestimate token/sec spikes.
[07:20] Priya: Is there an example OTLP config?

[07:38] Miguel: Tail-based sampling — that means we buffer traces to see whether they contain a cache.miss before deciding to keep them? That adds memory overhead.
[07:47] Ethan: Correct; tail-based buys you better decisioning (e.g., keep traces that have errors or cache misses) but requires memory. We usually cap buffer size and fallback to probabilistic sampling under pressure.
