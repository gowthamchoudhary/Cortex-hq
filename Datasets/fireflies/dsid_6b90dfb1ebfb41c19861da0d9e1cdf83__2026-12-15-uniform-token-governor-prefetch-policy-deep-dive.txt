Uniform Token Governor & Prefetch Policy Deep Dive

We walked through continuous batching behaviors, the interplay between max_num_seqs and token ceilings, KV cache warmup strategies, and tradeoffs with quantization. The trick is to pick a governor and token ceilings that protect short tails while still allowing high throughput.
[01:35] Sophie: let's talk concrete knobs. We'll propose a 'uniform token governor' — basically cap per-request token accrual and enforce soft preemption if a request exceeds a window.
[01:48] Priya: soft preemption? do you mean interrupt and requeue?
[01:51] Arun: more like slice and continue: split a long request into multiple scheduling quanta so it doesn't block a slot for too long, this is scheduler-level slicing, not model-level. It keeps KV cache locality but prevents head-of-line blocking.
[02:05] Daniel: Will that increase overall compute because of more context switches?
[02:08] Arun: marginally, yes. there's some overhead to more smaller dispatches, but in our tests the throughput loss is offset by reduced tail latency and better utilization across tenants.
[02:19] Liam (CTO): how does this interact with KV cache warmup? we saw cold cache penalties on first long requests after evictions.
[02:27] Maya: Good point. our recommendation is to combine a prefetch window with a warmup policy: when a long request is detected we prefetch the KV shards for the next N tokens into the local GPU cache (or pre-warm across the pool) and mark the request as 'warm' in the governor so subsequent slices read cached KV.
[02:45] Priya: sounds good; what's N typically?
[02:48] Arun: depends. for your model and quantization profile, we often use prefetch windows between 64-256 tokens. for int8 quantized runs we've seen 128 be a sweet spot. for int4/qat variants you might do a bit lower, like 64.
[03:05] Daniel: we run Q4_0 on some envs, and int8 on others — any guidance?
[03:10] Sophie: quantization lowers memory and can increase throughput but can alter kernel selection and kv cache size. Q4_0 often reduces KV per token which helps cache hit rate, but int8 with different kernels may have different warmup profiles. we'll include model-specific prefetch profiles.
[03:29] Speaker 1: can you explain how the 'uniform token governor' enforces fairness across tenants?
[03:33] Arun: Sure. it's like a token bank per request with a per-tenant weight. Each request accrues budget up to a ceiling; if the request exhausts budget, it's paused and requeued. the scheduler ensures no single request consumes >X% of GPU time in a rolling window. We also do priority windows for enterprise tiers so you can allow larger headroom for reserved capacity.
[03:56] Priya: are these ceilings expressed in tokens or in token-time (token*seq_len)?
[03:59] Arun: tokens. but we map tokens to estimated exec time using a small model of kernel latency per token for the current model/quant; that helps make ceilings meaningful across different models.
[04:12] Daniel: interesting. about KV eviction — we noticed aggressive eviction during bursts; our eviction threshold is basically LRU with size limits. recommendations?
[04:21] Maya: We prefer a two-tier policy: keep a hot set pinned for a short TTL, evict least-recently-used outside that. Also use a small async prefetch thread to pre-warm items based on request patterns. Set eviction threshold to keep hot-set hit-rate >85% for your trace.
[04:36] Liam: how do we measure hit-rate easily? the console has token-level breakdowns?
[04:40] Sophie: Yes, Redwood Console exposes per-prefix KV hit-rate and per-route latency splits. we'll point you at the dashboards and the sample queries to compute a rolling hit-rate.
[04:50] Speaker 3: you mentioned splitting requests into quanta, what about model state across slices?
[04:54] Arun: We maintain KV across slices so long as the request id persists; slices are contiguous in time and the runtime stitches outputs. model's attention state (KV) is preserved in the runtime's cache; prefetch ensures the next slice's KV is resident.
[05:07] Priya: network implications for on-prem VPC — prefetch generates additional egress between control plane and workers?
[05:13] Maya: Prefetch is internal to the serving cluster if you're on dedicated/dedicated private. For VPC/private deployments we do recommend colocating KV shards with GPUs or using a high-bandwidth fabric. we will provide a recommended NIC and MTU config.
[05:27] Daniel: we use 100GbE between NVLink boxes; is that sufficient?
[05:30] Arun: yes, but watch congestion; prefetch spikes can saturate fabric so use a smoothing window and rate-limit prefetch per node.
