[01:44] Liam: Rough numbers: doubling dims roughly doubles embedding memory (and disk if stored dense) and increases per-cosine compute proportional to d. On a single rerank call for k=50 candidates, compute ~ O(k*d) vec-ops. So 256->512 roughly doubles CPU/GPU flops for the scoring step and increases transfer costs. In practice we measured p95 impact of ~1.6x for scoring stage due to better kernel utilization.

[02:35] Priya: On kv cache — I thought kv cache helps generative contexts. Do you use it for rerank?
[02:42] Liam: Good callout. KV cache is mainly for autoregressive generation. For pure embeddings and cos-sim rerank, KV cache isn't used. However, if you add a small LLM scoring pass (e.g., prompt-based re-scoring, or a cross-encoder) the KV cache matters for repeated contexts and can lower token latency. For rerank stage that is vector-only, focus on matrix throughput and memory bandwidth.
[03:05] Dana: We're exploring a hybrid: ANN to retrieve 200 candidates -> embed re-score to top 50 -> optional LLM-based final check for top 5. So yeah both types matter.

[03:27] Samir: For embed storage — we store vectors in Milvus and use float32 today. Thoughts on storing quantized vectors (int8 or PQ)?
[03:34] Liam: Quantized on-disk is fine — PQ or int8 reduces storage and I/O; search accuracy tradeoff depends on quantization scheme. For compute-time quantization (loading into GPU as q4/8) you save memory and sometimes increase throughput but must watch accuracy. We recommend benchmarking with your recall set.
[03:48] Dana: Any recommended default dims for clinical search? 256 vs 512?
[03:53] Liam: Many customers start at 256 for a good cost/recall sweet spot; 512 helps recall but cost rises. For sensitive domains where recall is critical, 512 can be justified. 1024 is usually overkill unless doing large multi-modal or very nuanced semantics.
[04:10] Maya: I'll note that for Aurora's dataset size (~2M docs) storage and retrieval cost is material; we can run cost sims for 256 vs 512.
[04:20] Samir: Batching — what's a good batch size in production? We can't introduce per-request tails.
[04:25] Liam: Two things: batch used at embed generation (if you generate embeddings for queries in realtime) and batch in scoring (matrix multiply across k candidates). For query-time embeddings of single queries, batching with continuous batching can group requests to batch sizes 8-32 without much extra latency if you accept a 10-40ms queuing delay. For scoring stage, scoring k=50 is effectively a small matrix multiply; optimal single-op batch sizes vary by GPU and kernel. We often see best throughput at microbatch sizes 16-64 depending on d.
[04:58] Ravi: Example: with d=256 and batch=32, p95 was 85ms on our infra for the scoring step; reduce batch to 8 -> p95 60ms but cost per query rises due to lower GPU utilization.
[05:12] Priya: How does quantization affect tail latency?
[05:15] Liam: Quantization often improves memory footprint and can reduce kernel runtime, lowering p99 in some cases. But some library kernels for q4 are less mature and you can see jitter. We advise running three profiles: float32 baseline, int8/PQ on-disk + float compute, and q4 runtime. Liam: We'll provide these runs.
