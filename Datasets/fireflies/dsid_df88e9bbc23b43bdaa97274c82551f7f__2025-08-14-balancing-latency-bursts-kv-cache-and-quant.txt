[02:30] Diego Marquez: can you explain the difference between max_num_seqs and the soft batching window? We saw references in the docs but not sure which to tune first.
[02:44] Marta Silva: yeah and also eviction — our KV cache footprint is huge because we keep prefixes for 20k sessions, is that even necessary?
[02:51] Ravi Kapoor: good q. Briefly: soft batching window (time cap) is a latency knob — if you want strict SLO you reduce it. max_num_seqs is a capacity knob — it limits the number of concurrent sequence starts packed into a single micro-batch. The runtime will trigger a dispatch when either the window times out or max_num_seqs/hard token budget is hit. So for bursty traffic you can tighten window to reduce p99, but you'll lose throughput efficiency; alternatively reduce max_num_seqs so short requests don't sit behind long ones.
[03:28] Imani Brooks: uh-huh. And KV cache — does the runtime evict least-recently-used or is it fixed?
[03:34] Ravi Kapoor: currently LRU-ish with a weighted policy, but eviction is at granularity of prefix blocks; we recommend sizing so that the hot set fits in KV to cut repeated autoregs. For you, keeping 20k sessions is probably overprovisioned unless most are hot within a short TTL.
[03:50] Sanjay Rao: our sessions have sticky routing via cookie — some customers do have very hot repeating sessions.
[03:55] Leah Chen: picture this: short-chat spikes — you want to favor lower window (like 10-40ms) and a lower max_num_seqs (16-32) so those small sequences don't wait behind a 512-token request that drags the batch. For steady throughput jobs, bump max_num_seqs to 64+ and allow longer window to amortize kernel launch.
[04:28] Diego Marquez: what about token caps? if we set max tokens lower, does that interact with continuous batching?
[04:37] Ravi Kapoor: yes — there is a hard token budget per micro-batch for memory safety. If incoming sequences combined tokens exceed that budget the scheduler will dispatch early. So token limit essentially provides a second safety that prevents long sequences from starving short ones — but it's coarse. In practice we set micro-batch token budget to something like 32k-64k depending on model and GPU memory.
[05:05] Imani Brooks: we run a 13B and a 70B quantized model in private. The 70B is int8 quant, but we saw 15-20% accuracy drop on a small eval — any guidance?
[05:20] Ravi Kapoor: quantization tradeoffs are workload specific. 4-bit (FP4 / Q4) with aware rounders often gives 10-15% perf cost but is much cheaper. Int8 can be very stable if it's per-channel and you calibrate well, but it depends on ops support on your hardware. For throughput tuning, quant reduces memory so you can fit higher max_num_seqs per GPU which improves throughput, but may worsen p99 if the soft window is increased.
