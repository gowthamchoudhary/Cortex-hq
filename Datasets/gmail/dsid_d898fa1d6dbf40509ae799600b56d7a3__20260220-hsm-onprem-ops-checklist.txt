Hi Hiro — answering inline: 

1) Network: we recommend using a short list of static egress IPs for the KMIP control plane (3 IPv4 addresses) and a DNS name for telemetry that rotates weekly. We can provide an allowlist once SOW is signed; during test we can use temporary IPs.

2) BYOK lifecycle: our KMIP supports Create/Wrap/Unwrap/Destroy. For automated envelope rotation we provide an authenticated operator role that can request rewraps via KMIP. Root key rotations must be manual (customer performed) and you will need to re-establish trust after root rotation. No firmware hooks required for standard KMIP flows; if you want HSM-specific key material migration we have a vendor-assisted procedure in the attachment.

3) Audit: HSM syslog (CEF) + KMIP audit events exported as JSON to an S3-compatible endpoint. We can keep events for 90 days by default, longer retention available as a paid option.

Quick notes from engineering POV: 

- KMIP connector: I'll prototype a sidecar-based KMIP client that exposes an internal secure gRPC to the runtime. It will handle key wrapping/unwrapping and maintain a local cache of envelope keys with TTL and strict LRU. We'll implement rotation as a two-phase swap: stage new envelope key, rewrap active data keys, then retire old envelope after verification.
- Secrets handling: store only wrapped keys in our vault (Hashi-compatible path). Unwrapped keys never leave HSM. Use HSM-attested ephemeral sessions for derivations.
- Rotation windows: propose rolling rotation at 03:00 UTC with a 2-hour maintenance window; include automatic rollback if >0.5% request error spike.
- Network: require egress to SecureKMS KMIP CIDR; use mutual TLS pinned certificate; disable plaintext KMIP. For telemetry we will post to customer's S3 via VPC endpoint (no internet egress).
