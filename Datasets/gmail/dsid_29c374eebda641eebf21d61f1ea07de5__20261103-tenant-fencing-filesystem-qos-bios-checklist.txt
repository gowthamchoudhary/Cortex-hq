Quick notes / proposed defaults from infra perspective:

- Nodepool layout (proposed):
  * system‑infra (non‑gpu, 3 nodes, taint system:control‑plane=true) — control plane and storage controllers
  * gpu‑lowlat (GPU, 6 nodes, 1x A100/RTX per node) — low latency, small batch, pin to NUMA local memory
  * gpu‑batch (GPU, 4 nodes) — large batch, higher tolerated latency, aggressive prefetch/caching
  * storage‑io (non‑gpu, 4 nodes, NVMe JBOD) — host the blockstore volumes, run CSI controller replicas here

- Isolation: prefer separate block devices per tenant when tenants have strict IO SLAs. That reduces noisy neighbor risk and simplifies QoS at the host level. Shared filesystem (e.g., XFS on top of a distributed block store) is OK for low‑priority tenants.

- StorageClass profiles (defaults):
  * redwood‑fast (Provisioner: local‑csi or external CSI; parameters: fsType=xfs, ioScheduler=none, discard=on, replica=1; reclaimPolicy=Delete; volumeBindingMode=WaitForFirstConsumer)
  * redwood‑durable (Provisioner: external CSI; parameters: fsType=ext4, replica=3, snapshotEnabled=true; reclaimPolicy=Retain)
  * redwood‑ephemeral (emptyDir‑based, nodeLocal cache, for scratch)

- QoS mechanisms: use nodepool separation as primary QoS boundary. Kubernetes blkio/cgroup v2 throttling is material but less predictable with complex CSI drivers. Where you must use shared volumes, we recommend CSI that supports IOPS/throughput parameters exposed to the scheduler.

- BIOS baseline (must haves):
  * Smt: on for throughput jobs, consider off for noisy single‑threaded workloads — default ON unless profiling shows regressions
  * C‑states: disable deep C‑states for low latency nodes
  * NUMA: set interleaving disabled; bind processes to NUMA for GPU nodes
  * PCIe ASPM: disable on inference nodes (reduces latency jitter)

- Backup/retention: recommend rolling snapshots with staged throttle (use CSI snapshot + rate limit) and schedule outside 15:00–19:00 local peak window.

Thanks — a couple compliance / risk items to flag before the workshop:

- Encryption at rest: Hearthstone will need proof of KMS integration for private deployments. We should bring the KMS integration guide (customer KMS + Redwood key wrapping) and a short checklist for key rotation.
- Audit logging: they asked about immutable audit trails for admin actions. We should propose forwarding to their SIEM (rsyslog/Fluent) and a retention baseline (90/365/1095 days).
- Tenant fencing: for regulated tenants, require separate storage class + network policy + optionally separate Kubernetes control plane namespaces (or dedicated small clusters). That increases operational cost but gives stronger isolation.
- Canaries: propose a two‑tier rollout for host changes: (1) single host validation (fio + perf‑regress), (2) 10% nodepool, (3) full rollout. Include rollback playbook in the checklist.
