Team —

Attached is the finalized postmortem for the 11/20 KV-cache eviction incident (incident_postmortem_20271120.pdf). Short summary: between 01:03–01:26 UTC we observed persistent cache-thrashing on a subset of Dedicated clusters which increased 95th latency by ~230ms and caused elevated 429s for about 15% of production traffic for 23 minutes. Root cause: an inadvertent config change that disabled the soft-entry guard, compounding a burst of long sequences and causing accelerated KV GC.

What we did (already completed):
- Rolled back the configuration within 7 minutes and restored normal cache behavior.
- Scoped impacted clusters and re-provisioned one pool that had sustained degradation.
- Short-term mitigations added to runtime to reject pathological prefixes (see runbook_kvcache_update.md).

Outstanding asks for QBR alignment (please accept ownership in-thread with ETA):
1) Permanent fix for soft-entry guard and additional unit tests (owner: SRE) — target Nov 28.
2) Canary/rollback automation for Dedicated config changes (owner: Platform Infra) — target Dec 5.
3) Customer-facing SLA remediation proposal and credit path for affected accounts (owner: Finance + Sales) — target Nov 24.
4) Runbook + run drills for KV eviction recovery (owner: Reliability Docs) — target Nov 30.

I've attached an action tracker (action_tracker_qbr_20271121.xlsx) and linked the internal doc and HubSpot record for Acme Analytics. Please reply with owners and firm ETAs by EOD 2027-11-22 — we need a clean slate for the QBR runbook and the slides.

Thanks — this incident is lower-severity than the April outage but it highlights a recurring gap in change guardrails we need to close before the next quarter.
