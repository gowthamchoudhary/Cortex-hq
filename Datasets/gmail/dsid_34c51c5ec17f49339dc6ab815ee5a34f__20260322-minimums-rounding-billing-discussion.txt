Hi Lara —

Thanks — great questions. Quick summary up front, followed by worked examples and the SOW language we'll include.

Summary (short):
- Billing unit: Redwood measures tokens precisely for each API request. For invoicing we report billed usage as whole tokens and round up fractional tokens at the request level (i.e., each API call's total token usage is rounded up to the nearest integer).
- Minimums: there is a 1-token minimum billable unit per API request to avoid microbilling noise. Bulk batch calls aggregate internally and are billed on the cumulative tokens for the call (then rounding applies).
- Streaming: tokens generated during streaming are billed as generated; we do not apply an extra per-chunk minimum beyond the 1-token per-request floor.
- Truncation: we bill for the tokens submitted to the service. If you supply a prompt that exceeds the model's context and it is truncated at the client or at the model boundary, you are billed for the tokens that were sent and processed by the model.
- Context-based pricing: tokens are tokens — but models with extended context (e.g., 32k/64k variants) have different per-token rates. The committed-use discount applies to total billed tokens (prompt + response) up to the committed cap; on-demand rates apply thereafter.

Worked examples (attached as CSV too):
1) Single short request (chat completion)
   - Prompt tokens: 12.4
   - Generated tokens: 18.6
   - Per-request total (exact): 31.0 tokens -> rounded up to 31 tokens billed (no change)
   - Minimum check: 31 > 1 so minimum doesn't affect it

2) Tiny telemetry call (many tiny calls scenario)
   - Prompt tokens: 0.2
   - Generated tokens: 0.1
   - Per-request total (exact): 0.3 tokens -> rounded up to 1 token billed (per-request minimum applies)

3) Batch embeddings call (single API call with 50 inputs)
   - Each input tokenized total: 15.2 tokens average -> aggregated request tokens: 760 tokens exact -> rounded up to 760 tokens billed (rounding at call level)

Notes: the attached billing-examples-20260319.csv contains these rows and a few more permutations.

SOW language (proposed clause we can add to the SOW):
"Billing units and rounding: Redwood measures usage in token units. For invoicing, token usage is calculated per API request and rounded up to the nearest whole token. A minimum of one (1) billable token applies to each API request. For batched requests, token usage is measured at the aggregate request level prior to rounding. Tokens included in the request payload that exceed the model's context window and are processed or truncated by the server will be billed. Committed-use discounts apply to total billed tokens (prompt + generated) up to the committed cap in the applicable billing period."

Hi Lara —

Quick answers to your follow-ups plus explicit appendix-style example (I also attached the CSV as noted by Sean).

1) Streaming partials: tokens are metered as they are received by the inference service. If a generation is aborted mid-stream, you are billed for the tokens that were already generated and transmitted to the client. There is no additional hidden rounding per chunk beyond the per-request rounding rule; streaming sessions are billed on the tokens emitted by the server up to the point of termination.

2) Committed cap true-up: our standard is monthly true-up. That means usage during a calendar month applies toward the committed cap for that month; any usage beyond the commit is charged at on-demand rates on the same invoice. We can consider quarterly true-ups for enterprise SOWs if you prefer, but monthly is default.

3) Multiplexed batching: Metering and billing are at the logical request level — even if we batch many tiny logical requests into a single GPU batch for efficiency, our billing reports break down billed tokens per logical request (i.e., the rounding and minimums are applied to each logical request before aggregation). That makes internal chargeback simpler on your side.

Appendix example (explicit):
- Case A: tiny event (single logical request)
  - Prompt tokens: 0.18
  - Generated tokens: 0.12
  - Exact total: 0.30 -> rounded to 1 token billed (per-request minimum applies)
  - Line on invoice: "ChatCompletion — 1 token @ $0.0006/token = $0.0006"
- Case B: multiplexed batch with 100 tiny logical requests sent in one API call (server-side batching)
  - Each logical request exact total: 0.30 tokens -> each rounded to 1 token -> billed tokens total: 100 tokens
  - Invoice will show 100 logical-request lines or an aggregated line per your preferred invoice format; we'll include breakouts in the usage export so you can do internal chargeback.
