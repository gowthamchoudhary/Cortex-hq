Copying my initial technical readout — high-level feasibility and risks below. Quoting Ben’s note for context.

Short answer: feasible, but non-trivial. Two practical options:

Option A — Dedicated, non-quantized path (recommended for fidelity):
- Requires pinned GPU pool (A100/ equivalent), model loaded in FP16/FP32 (no int8 quant).
- Estimated infra delta: ~1.5x GPU memory and ~1.4x per-token cost vs our current default quantized path.
- Canary strategy: we can start with 5% traffic on dedicated nodes, ramp to 20% after 48h, then 50% after automated health checks.
- Work: infra orchestration (2 sprints), model-variant packaging + routing policy (1 sprint), telemetry/trace updates (0.5 sprint).
- Risks: KV cache warmup kills cold-start latency; sustained burst handling needs buffer pool.

Option B — Quantized-but-tuned path (lower cost, some fidelity loss):
- Use 4-bit quant with targeted per-layer calibration. Reduces cost but introduces small inference drift against audit traces.
- Work: calibration and eval run (1 sprint), rollout policy coding (0.5 sprint).

Instrumentation and gating items to ship for safe canary:
- Token-level delta metrics vs baseline (per-prompt BLEU-like match for KYC extraction).
- OpenTelemetry trace tags to correlate user session -> model variant.
- Automated rollback policy when fidelity delta exceeds threshold for 12h.

Attachments: implementation-sketch.pdf (high level infra diagram), cost-estimates.csv (rough numbers).

ETA: If we prioritize, initial canary infrastructure (Option A minimal) is ~3 engineering sprints (6 weeks) to reach 5% traffic with observability. Option B (calibration-first) can be done in ~2 sprints and used as a temporary mitigation while A is built.
