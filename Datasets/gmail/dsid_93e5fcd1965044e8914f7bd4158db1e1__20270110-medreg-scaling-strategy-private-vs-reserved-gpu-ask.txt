Marissa / team — digging into the numbers. Assumptions (please confirm):
- p50 prompt = 120 tokens, p95 = 820 tokens
- Ensemble inference: generation (13B) + reranker per user request => ~1.45x token work vs single model
- Target steady concurrency to support = 600 sessions, allow 2.5x headroom for spikes

Sizing sketches (ballpark):
Option A — Redwood Dedicated (reserved GPU pools, managed by Redwood but single-tenant capacity):
- Optimal hardware: 4 x A100 80GB per serving pod (NVL or equivalent) with continuous batching + KV cache
- Pod throughput: ~1800 tokens/sec (when batched efficiently)
- To support 150K tokens/min (2500 tokens/sec) sustained + 2.5x headroom => target capacity 6250 tokens/sec => ~4 pods => 16 A100 80GB GPUs
- Latency range (median token): ~180-380ms depending on batching; token-latency SLA target feasible with preferred request routing and priority lanes.
- Pros: faster to provision than on-prem, Redwood manages software/optimizations; supports isolated single-tenant scheduling.
- Cons: data egress and control model slightly less prescriptive than full Private deployment; requires contractual isolation clauses.

Option B — Redwood Private (VPC or on-prem managed by customer):
- Recommended hardware for on-prem: 16 x A100 80GB (same GPU count) ideally in 4-node groups for redundancy; or 24 x A10G for cost-led option but higher latency and lower batch density.
- Pod placement: co-located inside customer VPC; Redwood control plane integrates with KMS/HSM for keying and audit logs.
- Latency: similar at peak if networking and NVLink per-node configuration match; operational responsibility shifts to customer for hardware maintenance and capacity scaling.
- Pros: full control over data residency and network; easier for procurement to justify from a compliance standpoint.
- Cons: longer lead time for hardware procurement (~8-12 weeks), higher ops overhead initially, potential for lower utilization without Redwood-managed bursting options.

Operational recommendations common to both:
- Start with Dedicated reserved capacity sized for 80% of expected peak while enabling Private readiness (hardware spec & runbook) — gives faster time-to-production and a path to migrate if compliance requires.
- Enable KV prefix caching for common prompt prefixes to reduce token work by estimated 12-18%.
- Deploy canary route with smaller replica set (2 pods) to validate perf and scaling.
