Neha —

Requesting final approval on the v1.0 error budget policy and the enforcement rollout plan. This is the version we intend to socialize broadly (SRE + Platform + Infra + PM Hosted/Dedicated) and start implementing gating against.

Confluence draft: confluence://eng-sre/slo-and-error-budgets/error-budget-policy-and-enforcement

Key changes since last review:
- Breach definitions are now purely SLI-driven (success rate + streaming reliability + latency SLOs), with explicit exclusions aligned to the SLI spec.
- Multi-window burn-rate alerting wording is finalized (fast + slow windows, with severity mapping).
- Enforcement phasing is explicit (dashboards → warn-only gate → soft gate → hard gate).

Decisions I want to lock today:
1) Enforcement phasing / timeline
   - Phase 0 (now): dashboards + burn-rate paging only.
   - Phase 1: warn-only deploy gate when a tier is in “red burn” (e.g., 2h burn-rate >= 2x). Gate posts to Slack + requires override reason.
   - Phase 2: enforce “soft freeze” when remaining budget < 25% (block non-critical rollouts; allow config-only mitigations + rollbacks).
   - Phase 3: enforce “hard freeze” when budget exhausted (block all non-emergency deploys into the affected tier/region).

2) On-call expectations (who gets paged / who owns the mitigation)
   - Hosted: SRE primary + Routing on-call paged for fast-burn; Infra on-call paged when mitigation requires capacity shift.
   - Dedicated: Dedicated pool owner (Infra) + SRE primary paged for fast-burn; stricter comms expectations.

3) Exception process language
   - Proposed: emergency overrides must include incident ticket or “risk accepted” by a VP-level approver; override gets logged and reviewed weekly.

If you can reply with “approve” (or edits) today, I’ll mark the policy as approved and ask Talia to schedule the training + rollout comms.

Thanks,
Sean
