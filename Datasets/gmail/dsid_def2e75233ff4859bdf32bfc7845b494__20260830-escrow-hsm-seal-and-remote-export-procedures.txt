Hi Alice / Monica — apologies for the slightly long note, but I wanted to be explicit on each ask. Answers below (concise + evidence pointers). I've attached the HSM sealing/escrow doc and the attestation package for your review.

1) Emergency export / remote escrow
- We support an emergency export for customer BYOK keys, but we treat this as a last-resort, auditable, multi-party process.
- Preconditions: a valid legal/contractual request (e.g., signed SLA exception + customer POA), two independent approvers from Redwood Security (Director-level + Head of Ops) AND an authorized Helixera representative (customer-supplied approver).
- Export mechanics: key material is exported only from Hardware Security Modules (HSMs) that support secure key export under controlled wrapping modes. The private key material is exported in an encrypted, individually-wrapped archive using an operator multi-wrap scheme (>=2 layers) and retained only in a hardware-backed escrow appliance while in transit.
- Custody & transport: chain-of-custody logs are generated; if hardware courier is required for physical media, we use bonded carriers and tamper-evident containers. Electronic transfer uses mutually-authenticated TLS 1.2/1.3 with client certs + PKCS#7 envelope.
- Audit: each export action creates a tamper-evident audit record (signed ledger entry) and a time-stamped attestation that we provide to the customer.

2) HSM sealing & attestation
- HSM types: we operate with FIPS 140-2 Level 3 validated modules and can integrate with CloudHSM / BYOK models (for SaaS we use vendor-validated modules from our HSM partners).
- Sealing: when a BYOK key is imported, the key is sealed inside the HSM; Redwood never stores unwrapped private key bytes outside the HSM.
- Attestation: we provide hardware attestation evidence (quote + certificate chain) generated by the HSM vendor. Attached: attestation_evidence_2026-07.pdf contains sample quotes and the verification procedure.

3) Key lifecycle & rotation
- Default policy: symmetric data keys rewrap cadence is configurable; platform default key rotation is 90 days for envelope keys; customer can override to 30/60/90/180-day policies per vault.
- Rolling rotations: we support zero-downtime rotation by double-wrapping (new and old KEKs active during the transition window) and automatic re-encryption of cached envelopes when requested.
- Decommission: when a key is retired, we zeroize HSM state, remove references, and produce a deletion certificate with SHA-256 hash of the key handle. Evidence is retained per the contract retention window.

4) PKCS#11 / interfaces
- Supported interfaces: PKCS#11, KMIP (select partners), vendor cloud-HSM REST APIs for import operations. We also support wrapped import using CMS/PKCS#7 for interoperability.
- Limits: import/export throughput is governed by HSM vendor quotas; typical enterprise-level quotas are adequate for onboarding (we provide a pre-onboarding throughput plan).

5) TLS and mutual auth
- Control plane: mutual TLS (mTLS) is supported for admin and provisioning APIs. We support TLS 1.2 and TLS 1.3 (TLS 1.3 preferred). Cipher suites follow our hardened policy (AEAD ciphers, ECDHE key exchange).
- Client cert rotation: we support automated cert rotation via ACME-like workflows for ephemeral agents and long-lived certs for appliances with rotation hooks; rotation notices are emitted to your ops team in advance.

6) Proof of deletion / crypto-shredding
- Deletion evidence: we provide deletion certificates (signed statements) + HSM audit logs showing the erase command and resulting internal state change. For BYOK where the customer provides the private key escrowed offsite, we can provide signed attestations and an HSM-backed zeroization log.
