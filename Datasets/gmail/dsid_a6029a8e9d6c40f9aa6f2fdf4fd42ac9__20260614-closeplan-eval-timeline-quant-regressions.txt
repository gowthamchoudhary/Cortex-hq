Olivia — thanks for the replay data and prompts. We completed the initial eval and wanted to share a concise summary and proposed next steps so procurement has what it needs. Short version first, then data: 

Summary:
- FP16/BF16 baseline meets interactive SLOs for P95 and TTFT.
- INT8 gives meaningful cost/throughput uplift and generally preserves P95 for <8 concurrent sessions.
- INT4 shows best single-session TTFT but exhibits P95 spikes when concurrency increases (kernel fallback in attention). Not safe to enable for SLA routes without fixes.

Key numbers (canonical interactive workload):
- FP16: P50 85ms / P95 210ms, TTFT 95ms, sustained throughput 22k tokens/s at 16 concurrent sessions.
- INT8: P50 60ms / P95 240ms, TTFT 70ms, sustained throughput ~42k tokens/s at 16 concurrent sessions (note slightly higher P95).
- INT4: P50 55ms / P95 600ms (under >8 concurrency), TTFT 60ms, throughput up to 58k tokens/s single-threaded but unstable.

Kernel findings (high level):
- Attention kernel: INT4 path triggers a slow scalar fallback when micro-batch alignments exceed 128 tokens; the fallback shows up as isolated P95 spikes.
- KV-cache writes are slightly more expensive in INT4 due to packing/unpacking overhead on our runtime.

Proposed mitigations / MAP updates:
1) Short kernel patch (runtime scheduling and micro-batch clamp) — Redwood engineering can roll to the dedicated eval pool within 48–72 hours, then re-run the concurrency sweep.
2) MAP routing policy: enable INT8 as standard for concurrency >=8; enable INT4 as opt-in for non-SLA batch jobs where cost is primary.
3) Quality checks: run canonical-prompt diff for every quant profile and include automated regression alerts in the MAP acceptance criteria (max token-level edit distance threshold per prompt).
