Sara / Monica — quick technical note from infra:

- Redwood does not currently persist a separate KMS-signed timestamp token in the audit DB. We do persist the following fields on every access record: event_ts (server UTC), key_version_id, key_fingerprint, envelope_ciphertext_id, and a SHA256 of the ciphertext.

- For audit-grade proof, we can add a derived_signed_ts field (HMAC over [event_ts,key_version_id,record_id] with a rotation-protected signing key) that will be recorded alongside the existing fields. That adds ~2ms write latency and requires a short change to our ingest pipeline.

- Attached is a sample ingest schema we typically share: kafka-ingest-schema.json (stub). It shows where a derived_signed_ts would live.

Proposal / next steps:
1) If Lumen needs a cryptographic timestamp today, we can produce a signed attest document for a selected time window (best-effort).
2) For long term, we propose shipping derived_signed_ts in the next sprint as a configuration toggle for accounts that require it. It will require a minor infra rollout and updates to the log-export path (estimated 2-week effort including QA and canary).

Karthik — can you confirm product acceptance criteria for shipping that toggle and whether we should include an optional retention policy flag in the same rollout?
