I've pulled the pcap and ran a quick correlation with the server-side traces in INF-3421. Notes: 

- I see repeated SYN / SYN-ACK exchanges where the client sets MSS=1460, server/cloud path responds with ICMP Fragmentation Needed (type 3 code 4) for large segments but those ICMPs come back to the appliance and appear dropped by the appliance (no DSCP rewrite, just dropped). That's classic PMTU blackhole.
- Separately, the appliance is performing PAT (SNAT) and reusing source ports aggressively. The cloud-facing side shows ~300 concurrent NAT translations for that customer and we observed several TCP flows failing with RST after port reuse — symptomatic of ephemeral port exhaustion and translation collision.

Immediate mitigations we can try (low risk):
1) On appliance: enable MSS clamping on the WAN/egress interface to 1380 (captures indicate MSS ~1460 -> clamp should avoid fragmentation). Command (example): set interface wan mss-clamp 1380
2) Increase ephemeral port pool on appliance or enable port-preserving SNAT so translations don't collide (device-specific). Example: set nat ephemeral-range 32768-61000
3) On firewall/Security Group: allow the ephemeral port range 32768-61000 for outbound TCP so replies aren't blocked; confirm no restrictive connection tracking timeouts are set below 60s.

Longer-term: the appliance firmware seems to be dropping ICMP type 3 code 4 when under high conntrack churn; we should consider a firmware rollback or vendor fix. I recommend we schedule a rolling config change to enable MSS clamp + ephemeral range increase for tomorrow's off-peak window and monitor.
