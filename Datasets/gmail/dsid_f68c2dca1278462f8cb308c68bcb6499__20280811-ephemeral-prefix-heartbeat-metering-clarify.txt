Hi all — dug into the metering behavior and produced a short explainer + sample math. TL;DR: yes, heartbeats can incur charge but our rules and aggregation windows significantly limit billing impact for tiny maintenance payloads. Details below.

Metering primitives (high-level):
- Tokenization: every request body is tokenized; tokens are the base billing unit.
- Per-request quantum: we apply a minimum per-request token quantum of 8 tokens for very small payloads (this covers protocol overhead and avoids microbilling on tiny network probes).
- Conversation rollup window: messages that share a stable conversation/session identifier (ephemeralPrefix or conversation_id) are rolled up into a 15-minute aggregation window for context billing; that window has a per-window floor of 120 tokens per active conversation per 15-minute window.
- Maintenance bucket: heartbeats that are strictly < 64 bytes and are flagged as "maintenance" by the SDK are subject to a special suppression rule: if the maintenance request is the only event in the conversation window it will incur the per-request quantum only; if it accompanies a generation request in the same window the maintenance payload is zero-rated (not double-billed) because we attribute cost to the generation.

How this maps to your numbers (assumptions):
- 1,000,000 ephemeral sessions/day
- median lifetime 10s => ~0.4 heartbeats per session (since heartbeats every 30s)
- conservative peak estimate 2,000,000 heartbeats/day

Scenario A — no generation calls for the session (pure connect + idle heartbeats):
- Each heartbeat tokenized -> small payload => per-request quantum = 8 tokens billed
- 2,000,000 heartbeats/day * 8 token-quantum = 16,000,000 billed tokens/day
- At your agreed rate (example) that maps to X unit cost — we can translate to dollars in the term sheet.

Scenario B — ephemeral session includes at least one generation in the 15-min window (typical UX):
- The first generation in the window captures the context and is billed normally; maintenance heartbeats in that same window are zero-rated.
- With your traffic profile, if ~60% of sessions trigger a gen within the same window we would only bill the remaining 40% heartbeats as per-request quantum.

KV-cache warmups:
- Small prefix probes that hit the fetch path are tokenized and billed; however we apply a cache-warmup credit for the first prefix probe per unique ephemeralPrefix within a 24-hour rolling window (to limit charges from migrations/reconnects). Subsequent probes are billed normally under the per-request quantum or rolled into an existing conversation window if applicable.

Rounding/minimums/aggregation note:
- Billing totals are computed by aggregating token counts across your account and then rounding each invoice line item to the nearest 1,000 token bucket (to keep invoices readable). This rounding is applied after discounts/credits.

Sample back-of-envelope (peak conservative):
- 2,000,000 heartbeats/day * 8 tokens = 16M tokens/day => ~480M tokens/month (30d)
- If 60% of sessions have a gen in-window -> billable heartbeats drop to 192M tokens/month
