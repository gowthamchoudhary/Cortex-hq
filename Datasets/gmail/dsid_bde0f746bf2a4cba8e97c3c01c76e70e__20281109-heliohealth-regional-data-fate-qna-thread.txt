Hi Helio team — thanks for the clear list. I'll put together concise answers and a diagram. In the meantime:

Quick answers (summary):
- Regions: Primary storage for API request payloads and response logs is per-region (we deploy in us-east-1, us-west-2, eu-west-1, ap-southeast-1). For Helio we can constrain to US regions only; we do not replicate request/response logs to EU/APAC unless configured.
- Default retention: 30 days for request/response logs (used for debugging and billing), 90 days for aggregated telemetry/metrics; KV cache contents are ephemeral and not persisted long-term.
- Deletion: Account-level purge triggers a workflow that deletes live logs, invalidates and removes prefixes from KV caches, and submits background jobs to remove records from our index store and long-term object buckets. Backups are treated separately (see below).
- Backups: We encrypt and snapshot backups; we do not automatically delete snapshot copies on immediate purge — snapshot rotation is on a 90-day cycle by default. For contractual commitments we can commit to shorter snapshot retention or manual snapshot removal per agreement.

Hi — adding the architecture sketch and procedural details you asked for. See the attached PDF for the region mapping; key points below.

Technical details (exported for matrix):
- Storage tiers:
  * Live request/response logs: retained in region-local object store (S3-equivalent) with AES-256 encryption; access-limited via IAM roles.
  * Indexed metadata (searchable traces): stored in region-local index clusters with role-based encryption keys.
  * Aggregates & metrics: aggregated centrally for billing/ML features but contain no PII unless customer opts in.
- Deletion workflow (account purge):
  1) Customer request received via Console API -> triggers 'purge-request' event.
  2) Synchronous deletion: remove live log objects and indexed metadata pointers within the region.
  3) Asynchronous jobs: kick off background workers to scrub object-store manifests and reindex affected buckets (progress tracked in audit log).
  4) Snapshot handling: identify snapshots containing the account and mark for expedited retention expiration; physically delete within agreed SLA (default snapshot TTL 90 days; contractual SLA required for shorter windows).
- Backups & DR: backups are encrypted and immutable for a short window; we provide proof of disposal when manual snapshot deletion occurs.

Hi Sam — answering each of your clarifications inline below.

On Thu, Nov 09, 2028 at 09:18, Samuel Greene <samuel.greene@heliohealth.com> wrote:
> Can you confirm whether deletion is cryptographic (re-keying/crypto-shredding) or logical object removal only?

We perform logical object removal for live objects and metadata pointers (we delete manifests and index entries). For snapshots, we support crypto-shredding (re-keying) as an add-on for customers that require cryptographic certainty; this is done by removing the key material in the KMS/HSM and marking snapshots as inaccessible before physical deletion. If you require crypto-shredding as part of the SLA, we can include that in the contract.

> For the account purge, how long until snapshots containing deleted data are physically removed if we sign a 30-day snapshot SLA?

If you sign a 30-day snapshot SLA we will schedule expedited deletion and ensure snapshots are permanently removed within 30 days. The background deletion job will also report progress to the audit log and the console.

> Do you provide an audit log entry per object deletion that we can pull for our records?

Yes — every purge job emits audit records with object-key lists and job status. You can export these logs via the Console (Security -> Data Actions -> Exports) or via the Audit API.

Plain-English line you can paste: "By default, live API request/response logs are stored in the customer-selected US region for 30 days; snapshots and backups are retained for 90 days by default but can be shortened by contract."
