Hi Anita — thanks for the clear list. Below is a concise proposal that should map to CedarPoint's audit needs; happy to iterate.

Proposed purge cadence (default):
- Incremental workspace logs: retained 30 days, automatic prune daily.
- Full snapshots (point-in-time data exports): retained 90 days, then tombstoned and purged at 90 days.
- Backups stored in cold-tier: lifecycle transition at 7 days, permanent delete after 365 days (unless escrowed).

Emergency rollback window and recovery SLA (operational):
- Standard rollback window: 14 days from purge execution (we keep tombstones + KV cache for 14d to enable efficient restores).
- RTO for a single-customer full-snapshot restore: typically 6–12 hours depending on dataset size; RPO depends on incremental schedule (max 1hr for high-throughput workloads).
- For restores beyond 14d we can provide an escrow retrieval process (longer lead times & costs apply).

Evidence we can provide:
- Deletion manifest (CSV listing object keys + purge timestamps) — sample attached (deletion_manifest_sample.csv).

Adding ops detail (runbook excerpt below) — this is the operational rollback we would execute if an accidental purge is reported within the 14-day window.

---- runbook excerpt ----
1) Identify purge job id and affected object keys (from purge job output).
2) Mark affected tenant as high-priority in restore queue.
3) Pull tombstoned snapshots from cold-tier index (tombstone TTL is 14d).
4) Rehydrate snapshot to staging cluster; integrity check (SHA256) against manifest.
5) Promote to primary, QoS checks, run smoke tests.
6) Notify stakeholder and close incident.

Estimated timing: 6–12 hours for typical 2TB tenant. For very large datasets (>=20TB) plan 24–48h.

We can run a one-off restore test if CedarPoint would like to validate RTO; we will need a signed test authorization (DocuSign) and coordination for a maintenance window.
