Naomi — thanks for the clear brief. Quick summary/recommendation up front: go with AWS PrivateLink (interface endpoints) for the pilot; propose adding a peering option for production if they need cross-account native routing later.

Why PrivateLink for the pilot (short):
- Security: preserves a managed service surface; customer never needs to expose public endpoints and can keep tighter network controls (SGs + endpoint policies).
- Operational isolation: less chance of route-table mistakes affecting other workloads compared with broad peering.
- Auditability: CloudTrail logs for interface endpoint calls + flow logs give the audit trail EdgeCorp wants.

Top 3 risks / mitigations:
1) Cost for per-AZ ENIs if multi-AZ scale is later required — Mitigation: start single-AZ; quantify ENI cost in the matrix and set thresholds for when to transition to peering.
2) Source IP preservation: PrivateLink changes source to ENI IPs, so EdgeCorp's allowlist must accept our endpoint ENIs or we must configure proxying — Mitigation: document ENI IP ranges and update their firewall runbook; include IP rotation cadence.
3) Throughput contention on ENIs during bursts — Mitigation: size testing during POC, add autoscaling/burst policy on Redwood Dedicated side or fall back to peering for heavy sustained throughput.

Required artifacts to hand over:
- Runbook: interface endpoint creation checklist, required SG rules, example endpoint policy (I drafted redwood-privatedeploy-checklist.md).
- IP list: initial ENI addresses (and update cadence) + CIDR ranges we will use.
- Test plan: synthetic load test steps and acceptance thresholds.
- Contacts: NetOps primary and escalation phone/email.

I'll attach a trimmed matrix (see comments in your spreadsheet). If EdgeCorp needs source-IP-preservation guaranteed, the fallback is peering or an IP-in-IP proxy we operate (more operational cost).

Short note from procurement/ops perspective: PrivateLink is the lowest-risk pilot path and keeps negotiations simple (no cross-account peering approvals). Two operational notes:
- If EdgeCorp expects <100ms p95 for inference, validate path P95 during POC; PrivateLink adds a small hop but is usually fine for single-AZ.
- VPN (site-to-site) is the slowest to iterate on — often involves firewall ticketing windows and cert rotations. Good for customers who cannot accept any cross-account endpoint at all, but heavy lift for a pilot.

My vote: PrivateLink + documented escalation to peering if we see sustained high throughput or if EdgeCorp wants their origin IPs preserved for strict logging policies.
