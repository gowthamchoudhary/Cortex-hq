Thanks Logan — digging in.

Short answer: we have a known corner where the routing emission is gated behind a non-critical path; under heavy KV cache evictions we can miss emitting the routing decision when the request is short-circuited by a cache miss + fast-fail. Not widespread but plausible for Brightlane's traffic profile.

Immediate asks for triage:
- Can you share a couple of request ids (from sre-error-snippet.txt) so we can match across layers? (prefer 3-5 ids)
- Please enable SDK verbose telemetry for Brightlane (sdk.log_level=debug) and toggle 'client.routing.retry_window_ms' to 150 (their default is 50) — this will reduce retry storms and give us more stable routing.

Short-term mitigation we can ship as a 1-line runtime hotfix: set runtime.fallback.force_emit=true which moves routing emission earlier in the pipeline. It should be safe; I can prepare a patch and smoke test on staging if you approve.
