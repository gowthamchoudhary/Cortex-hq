Erin — great questions. Short answers up front:
- Milvus v2.2 is supported as a target vector store for our backfill; we commonly use an export/import pattern (bulk insert) to avoid per-document RPC costs.
- No reads required to be offline while we hydrate a parallel index. We suggest dual-read routing during validation and then a DNS/traffic switch for final cutover.

More details / recommended approach:
1) Backfill strategy (phase A/B/C)
   - Phase A (seed): backfill documents with highest traffic & recent recency first (parallel worker pool, low priority IO).
   - Phase B (bulk): parallel bulk imports into Milvus with sharded batches, track insert latency and failed ids in a monitoring table.
   - Phase C (catch-up): tailing ingestion for any writes that occurred during bulk import and final consistency check.
2) Dual-read validation
   - We will route a percentage of production traffic to the new index (starting 1%, then 5%, 20%) and compare top-K results plus rerank score deltas.
   - Acceptance criteria: <3% drop in CTR-equivalent metric on sample queries or manual QA signoff.
3) Rerank evaluation
   - Use the rerank-eval-samples.csv you have; we will return normalized NDCG and pairwise preference results and attach example failure cases.
4) Operational notes
   - Memory-optimized nodes recommended for Milvus import to avoid OOM during large batches. If you prefer, we can perform the backfill from a Redwood-hosted worker pool with secure S3 access.

Cutover runbook highlights (attached runbook has step-by-step):
- Pre-cutover: run dual-read validation for 72 hours with <1% traffic to new index, confirm top-5 overlap >= 85% on sampled queries.
- Cutover steps:
   1) Pause writes to search index (enter maintenance mode).
   2) Final tailing ingest and consistency check (verify missing ids < 0.01% of total).
   3) Promote new index and switch routing.
   4) Monitor traffic and rollback to old index if search error rate increases > 1% or P95 latency worsens > 40%.
- Rollback: immediate DNS rollback and resume writes to previous index; we keep previous index intact for 24 hours as a hot fallback.

Smoke test checklist (we'll run these during the maintenance window):
- Run 500 representative queries and compare top-5 overlap and rerank score diffs.
- Validate embeddings dimensionality and checksum on a 1k-doc random sample.
