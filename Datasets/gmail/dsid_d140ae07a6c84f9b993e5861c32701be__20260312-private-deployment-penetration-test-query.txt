Hi Janelle — apologies for the quick note but wanted to get the technical boundary details in front of you. Below is a concise summary; I attached the longer PDF and remediation tracker to this thread.

Deployment patterns we commonly support (high level):
1) Customer-managed VPC (recommended for regulated workloads):
   - Control plane: Redwood-managed control plane services run in Redwood cloud (API, console) and are out-of-scope for customer-run VPC tests, unless agreed.
   - Data plane: Customer provisions subnets and instances (or EKS nodes) in their VPC; Redwood Private agents (container workloads) run on those customer-hosted nodes. These agents are in-scope for the customer VPC test.
   - Network egress: We support private endpoints and VPC endpoints; egress to Redwood control plane is limited to specific, documented service endpoints (we will provide FQDNs and IP ranges for routing/firewall rules).

2) On-prem / air-gapped bundle:
   - Entire stack is in customer control; pen test scope is fully within customer environment. We provide build artifacts and guidance for verification.

Typical pen-test scope we recommend for customer VPCs:
- Host/container runtime hardening (kernel packages, container runtime CVE checks)
- Network segmentation tests (east-west and ingress filtering, private endpoints)
- API auth & session management tests (token handling, replay, privilege escalation)
- Key management and secret handling (KMS/HSM integration points)
- KV cache isolation and unauthorized access to model state

Boundary assumptions to confirm before an engagement:
- Which subnets/instances does the customer consider in-scope? (provide subnet IDs)
- Whether Redwood control-plane endpoints will be reachable from the test VPC (we can provide test IP ranges if you want us to be a test actor)
- Expected level of exploitation allowed (read-only vs active privilege escalation)

Remediation summary (high level):
- All critical/high findings from our latest Private engagements were addressed within 30 days; fixes include kernel upgrades (Ubuntu 22.04 -> latest LTS kernel patch), container runtime pinning to patched versions, and stricter pod-level seccomp profiles.
- We closed an API auth token refresh issue (ticket SEC-1123) and rotated affected keys; evidence is in the remediation tracker.
- We hardened KV cache ACL checks and added additional audit logging to detect unauthorized cache access.

Attachments included: redwood-pen-test-summary-2026-03.pdf (redacted), remediation-tracker-SEC-1123.csv

If you prefer Redwood to perform the test inside your staging VPC, we can sign an SOW addendum and coordinate a narrow time window. Otherwise, the redacted report + remediation tracker is usually acceptable for procurement gating.
