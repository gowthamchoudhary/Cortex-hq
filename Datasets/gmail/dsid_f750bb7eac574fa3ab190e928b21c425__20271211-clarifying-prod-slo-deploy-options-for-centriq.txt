Hi team — thanks for the intro. Per Kimberly’s note, here’s a concise pre-read so the live deep-dive can be focused. I’ve attached two artifacts (centriq_slo_template.xlsx, deployment_options_diagram.png).

Summary of assumptions we used for the estimates below:
- Model family: medium-sized Llama-like open model (~13B) running with 512-token context.
- Hardware scenarios: RTX A5500 equivalent (single-GPU per-replica) vs DGX-class (multi-GPU shards) vs dedicated private pool (8x L4-like per-pod) for density comparisons.
- Workload: 200 qps peak; average prompt ~60 tokens; response avg ~40 tokens; session stickiness 70% (multi-turn).

Topline SLO estimates (95th percentile latency, end-to-end generation):
- Hosted (private-peered) – warm paths with KV cache in-GPU: 95p ~450–650ms; 99p ~900–1,200ms.
- Dedicated VPC (single-GPU optimized + aggressive autowarm): 95p ~380–580ms; 99p ~850–1,000ms.
- Sharded multi-GPU setup (for larger model variants): 95p ~600–900ms depending on interconnect and batching window.

Notes on batching & throughput management:
- Continuous batching at 10–30ms windows gives best cost/latency tradeoff for your QPS; tighter windows reduce latency but raise unit cost.
- For 200 qps peak, target pod sizing: 6–10 single-GPU replicas with hotspot autoscale (burst to 14) depending on model quantization.

KV cache strategy (recommendation):
- Primary: in-GPU KV for highest hit-rate and lowest tail latency (works well for >60% reuse).
- Fallback: external Redis cluster with local smart prefetch for cold sessions; this avoids cold-GPU penalty but adds network hop ~20–40ms.
- Warm pool: maintain a small set of warmed GPUs per region preloaded with top sessions to eliminate cold-starts during spikes.

Quantization & cost delta (ballpark):
- int8: ~1.6–2x throughput improvement vs fp16, tail latency typically reduced 10–25%; token-cost delta depends on licensing and throughput but raw compute cost per token down ~35–45%.
- 4-bit: additional throughput but requires careful quality checks; expect another 15–25% compute savings vs int8 in favorable models.

Security & KMS integration (private deployment):
- We support customer-managed KMS via standard envelope encryption + HSM-backed keys. For private VPC deployments we terminate TLS inside your VPC and never store plaintext outside.

2) Is there a hard upper bound on acceptable 99th latency for support-chat flows?
3) Will you consider a quantized variant for the pilot or prefer fp16-only for quality first?
