- Update/repin/rollback process: Normal updates follow a staged rollout (canary → 25% → 100%) with a minimum 7-day notification window for enterprise accounts; emergency rollbacks are initiated within our 1-hour SLA for critical regressions and will restore the previous signed artifact (we retain blobs and manifests). - Provenance: Each manifest includes a provenance_chain field that references upstream checkpoints (commit hashes, dataset manifests, license provenance). We store these references immutably alongside the model artifact.

Thanks for the thoughtful questions. Below are numbered answers mapping to your list. Kim (Legal & Compliance) and Marissa (Product) are cc'd for any follow-ups or to provide artifacts.

1) Mixed-license models: Manifest strategy and runtime enforcement
- Representation: The manifest includes a "license_breakdown" section that itemizes artifact-level and component-level licenses with a short canonical id (e.g., Apache-2.0, CC-BY-SA-4.0), source_url for the origin, and the percentage contribution score (estimated) where available. Example manifest snippet (annotated in attachments):
  {
    "model_id": "redwood/kestrel-7b-open-v2",
    "version_tag": "20271215",
    "artifact_digest": "sha256:3b7f9e...f2a1",
    "license_breakdown": [
      { "component": "base_weights", "license": "Apache-2.0", "source_url": "https://repo.example/base", "contrib_pct": "88" },
      { "component": "fine_tune_corpus", "license": "CC-BY-SA-4.0", "source_url": "https://datasets.example/corpus", "contrib_pct": "12" }
    ]
  }
- Runtime obligations: When a CC-BY-SA component is present, we surface an "obligations" field in the manifest that lists attribution text, distribution constraints, and recommended controls (e.g., disable redistribution of model weights, require provenance notice in UI). These obligations are surfaced to operator consoles and can be enforced via policy hooks in Redwood Dedicated/Private deployments (e.g., disable export endpoint).

2) Re-licensing / downstream rights
- Guidance: Redwood provides a usage posture mapping (dev/staging/prod/redistribution) per license class. We do not relicense third-party artifacts; we only publish manifests that declare upstream licenses. For share-alike licenses we treat outputs as potentially derivative and include conservative guidance to customers in the manifest. Customers can choose a restrictive runtime posture or request a dual-license from the original upstream where available.
- Commercial guarantees: We can provide contractual language (SOW/TOA) around tooling and controls (e.g., non-export clause, UI attribution obligation), but we do not make representations about third-party relicensing rights beyond the manifest provenance.

3) Cryptographic attestation
- Signing: Manifests and artifact bundles are signed with an organization key. Fingerprint (SHA-256 of public key): 9F:3B:4C:AA:11:7D:88:EE:5B:2D:0A:4C:23:9E:7F:5A:8C:2D:3A:6B:1E:44:C0:77:8D:91:3F:62:BD:AA:12:3F
- Sample signed manifest: See attached manifest-sample.json (signed) and redwood-model-manifest-v1.2.pdf. We also provide a small verification script (Python, open-source) that verifies signature + digest; if you want we can produce a statically-signed tarball for procurement to verify offline.

4) Retention and audit logs
- Actions logged: Every pin/repin/rollback, who initiated, who approved (if approval was required), rollout percentages, and timestamps are recorded in our immutable audit store. For enterprise accounts we provide log export (S3/CloudWatch) for the configured retention window.
- Retention policy: By default we retain artifacts and manifests for 18 months; on enterprise contracts we can extend to multi-year retention or indefinite preservation (we keep object blobs and manifest snapshots).
- Evidence export: We can emit a bundle containing the signed manifest history, signatures, and an approval chain CSV that satisfies standard procurement evidence requests.

Operational notes / additional options:
- Immutable pins: For sensitive accounts we offer an "immutable pin" feature that prevents repinning without an out-of-band legal approval and two-person engineering sign-off.
- Canary & tests: Repins trigger an automated pre-deploy test battery (sanity, perf regression, and a small coverage eval against saved prompt-suite) before canary promotion. Failure blocks rollout.
- Private deployment: If Globex requires, Redwood Private can run the pinning service in your VPC with local KMS for signing to satisfy more restrictive custody needs.
