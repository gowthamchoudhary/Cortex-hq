High-level answers and action items:

- SDK + Auth:
  * Redwood SDK supports both API-key short-lived tokens and OIDC flows. For your 30-minute rotation we recommend using short-lived API keys issued by your KMS/HSM and configuring the SDK to refresh on 401 with a single background refresh per process (mutex).
  * Implementation effort: low (1-2 engineer days to wire refresh + error handling).

- Routing / Regions:
  * Policy-based routing can be configured per API key or per route. You can pin specific routes to your private us-east deployment and allow fallback to hosted variants for non-sensitive requests.
  * We’ll provide a sample routing policy config snippet.

- Structured output / tool calling:
  * Use Redwood’s function-calling schema with explicit type contracts; emit a stable top-level wrapper (e.g., {"tool_call": {...}}). Validate outputs server-side and implement a small orchestrator that treats failed tool calls as retryable sub-tasks rather than re-generating the entire prompt.

- Throttling / 429s / Idempotency:
  * Recommended approach: client-side exponential backoff with full jitter, max 3 retries for safe idempotent calls (e.g., embeddings, generation with request-scoped idempotency keys).
  * For state-changing operations (tool calls that trigger billing or external side effects), attach an idempotency header: X-Request-ID (UUID v4) and persist mapping for 72 hours.
  * Also recommend 429-aware circuit-breaker on your gateway with dynamic queueing to smooth spikes.

Alyssa — attaching the quick SDK examples below inline for convenience. Happy to run a 30-min sandbox session.

1) Token refresh pattern (pseudo-code):
- On 401, acquire mutex and call your token service to fetch a fresh API key. Retry request once after refresh.
- Fail open only for read-only routes; block for state-changing routes.

2) Routing policy (YAML):
- routes:
  - path: /v1/generate
    priority: high
    target: private-us-east
    fallback: hosted-us-west

3) Idempotency and 429 handling (recommended policy):
- All requests that can mutate external state must include X-Request-ID: <uuid-v4>.
- Retry policy: initial_delay=200ms, backoff=2.0, max_retries=3, jitter=full.
- On 429: honor Retry-After if present; otherwise apply backoff.
- If Retry-After > 5s, enqueue and respond to caller with 202 Accepted + polling handle.

4) Embeddings / rerankers guidance:
- Compute embeddings async in batches (client-side batcher) and attach batch_id header.
- Use a deterministic embedding key per document to avoid re-ingestion duplicates.
