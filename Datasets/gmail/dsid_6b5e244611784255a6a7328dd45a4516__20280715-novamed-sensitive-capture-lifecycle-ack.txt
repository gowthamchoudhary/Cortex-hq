Ellie — thanks for the sharp follow-up, and great question. Short answers up front: 1) No, hosted inference does not persist full prompt payloads to long-term object storage by default — we keep in-memory/ephemeral buffers and short-lived KV caches for active sessions only. 2) Model outputs are not persisted beyond short diagnostic retention unless configured or requested; default TTL for output traces in hosted is 0 days (ephemeral) for standard customers, with optional opt-in retention for troubleshooting/quality monitoring.

I'm attaching a one-pager that summarizes our default behaviors and the available configuration knobs (redwood_data_retention_onepager.pdf). Below are the details your security team typically asks about. If you want, Jasmine can join your security call next week to run through both the matrix and a sample retention CSV.

Summary details:
- Prompt payloads: Ephemeral in-memory processing; no write-to-disk for hosted API requests under standard plan. We maintain short-lived KV cache in RAM for active sessions; caches are evicted per LRU and never persisted to disk.
- Output responses: Default: ephemeral (not stored). Optional: customers can enable 30/90/365-day retention for outputs for debugging or evaluation via per-account config and explicit data retention policy. Enabling retention routes outputs to an encrypted object store in the chosen region.
- PII redaction: We offer an optional preprocessor that can hash or redact configured sensitive fields before they reach the model.
- Logging: Audit logs (control-plane events) are persisted for 90 days by default; request-level telemetry (latency, token counts) is separated from payloads and contains no prompt text unless retention is enabled.

Sample mapping (field, store? , default ttl, storage location):
- patient_name: not stored by default; redaction/hash recommended if the app sends PII.
- mrn (medical record number): not persisted in hosted default; recommend pre-hash or tokenization. If retention enabled -> 30d (s3-us-west-2, encrypted).

A couple of operational notes:
- Enabling retention creates a per-account encrypted bucket in the selected region and a narrow IAM policy so only the customer and Redwood's debug service can access (audit logs for access are included).
- We support custom retention windows per-field on Dedicated/Private plans; hosted allows account-level TTLs (30/90/365).
- Deletion is asynchronous; deletion jobs run nightly and are manifested in audit logs (we can provide a sample manifest for compliance).

Ellie — quick technical confirmation on the KV cache behavior: default hosted path keeps KV cache in GPU/host memory and we do not swap to persistent disk under normal operations. Under extreme memory pressure on Dedicated hosts we may write memory-backed paging artifacts to ephemeral instance storage; these artifacts are encrypted and scrubbed on instance termination and are not part of the account-level retention buckets. For compliance reviews we can provide a short technical note describing eviction behavior and the scrubbing process.

One more item: if NovaMed needs an air-gapped or Private deployment, we can guarantee zero outbound persistence to Redwood-managed object stores — the Private offering routes all storage to customer-managed buckets and full KMS control.
