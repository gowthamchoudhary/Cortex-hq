Alice / Priya —

Thanks — quick technical answers from our side:

1) Long-context flows (≈2.5k tokens): map these to the p1-heavy profile. That profile reserves larger KV cache and uses the quantization profile we discussed (q4-mix). I’ve annotated the spreadsheet with expected memory footprints and per-GPU rps at both 50% and 100% replay.

2) Fallback behavior: when reserved capacity is saturated, routing will automatically try the next compatible model pool (hosted API) with a soft-fail policy. From a user perspective you will see increased latency for affected requests and in rare cases (if hosted is also saturated) a 503 with a JSON payload: {"error":"temporarily_unavailable","message":"Please try again momentarily"}. We’ll surface a per-request header x-rw-fallback: hosted in your logs so you can instrument client-side behavior.

3) Acceptance criteria for the rehearsal (suggested):
- 95th percentile latency stays within 1.5x of hosted baseline for top 10 routes at 100% replay
- KV-cache hit rate delta < 8% vs hosted baseline
- No silent data path regressions in request/response traces
