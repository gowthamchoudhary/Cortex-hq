Hi Lila — thanks for the detailed requirements. Copying a few technical constraints here so procurement has full context.

Summary of what Redwood can commit (hosted vs what requires Dedicated):
- Hosted tier (standard): operational SLO baseline is 99.9% regional availability. We provide per-route token-level latency histograms and a monthly SLI export.
- Dedicated reserved capacity (contracted GPU pools): we can commit to 99.95% regional availability for explicit reserved capacity configurations; achieving 99.975% typically requires a Dedicated + cross-region replication plan with warm standby.

Failover and "detection":
- We can define "detection" as either (a) automated healthcheck + automatic routing switch (full automation) or (b) monitoring detection followed by operator-confirmed failover. The contract needs to specify which; automatic failover is supported but only if you accept automated routing and warm-warm replication on the backend (this has cost/standby implications).

Telemetry we can provide:
- Monthly SLI export (CSV) with per-region availability, request counts, P50/P95/P99 latency buckets at token/request granularity.
- A shared dashboard link for rolling 30/90 day SLO windows.
- Ad-hoc debug snapshots on request (requires signed DPA amendment if it includes debug traces).

Operational notes on credits and runbooks:
- If you require sub-15 minute contractual detection-to-failover, we will need to include a standby-capacity uplift line item on the order form (sizing and monthly charge TBD).
- We'll propose a three-tier credit schedule (severity based). In practice we aim to avoid punitive credits by offering conservative, measurable SLI definitions and automatic fallback to a degraded-latency profile while preserving throughput.
