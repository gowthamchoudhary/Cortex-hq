High level thoughts / questions:

- \"Pinning\" can mean a spectrum: (A) soft routing preference with TTL (route tenant X to model v1 unless capacity forces fallback), (B) strict residency (allocated warm pool pinned to tenant + model), or (C) model-variant lock on the control plane (requests always see the same model artifact but may run on shared pools). Each has different cost/complexity.

- If customer is set on deterministic outputs, soft routing (A) carries risk under contention; (B) is safest but looks like a Dedicated-style commitment.

Questions for CobaltX we should surface now:
1) Expected sustained QPS at pilot peak and 95th percentile latency SLA they need.
2) Appetite for a short reserved capacity commitment (even a small burst pool) vs. strict hosted SLA.

Short answer: feasible, with trade-offs. Longer:

Option A — Soft routing + TTL (lowest effort): ~1–2 engineering sprints (2–4 weeks) to add tenant routing TTLs, dashboards, and a policy that avoids fallback for pinned tenants except under critical capacity pressure. Pros: fast, no infra churn. Cons: not strictly deterministic if we hit contention.

Option B — Tenant residency (hard pin / warm pool): requires allocation changes to scheduler, tenant affinity keys in serving runtime, and warm-pool orchestration: estimate 6–8 weeks (including testing + canary). Pros: deterministic behavior, predictable latency. Cons: increased resource costs and provisioning work; edges toward Dedicated semantics.

Option C — Control-plane model-lock (artifact-level pinning): small effort to ensure model version is fixed per tenant in control plane (~1–2 weeks) but requests still run on shared pools — good middle ground if customer accepts best-effort latency.

Interim workaround we can offer this month: 1) model artifact lock + 2) scheduled burst reservations during their peak demo windows (automation to pre-warm KV cache) — this would give near-deterministic outputs for a limited window while we execute a longer-term residency plan. We have an internal draft spec (pinning_spec_draft.md) attached.

Critical engineering notes:
- KV cache pre-warm hooks exist but need an ops playbook to trigger per-tenant.
- Rollback is straightforward if we keep control-plane lock reversible; warm-pool changes need runbook for de-provisioning.

If Sales wants a firm canary date in December, the interim workaround is the only realistic path unless CobaltX accepts a small Dedicated commitment.
