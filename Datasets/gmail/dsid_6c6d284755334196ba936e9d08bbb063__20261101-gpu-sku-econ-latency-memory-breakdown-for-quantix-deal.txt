Claire — thanks for the clear profile, that helped. I ran a quick pass with our cost/latency model and here are my top-level recommendations (highly condensed):

Summary recommendation (hybrid tiered pool):
- Reserved H100-heavy pool for long-context analytics and large-model sessions (slot size: 1 H100 per 2 active long-context requests with 12GB KV cache headroom).
- A100 mid-tier reserved pool for the 2k-context chat model (best cost/latency balance at medium batch sizes).
- L4 burst/embeddings pool (on-demand or small reserved cluster) for high-volume embeddings and cheap alignment calls.

Why this mix? Quick tradeoff bullets:
- H100: best for memory-bound long-context workloads due to larger aggregate model shard memory and higher memory-bandwidth; yields predictable 95p latency for 8k+ contexts. Higher unit cost but reduces failures and simplifies placement.
- A100: sweet spot for latency-sensitive 2k chat — good throughput at lower cost compared to H100 when model fits GPU memory comfortably.
- L4: very cost-effective for embeddings and low-precision workloads; can be used for background batch embedding jobs and as a cheap overflow for simple prompts.

Back-of-envelope numbers (simulated using your traces):
- Target sustained QPS 65 -> concurrent active tokens/sec mapped to slot counts gives approximate reserved counts: H100 x6, A100 x9, L4 x4 (these are conservative, include 20% headroom).
- Estimated 95p latency with this mix: chat (A100) ~180ms, long-context (H100) ~210ms, embeddings (L4) <60ms.
- Monthly blended cost (reserved rates + modest burst): ~estimated $Y (see spreadsheet).

Operational notes / risks:
- Cold-start KV cache: long-context sessions suffer first-request penalty — recommend prewarming strategy for known heavy clients.
- Autoscaling fallthrough: configure routing policy to degrade to A100 for non-critical long-context jobs if H100 capacity exhausted (with clear SLA flags).
- Quantization: we can recommend an INT8 path for embeddings on L4 to reduce token cost further.
