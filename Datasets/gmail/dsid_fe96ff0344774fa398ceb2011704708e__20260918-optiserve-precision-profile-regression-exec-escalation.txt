Quick preliminary read after scanning the traces and runtime logs attached:
- We see a sharp increase in kernel fallback events on the serving nodes handling OptiServe traffic immediately after the precision-profile P2 was enabled. Fallbacks are due to quantized attention kernels not matching the sequence length distribution for these hot routes — that forces a generic (slower) code path.
- The increased 5xxs look like downstream timeouts from token decode stalls and queueing backpressure.

Immediate recommendation (fastest mitigation):
1) Roll P2 -> P1 (previous precision-profile) for the OptiServe deployment (can be done without a full model rollback). This should restore kernel selection to the fast path.
2) If rollback is not acceptable, apply traffic-weighted canary: 5% -> 20% -> 50% while monitoring kernel fallback metrics.

I can push the rollback now and validate with a smoke test. If we do this, expect p99 to drop within 2–5 minutes after the change if this is the root cause.

Logs/IDs I looked at: trace ids 8f3a2c, 8f3a9e, 8f3b10 (included in CSV).
