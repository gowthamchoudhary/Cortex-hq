Draft retry & idempotency guidance (please edit):
- 429 handling: honor Retry-After header when present. If absent, apply exponential backoff with full jitter: base 200ms, backoff factor 2, cap 30s. Max retries: 5.
- Idempotency: require client-supplied Idempotency-Key for POST/upsert semantics on embeddings and reranker jobs. For embeddings upserts, recommend deterministic content-hash (sha256 of normalized input) combined with customer id to prevent cross-tenant collisions. Server should detect duplicate idempotency-key and return 200 + existing resource id.
- Request IDs: require X-Request-ID on all calls. If not present, SDK injects one. Store request-id in logs and surface it in error payloads for customer debugging.
- Retry semantics & billing: document that retries may be billed depending on whether the server accepted the request before failing (we’ll add visibility hooks in Console).
- Circuit-breaker: per-api-key failure rate threshold (e.g. 5xx/429 > 10% over 60s) triggers short cooldown and fallback to queued batch path.

Risks to call out: retries without idempotency keys => duplicates; naive exponential backoff may still be too aggressive for hotkeys; missing request-id complicates SRE troubleshooting.

try {
  const resp = await fetch(endpoint, { method: 'POST', headers, body: JSON.stringify(body) })
  if (resp.status === 429) {
    const retryAfter = resp.headers.get('Retry-After')
    if (retryAfter) {
      await sleep(parseInt(retryAfter) * 1000)
    } else {
      // exponential backoff w/ full jitter
      await backoffWithFullJitter({ base: 200, cap: 30000, factor: 2, attempts: 5 })
