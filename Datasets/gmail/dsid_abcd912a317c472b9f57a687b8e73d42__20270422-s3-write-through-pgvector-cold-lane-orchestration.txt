Logan,

Thanks for taking this on. At VectorGlue we’ve been exploring a hybrid persistence pattern that keeps hot vectors in pgvector for sub-50ms read/write workloads, while archiving older vector shards to S3 cold lanes with object keys tied to index segments. The motivation is predictable storage cost and easier long-term retention.

We sketched a few items we think are important and wanted to flag them before the call:
- Write semantics: prefer write-through to pgvector (fast index updates) with async tombstone + flush to S3 for colding.
- Consistency: reads should fall through to S3 if pgvector miss; need TTL-based prefetch/rehydration on read paths.
- Metadata: object keying must include model id, namespace, and index epoch to support incremental reindexing.
- Cost model: expect egress when rehydrating; we’d like your input on batching strategy to reduce token-level cost.

Can you share Redwood’s operational constraints (SLOs, acceptable rehydrate latency), and whether you have preferences on where to run the canary (hosted vs dedicated)?

Attached is a rough diagram and our cost sketch. Would love to sync Wed or Thu.

- SLOs: for the pilot we target read p50 < 60ms for hot hits, and cold rehydrate p95 < 3s (acceptable as background fallback).
- Canary: we prefer running the initial canary on a Redwood Dedicated slice in us-west1 to better measure tail latency under realistic queueing.
- Batching: we’ll apply prefix-aware batching for rehydrate reads and use a short adaptive prefetch window for namespaces with >1 read/sec.
- Ownership: Redwood will implement the routing policy and read-fallthrough in the serving runtime; VectorGlue will own the S3 object layout and lifecycle hooks.
