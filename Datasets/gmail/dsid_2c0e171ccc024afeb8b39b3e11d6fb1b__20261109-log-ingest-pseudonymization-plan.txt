High-level technical options we discussed (R&D + recommended next steps):
1) Edge redaction (recommended for highest assurance)
   - SDK or sidecar that scrubs sensitive fields before they hit Redwood ingest. Works for request bodies, headers (X-Forwarded-For, Authorization), and custom fields.
2) Cryptographic pseudonymization
   - Compute an HMAC of the original trace ID / user ID using a customer-managed key (KMS). One-way unless key is compromised. Allows stable per-customer tokens for cross-request correlation.
3) Ephemeral mapping service (VPC/private deployment)
   - Map raw IDs to short-lived tokens in a customer-controlled store (TTL configurable, e.g., 24h). Provides correlation while minimizing long-term risk.
4) Aggregation & sampling
   - Store only aggregated telemetry for analytics and keep sampled payloads with redaction rules applied.

Trade-offs to note:
- HMAC/pseudonymization preserves correlation but requires KMS management and careful rotation policies.
- Edge redaction prevents sensitive data from leaving customer boundary but requires integration effort on your side.
- Full retention/archival needs can be configured per-bucket with lifecycle policies; audit logs can be kept separately with restricted access.

Hi Amy / Rafael — looping in a few technical details from the engineering side so we can be explicit for SecOps. Short answers up front: yes, both HMAC-based pseudonymization and edge redaction are practicable; they have different operational trade-offs.

HMAC / KMS approach (one-way tokenization)
- Mechanism: compute HMAC(key=customer_kms_key, message=raw_trace_id || customer_id) and store the HMAC value as the token in logs.
- Security: the original trace ID cannot be reconstructed from the HMAC without the KMS key. If the key remains private to your KMS, logs alone are insufficient to reverse the mapping.
- Considerations: key rotation -> token stability. If you rotate keys, tokens will change unless we maintain a key-rolling compatibility window.

Edge redaction / SDK approach
- Mechanism: a small SDK or sidecar inspects outgoing requests and removes or replaces configured fields before they leave your network.
- Advantages: raw PII never reaches Redwood infrastructure. Simpler for audits but requires integration and testing.

Ephemeral mapping (private deployment)
- Mechanism: run a mapping service in your VPC that returns short-lived opaque IDs. Redwood only sees these opaque IDs. TTL configurable (e.g., 6h–24h).
- Advantage: allow short-lived correlation without long-term risk.

Logs & retention
- We can configure per-bucket lifecycle policies in your account for 30/90-day windows. For Hosted customers, we provide tenant-scoped buckets with server-side encryption; for Dedicated/Private we recommend customer-managed buckets.
