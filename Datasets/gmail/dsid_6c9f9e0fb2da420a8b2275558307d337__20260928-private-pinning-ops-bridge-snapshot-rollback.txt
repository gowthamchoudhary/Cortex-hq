Hi team,

Quick summary: MeridianCloud and Redwood need to agree on a concrete pin-rotation + snapshot rollback pattern for our Private deployment (vpc/on-prem customer clusters) so we can schedule a maintenance window without risk to pinned model versions or customer entitlements. I put a starter proposal in the attached CSV (proposed-pin-rotation.csv) and a lightweight snapshot checklist (snapshot-checklist.md).

Goals for this thread:
- Confirm the operational handshake (who triggers snapshots, who validates success)
- Define maintenance window boundaries (drain, cutover, post-checks)
- Agree on rollback triggers and the fastest path to revert to a pinned version via snapshots
- Identify network tasks Meridian needs to perform (ACL changes, BGP hold-downs) and schedule them into the window

Key constraints:
- We must preserve customer pinned model versions for 72 hours post-upgrade as a safety window.
- KV cache migration should be non-blocking; if cache regen is needed, we want clear traffic-shedding thresholds.
- Snapshot operation must be atomic for model artifacts + config blob.

Proposed high-level cadence (see CSV for per-customer rows):
1) Preflight (T-48h): create test snapshot and validate restore on a staging subnet.
2) Pre-drain (T-2h): start graceful drain of canary hosts and scale down background workloads.
3) Snapshot (T-30m): take final snapshot of model artifacts and config.
4) Pin rotation + deploy (T0): rotate pin on controllers and start staggered rollout (canary -> 20% -> 50% -> 100%).
5) Post-checks (T+30m): smoke tests, latency/traffic checks, rollout verification.
6) Abort/rollback (if threshold crossed): restore VM/container snapshot and revert pin to pre-upgrade version.

Attachments: proposed-pin-rotation.csv (contains suggested canary candidate list and rollback owner column), snapshot-checklist.md (preflight checklist for snapshot integrity).

Thanks Alex/Mateo. A few engineering details to pin down (these will affect timing):

- KV cache & model warmup: when we rotate a pinned model we do a warmup that can add ~45–90s per replica depending on sequence length. For large canaries we should budget for cold-cache latency spikes during the 20% -> 50% step.
- Snapshot atomics: the runbook needs a two-phase commit for model-artifact + config blob. snapshot-checklist.md is a good start; I'll add a checksum validation step and automated restore verification (smoke endpoint returning model SHA).
- Compatibility ladder: we must confirm binary/weight compatibility for the target pin. If quantized kernels change, the rollout must stop until we confirm fallback kernels are present on all nodes.
- Automation hooks: I'm proposing we wire the release automation to 3 explicit abort signals: 1) error-rate > 3x baseline sustained for 5m; 2) 95th latency > baseline + 350ms for canary cohort; 3) failed smoke restore after snapshot. If any trigger fires we run the restore-job that reverts docker image + artifacts from the snapshot.

Proposed small-change schedule (customer cohort of <50 qps):
- Canary: 15 min warmup + 15 min observe
- 20%: 10 min ramp + 20 min observe
- 50%: 15 min ramp + 30 min observe
- 100%: 10 min ramp + 45 min observe (final rollback decision window)

I'm attaching (inline) the gating checks we use in our CI->CD pipeline in the internal runbook.
