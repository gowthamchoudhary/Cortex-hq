Hi Amelia — thanks for the clear questions. Short answer up front: we measure p50/p95 using fixed 5-minute buckets that are then rolled up into a 6-hour aggregate for SLA evaluation; short bursts are captured in the 5-minute buckets but the 6-hour aggregation prevents a single sub-minute spike from failing a daily commitment.

Attached is a small CSV with a worked example (ledger_slo_calc_example.csv) and a short addendum we propose to include in the contract (proposed_windowing_addendum_v1.pdf). Key points:

- Per-request latency is measured at the API gateway (end-to-end request completion).
- We compute p50 and p95 within each 5-minute non-overlapping bucket.
- For SLA evaluation we take weighted aggregation across buckets over a 6-hour rolling window by request volume (so buckets with more traffic influence the aggregate more).
- A breach is recorded only if the aggregate p95 for the 6-hour window exceeds the committed p95 threshold.
- For multi-region customers we compute per-region p50/p95 and require the committed thresholds to be met in the primary region(s) listed in the contract. Cross-region failover events are treated as separate incident classifications.

Why 5-minute buckets + 6-hour rollup? It balances sensitivity and stability: 5-minute buckets preserve short-lived performance characteristics (so we can analyze spikes), and the 6-hour aggregate avoids penalizing customers for transient platform-wide noise or rare infra maintenance spikes while still catching sustained degradation.

A couple of edge cases we call out in the addendum:

- Cache/Cold-starts: When a model variant is newly deployed and cold-starts are expected, we exclude the first 10 minutes of traffic for that rollout from SLA calc for that route if a canary rollout policy is used (this is a standard carve-out and is triggered only when both parties use the rollout API flag).
- Model switch/forced fallback: If a request is routed to a lower-capacity model variant because of capacity constraints, we label those requests and exclude them from the primary SLA bucket; they are accounted for in a secondary "fallback" metric and described in the addendum.

Adding the technical detail Amy requested. Quoting Tessa's summary above for context.

- Measurement: latency_ms for each request recorded at gateway and written to our metrics pipeline.
- Bucketing: non-overlapping 5-minute time slices [t0, t0+5m), compute the empirical distribution across all requests in that bucket. p50_bucket = 50th percentile of that bucket; p95_bucket = 95th percentile.

- Aggregation across buckets to form the 6-hour window: for each percentile (p50 or p95) we compute a request-weighted percentile across buckets as follows:
  * Let bucket_i have N_i requests and have percentile value P_i.
  * The aggregated percentile P_agg is computed by expanding each bucket's percentile into N_i pseudo-samples at value P_i and computing the target percentile across the combined set. Practically we compute P_agg by sorting buckets by P_i, accumulating N_i, and interpolating to the 50th/95th percent rank across sum(N_i).

- Normalization: empty buckets (N_i = 0) are ignored in aggregation; buckets with extremely low traffic (<5 requests) are included but flagged in the daily report so we can review sensitivity.

- Burst handling: a single 5-minute bucket that is a spike will influence the 6-hour aggregate proportional to its traffic. This means an extremely short but heavy burst can move the aggregated percentile; however a minute-scale spike with small absolute request count is unlikely to push the aggregate over the threshold because of weighting.

- Why not sliding 1-hour? We considered sliding 1-hour windows but found they are too reactive to transient network blips and increase noise for customers with spiky workloads. The 6-hour window aligns with our outage detection and remediation cadence and gives predictable billing/credit calculations.

If LedgerWorks requires a stricter rule (e.g., daily hard SLO without 6-hour aggregation) we can discuss a contract-style exception and remediation credits; that would typically require a higher price tier or a reserved capacity commitment.
