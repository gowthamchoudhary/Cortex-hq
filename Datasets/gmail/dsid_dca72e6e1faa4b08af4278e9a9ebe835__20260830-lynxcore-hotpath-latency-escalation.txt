Quick findings from a 30-min sampling window (live profiler + trace tail):
- Packet: v3.2-quant introduced a tighter per-layer tile that increases attention kernel invocations by ~18% for sequences > 160 tokens.
- KV cache: LynxCore's traffic shows very high prefix reuse, but the quant change increased cache fragmentation leading to more cache misses and additional memory allocations during decode.
- Errors: the 5xx spike aligns with increased retry loops when decode latency exceeds the request timeout; several reported 502s trace back to transient OOM on a subset of nodes (we're seeing realloc failures ~1-2s before 502).

Immediate remediation options:
A) Roll back to v3.1 for LynxCore (fastest).
B) Patch v3.2-quant with a different tiling parameter and redeploy to canary ring (slower, but preserves quant benefits).
C) Apply aggressive request-level backpressure and increase per-tenant memory limit (short-term mitigation but costly).

I recommend option A for tonight and then run A/B tests with a patched v3.2-quant in a canary ring for 24 hours. I can prepare the rollback package; need confirmation from Soojin/exec and LynxCore for a controlled window.
