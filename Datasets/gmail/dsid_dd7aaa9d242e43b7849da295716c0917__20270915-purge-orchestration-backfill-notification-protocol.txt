Maria / Julio,

Thanks — appreciate the clear asks. High-level answers below, and I attached a one-page runbook diagram (purge-backfill-notification-diagram.png). We'll follow up with a short operational playbook.

1) Backfill windows: any backfill that touches customer-scoped objects will generate a \"Backfill Start\" event. Customers receive an email + Console banner if the backfill is expected to surface previously deleted objects. We also create an immutable audit marker. If the backfill would reintroduce data that had a pending purge request within the last 90 days, the system auto-triggers a manual hold flag and notifies both Redwood support and the customer's admins.

2) Purge latency/escrow: our normal target for irreversible purge is 30 days after request acknowledgement. Exceptions: (a) legal hold or active investigation, (b) cross-border escrow transfer in process, (c) subprocessor migration in-flight. Exception triggers are recorded and require approval from the data retention owner + Legal. Escalation path: Redwood support -> Retention Ops -> Legal. We will provide an SLA clause and a list of valid exception categories for the DPA.

3) Logs & traces: default application request/response logs are retained for 90 days; ephemeral tracing (per-token inference traces) is 30 days by default. Log-exemptions (e.g., extended retention for audit) are applied per-account and recorded in our audit log; they require a signed SoA.

Kim / Diego / Maria,

Technical confirmation and an ops note below. TL;DR: we can support the requirements, but need to make a few implementation choices and document tradeoffs.

Implementation details:
- Auto-hold: we will implement a detection rule that triggers a manual-hold flag when a backfill touches objects with purge requests within last 90 days. The rule evaluates the backfill manifest during the staging phase.
- Visibility: the hold will surface in the Console (Retention -> Holds) and via a new API endpoint /v1/holds which returns hold_id, initiator, reason, and expiry (nullable). We will include a webhook for customer endpoints to receive hold events.
- Purge status updates: our job scheduler publishes status to the customer's mailbox and to the Console job log. We can add a weekly progress webhook and CloudEvent for purge_job.status that reports percent_complete and blockers.

Ops tradeoffs / exceptions:
- Cross-border escrow transfers: when data is copied to an escrow for legal/regulatory reasons, purge may be delayed until transfer completes. We can limit this to explicit, pre-authorized escrow actions to avoid open-ended exceptions.
- Forensic hold during investigations: holds may be open-ended but must be reviewed monthly. We can require evidence and an owner.
