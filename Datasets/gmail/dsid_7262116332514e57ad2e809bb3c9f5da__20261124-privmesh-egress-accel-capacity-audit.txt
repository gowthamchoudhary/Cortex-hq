Folks — I filled the worksheet with an initial pass and uploaded a topology sketch (privmesh-topology-v1.vsdx). Summary below (numbers conservative + include 15% headroom):

1) Steady-state sizing (target: 12k tokens/sec sustained)
- Model footprint: gen model ~ 40 tokens/sec per A100-equivalent for typical 512-step runs (after quantization) — we model 30 tokens/sec to be conservative.
- Effective tokens/sec per node (with multiplexing and 60% KV hit): ~1500 tokens/sec per node.
- Nodes required: ceil(12000 / 1500) = 8 nodes (matches ask).

2) Burst handling (90s window up to 36k tokens/sec)
- Warm pool: maintain 2 spare nodes (hot standby) + ability to spin-lane 3 additional nodes from cold in ~45s with pre-warmed KV snapshots.
- Admission: soft-fail starts at 18k tokens/sec (50% of burst cap) with degraded-mode rank-only responses for non-critical paths.

3) Networking / egress acceleration
- Preferred: 2x 100GbE cross-connect (LACP) between Redwood edge and Arbor colo fabric with MTU 9000 and RoCE v2 support. This supports worst-case synchronous KV replication and offload.
- Fallback: single 40GbE to Equinox with enforced bandwidth caps and QoS.
- Egress shaping: per-tenant DSCP mapping + token-bucket at opposite side (we included sample qos-and-egress-profiles.yaml).

- p50 token latency: <12ms local generation; p99 <65ms under steady; target p99 <150ms under burst (with admission).

Thanks — quick technical notes / clarifications before we hand this back to Arbor: 

- RoCE/MTU: Agree with MTU 9000 and RoCE v2 if the colo supports it. We'll need to validate PFC behavior on Arbor's switches; misconfigured PFC + RoCE will cause microbursts to drop packets and blow up p99. If Arbor cannot guarantee lossless Ethernet for RoCE, recommend TCP + NIC TSO/GSO offload and additional cross-connect bandwidth.

- KV cache propagation: pre-warmed KV snapshot approach works, but ensure snapshots are sharded and stored on NVMe local to the node to avoid cross-node egress during warmup. If snapshot restore is >20s we need to increase hot-standby count.

- Admission curve math (sketch):
  * steady_accept_qps = floor(steady_tokens_per_sec / avg_tokens_per_request)
  * with 30 tokens/request average -> steady_accept_qps = floor(12000 / 30) = 400 qps
  * burst_peak_qps = 1200 qps (36k tokens / 30 tokens)
  * warm-pool sizing: hot_spares = min(3, ceil((burst_peak_qps - steady_accept_qps) / node_qps))
    where node_qps = floor(1500 / 30) = 50 qps per node -> hot_spares = ceil((1200 - 400)/50)=16 (this is conservative and shows we must rely on admission controls + faster cold-start paths).

  That last calc shows a tension: if average tokens/request is 30, nodes provide only ~50 qps each; to hit 1200 qps we'd need many hot nodes. So we should either: 1) increase multiplexing (raise node_qps), 2) reduce avg tokens/request (prompt engineering / truncation), or 3) rely on short-term egress to Equinox for overflow.

- Networking ops: please request Arbor provide RBAC'd console access for NIC counters and a test VLAN for MTU/RoCE validation. Also request the physical cross-connect cadence (when can they install 100GbE).

I'll add more precise simulations later today into the worksheet (arbor-capacity-audit-worksheet.xlsx).
