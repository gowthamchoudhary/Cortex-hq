Lena — thanks for the clear checklist. I answered inline and added an executive summary below; full detail is attached as a PDF (redwood_neha_answers_20260113.pdf). Please let me know if you'd rather we fill the sheet directly.

Executive summary (short answers):
1) Where data resides: Primary customer request and generated response data for Redwood Hosted API are stored transiently in the serving region you select at account creation (AWS regions for US customers by default: us-west-2 or us-east-1). Persistent artifacts (indexable logs, embeddings, analytics) are stored in the same region by default unless a region pin is requested. We can also support EU-region pinning for EU customers.

2) Retention defaults:
- Request/response logs (for troubleshooting and billing): default 30 days.
- Embeddings (if customer requests embedding service): default 90 days; customers can opt for shorter TTLs or request immediate deletion.
- Model KV/prefix caches: ephemeral; retained only for active session TTL (default 1 hour) and evicted automatically; not persisted to long-term storage.

3) Deletion request flow and timelines:
- Customer submits a deletion request via API (DELETE /v1/tenant/data) or support ticket.
- We create an immutable deletion job id and enqueue a multi-step workflow: a) remove pointers from active serving layer (within minutes); b) purge object storage slices and logs (within 24–72 hours depending on replication); c) purge analytics indices and embeddings (up to 7 days to honor batch jobs); d) remove backups and snapshots in accordance with backup lifecycle — see backups section below.
- Typical end-to-end confirmation window: 7–30 days depending on dataset size and backup retention policy. We will provide the deletion job id and a per-stage timestamped audit trail when the job completes.

4) Backups & caches:
- Backups: periodic snapshots exist for disaster recovery. Backup retention default is 14 days. When we process a deletion job, we create a background process to scrub data from active backups; if immediate removal from all backups is required, we offer an escalated workflow (enterprise add-on) to accelerate scrub and provide attestation.
- Caches: the KV cache used for inference is in-memory on serving nodes and is not written to durable storage; eviction occurs by TTL and LRU policies.

5) Evidence and audit logs:
- For each deletion request we provide: deletion_job_id, timestamps for each stage, S3/object keys removed, and a signed attestation (PDF) upon completion. Audit logs are retained for 180 days by default and are available via the Console and an API endpoint.

6) Exceptions:
- Legal holds or regulatory obligations requested by customer/legal process may require temporary retention; we will surface exceptions as part of the deletion job and provide the legal basis.
- For disaster recovery windows (short backup windows) immediate physical removal may be deferred until scrub completes.

Operational notes & controls:
- Key management: customer data at rest is encrypted with AES-256; customer keys may be managed via our KMS integration (BYOK) for Dedicated/Private customers. For Hosted customers, we use our managed KMS but will support customer-managed keys upon contract.
- Data residency controls: region pinning at account level; routing policy ensures requests are served from pinned regions when configured.
- Programmatic verification: customers can call GET /v1/tenant/deletion-jobs/{id}/status to poll progress and download the attestation when available.
