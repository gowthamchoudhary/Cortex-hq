Hi all —

Thanks for the context. Below are the practical SDK snippets and the operational rules we recommend for HazelPay's cutover. I've kept this focused so your backend and infra folks can copy/paste during the sync.

1) Endpoint choice
- For short, chat-style prompts we recommend the /v1/chat endpoint to support streaming and lower tail latency. Use /v1/infer for bulk batched scoring jobs.

2) SDK init (pseudo-JS + python examples)
- JS (node) sample:
  const Redwood = require('@redwood/inference');
  const client = new Redwood.Client({
    apiKey: process.env.RW_API_KEY,
    baseURL: 'https://api.redwood.ai/v1/chat',
    timeoutMs: 15000 // 15s socket timeout
  });

- Python sample:
  from redwood import Client
  c = Client(api_key=os.environ.get('RW_API_KEY'), base_url='https://api.redwood.ai/v1/chat', timeout=15)

3) Retry / timeout guidance
- Client-side policy (recommended):
  - Max attempts: 4 (initial + 3 retries)
  - Retryable: network timeouts, 429, 502, 503, 504
  - Backoff: exponential jittered base=300ms, factor=2, max_backoff=10s
  - If body is idempotent (e.g., embeddings), retries safe; for non-idempotent streaming, prefer at-most-once but enable server-side continuation tokens when possible.

4) 429 and rate-limit handling
- Respect Retry-After header if present (seconds).
- If 429 without header, apply exponential backoff with a randomized cap (start 500ms).
- Surface remaining_quota and reset_window headers from the API in your dashboards. SDK exposes these as response.meta.headers.

5) Traffic shaping / cutover ramp plan (example)
- Day 0 (smoke): 5% of traffic, cap bursts to 50 req/s
- Day 1 (ramp): 25% of traffic, cap bursts to 150 req/s
- Day 2 (steady): 60% of traffic, monitor 95th pct latency and error rate
- Day 3 (go-live): 100% but keep soft limit for bursts for first 2h

6) Observability & tracing
- Inject X-Request-ID client header; Redwood will return x-rw-trace for server-side spans.
- For retries, SDK emits metrics: redwood.client.retry.count, redwood.client.retry.latency in Prometheus-friendly format.

7) Example rate-limiter placement
- We recommend a client-side token-bucket (per-worker) plus a lightweight edge throttle in front of your gateway. This prevents sudden fan-out to Redwood backend during cascading retries.

8) Failover pattern
- Configure a fallback model (smaller quantized) for degraded states, with a quality gate. Use canary traffic route to measure delta.
