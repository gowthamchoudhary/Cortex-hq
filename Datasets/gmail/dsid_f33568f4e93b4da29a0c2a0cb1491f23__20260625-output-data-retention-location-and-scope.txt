Hi Alice — forwarding the short, definitive answers below (pulled from our infra and product teams). I attached the one-page summary and a mapping spreadsheet to your checklist. Let me know if you need the files in a different format.

Definitive answers (hosted API default):
- Training use: Redwood does NOT use customer prompt text or model outputs to train or improve public models by default. Customer data is isolated from model training unless an explicit program is agreed in writing.
- Persistence: Short-term operational logs (request metadata, error traces) are retained for diagnostics. These do not contain full model weights but may include prompt text or output text if customers have not enabled redaction. Default hosted TTL for request logs is 30 days.
- Opt-out / deletion: For hosted customers, you can enable a no-retention flag at the account level which prevents storage of prompt/output text and persists only minimal request telemetry. For Dedicated and Private deployments, we can configure zero retention. Deletion requests are auditable and processed within 72 hours; we provide deletion receipts.
- Granularity: Retention controls are per-account and per-route. Admin APIs allow setting a retention policy per API key or route.
- Region residency: Hosted storage defaults to the region of the selected endpoint. We currently support region constraints (us-east-1, eu-west-1). For EU-only residency we can route logs and stored artifacts to eu-west-1. Private deployments give you full control over physical location.
- Audit logs/export: You can export request logs and audit trails in JSONL via the Console or admin API. We also support periodic S3 exports to a customer-owned bucket.

Hi Alice — quick technical clarifications from infra/ops:
- Storage layers: There are three distinct layers you should consider: 1) request metadata (headers, latency, token counts) stored in logging cluster, 2) request payloads (prompts) and outputs that are optionally stored for debugging, 3) model caches (KV cache) which are ephemeral and never written to long-term storage.
- Default behavior: only layer (1) and ephemeral traces are stored by default; layer (2) is only stored if the account hasn’t enabled the no-retention flag or if explicit logging is turned on for a route.
- Redaction: We provide an option to enable automatic PII redaction on ingest (PII detection + masking) before anything is written to logs. That redaction pipeline can be configured to remove identified PHI/PII fields or replace them with tokens.
- Deletion proof: When deletion is requested, we run a retention purge job and emit a signed certificate of deletion that includes timestamps and the affected object IDs. For Dedicated/Private, deletion is performed in-customer infra and we provide a runbook for verification.
- Backup policy: Backups of debug storage are also subject to retention rules; we do not create long-lived backups of prompt/output text unless explicitly enabled for a project.
