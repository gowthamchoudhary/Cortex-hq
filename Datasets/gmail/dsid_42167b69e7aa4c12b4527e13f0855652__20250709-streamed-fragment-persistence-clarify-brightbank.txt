Thanks for the clear list of asks. Below is a concise summary you can drop into your data flow doc; I also attached a simple matrix (retention_matrix_v1) for procurement. If you need formal legal wording we can have Kimberly draft final text.

Key points (hosted API default behavior):
- Streamed fragments / interim tokens: not persisted to durable storage by default. During an active streaming call we buffer fragments in RAM to assemble the stream; that buffer is ephemeral and flushed on session end. We only persist tokens if the session is explicitly saved or if a customer enablement flag requests full transcript capture.
- User prompts (raw requests): stored by default for short-term operational/debugging telemetry (default TTL: 30 days). This is primarily for abuse detection, rate-limit debugging, and transient analytics.
- Model drafts / intermediate completions: we treat intermediate drafts as non-durable unless the model emits them as a final response (e.g., a completed generation object). In other words, partial/compositional drafts during decoding are not written to long-lived logs by default.
- Final outputs (finalized responses): persisted by default for a longer troubleshooting/quality window (default TTL: 365 days) for hosted customers. If a customer opts into longer retention for analytics or index-building we record that in their contract and separate storage class is used.
- KV caches: runtime-only by default on hosted — in-memory and not durable. Dedicated/Private deployments can configure persistent cache lifetimes; if configured, we recommend a TTL <= 6 hours as a best practice.
- Region/residency: when customers select an EU region we store data in that region by default; TTL policy values are the same unless a regional regulation requires a shorter retention (we will follow customer-specified policies for regulated workloads).

Attachments: retention_matrix_v1 (pdf).

Appreciate the follow-ups; below is a short, procurement-friendly response you can paste into the SOW, plus pointers on evidence and recommended defaults. I attached our concise retention summary and the completed BrightBank questionnaire.

Procurement-friendly wording (suggested):
"Redwood's hosted API retains user request records (prompts) for a default period of 30 days and retains finalized model outputs for a default period of 365 days for the purposes of troubleshooting and quality monitoring. Transient streaming buffers and runtime KV caches are ephemeral: streaming buffers are in-memory and only exist for the duration of the live session (buffered for assembly, then discarded); KV caches on hosted plans are in-memory and non-durable. Customers may opt-in to extended retention or enable transcript capture; any retention exceptions are documented in the customer's contract and handled in the region selected at account onboarding."

Evidence and deletion proof:
- When records are deleted via the standard retention cycle or via a customer-initiated erasure request, we emit an auditable deletion event with a timestamp and internal deletion runbook ID. For enterprise customers (Dedicated/Private) we can provide a signed deletion certificate and runbook trace; for hosted customers we provide a timestamped audit log entry that shows the deletion event and the logical identifier removed.

Observability/debug snapshots for streaming errors:
- On rare error paths we capture a minimal debug snapshot which may include assembled chunks necessary to reproduce the failure. Those error snapshots are treated as temporary debugging artifacts and are retained for up to 7 days by default; they are strictly access-controlled and logged.

KV cache guidance for Dedicated/Private:
- Recommended default TTL: 6 hours (recommended to limit blast radius). If customer workloads require longer cache persistence for latency reasons we document and sign that configuration in the Dedicated deployment contract.
