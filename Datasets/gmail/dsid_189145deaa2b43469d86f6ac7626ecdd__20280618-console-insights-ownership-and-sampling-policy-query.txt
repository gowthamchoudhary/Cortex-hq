Kimberly —

Thanks for the summary and the attachments. Quick responses inline: 

Ownership & discovery
- My recommendation: Observability/product should own the console experience (tiles, UX, escalation playbook). Runtime/infra should own data collection, storage, and APIs that surface raw traces/metrics. We define clear SLAs on data freshness, and an ownership matrix for on-call routing.

Sampling & retention
- Proposed defaults (initial):
  * Default sampling: 0.5% full-trace for normal traffic.
  * Tail/error sampling: 5% for requests that exceed cost threshold or hit 5xxs.
  * For customers who opt-in to full-trace, enable 100% for a configurable window (default 1 hour), with a hard cap on retained bytes.

Tenant toggle considerations
- Blockers: storage costs (we need quota/billing enforcement), and KMS/PII review for retained payloads. From infra side, we can implement an opt-in flag that routes traces to a higher-retention bucket with a billing tag.

Action items I'm comfortable with for this sprint:
- Dylan / Infra: surface an API that returns per-route cost and sampled trace references (not raw payloads) by Thu.
- Product: finalise escalation owner list and provide UI copy for the tenant toggle.

Sidenote for Atlas: we should prepare the one-pager that explains how sampling affects billing and debugging — I'll draft a short note.

We can deliver the per-route summary API by Thu, but a few implementation notes / constraints: 
- Full-trace retain/route: we must enforce an upper bound on total bytes per-tenant/day. I'd propose a default 10GB/day cap for opt-in full-trace, with billing tags if they exceed.
- Sampling metadata: we'll include trace_id, route_id, timestamp, cost_estimate, and a pointer to the storage location (GCS path) rather than the raw payload. That lets product link the tile to the trace without moving large payloads through the console.
- For the 0.5% baseline, it's fine. We will need a rate-limiter to ensure tail spikes don't generate burst storage beyond quota — I'll add that to the PR.

Blocking items:
- Karthik: we need a sign-off on the KMS policy (are we allowed to keep snippets of prompt/response in a higher-retention bucket for debugging?)
