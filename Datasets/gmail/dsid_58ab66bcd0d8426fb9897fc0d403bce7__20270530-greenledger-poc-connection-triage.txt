Quick triage update after repro and logs:

What I reproduced:
- Ran Alex's repro-script under controlled load against our hosted runtime with identical model and sequence lengths. I can reproduce the connection reset when the stream pauses ~>30s between token flushes.

Root cause (short):
- Runtime batching heuristic will close an in-flight streaming connection if it observes no token emission for the batch_timeout window (default 30s) to free resources under heavy concurrency. For some workloads (long-thinking LLM steps) this can coincide with client-side keepalive timers being shorter, which looks like a sudden reset to the SDK.

Evidence (attached): triage-log-snippet-20270530.txt shows server log lines: "request_id=.. node=rpc-12 batch_timeout=30s dropping-stream" correlated with the client's broken pipe events.

Immediate mitigation (what to tell customer):
1) Client quick fix (best short-term): set SDK keepalive to 90s and enable streaming_heartbeat=true. This keeps the TCP session alive across longer model pauses. Example: client.setKeepalive(90000); client.enableOption('streaming_heartbeat');
2) Server-side short-term: we'll open a canary with batch_timeout bumped to 60s for GL-POC-42 if customer approves — low-risk config change for their sessions only.

Longer-term plan:
- Create RWD-8721 (internal) to make batching heuristics more workload-aware (emit lightweight heartbeats from runtime to avoid forced teardown).
- Add a note to the Streaming Keepalive runbook with default values for POC customers and an SDK example.
