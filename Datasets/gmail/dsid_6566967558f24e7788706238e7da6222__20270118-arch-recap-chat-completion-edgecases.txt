Hi Laura —

Great summary — thanks. Quick answers and clarifications from our side so you can tailor the integration guide:

1) Auth & provisioning
- We prefer short-lived client-credentials (OAuth 2.0) for services that originate from our backend. For internal tooling/smaller teams we still use API keys managed by HashiCorp Vault. mTLS: not required today, but possible in 2028 roadmap.

2) Routing policy
- Preference: policy-based routing. Default to Hosted for cost/elasticity but we need an option to pin sensitive customers to Dedicated. We have a compliance requirement to keep EU PII in EU-only regions — for Novus that applies only to a subset of customers.

3) Request/response semantics
- Chat: multi-role messages are required for system/user/assistant separation.
- Tooling: determinism in tool outputs is important for the automation flows we plan to build — if Redwood can enforce a strict JSON schema on the response that would be preferred; otherwise we will need robust post-parse validation in our app.

4) Streaming vs batched scoring
- For reranking: P95 under 120ms is ideal for our online use-case; offline batch rerank (nightly) is ok to be higher latency. Throughput: expect occasional spikes up to 300 qps during reindexing windows. Cost sensitivity: moderate — we care about unit costs when ranking at scale.

5) Tokenization/limits
- We currently standardize on tiktoken-like tokenization. Off-by-one on max_tokens has bitten us before; any explicit guidance and sample code for reliably computing remaining tokens would be helpful.

6) Embeddings/reranker
- We will likely normalize vectors and use dot-product for speed. Our recall-first retrieval uses a sparse-first stage (ES / FAISS) then dense rerank.

Thanks Elaine — great context. Some technical notes from the runtime/integration side that we should put into the SDK guide (high level):

A) Chat vs Completions (recommendation):
- Use Chat API for interactive, multi-turn experiences with explicit roles. Chat semantics preserve role metadata which helps model conditioning and safety filtering.
- Use Completions API for single-shot scoring or short-format generation where you control exact stop sequences and want minimal framing overhead.

B) Tokenization & max_tokens guidance:
- We'll include sample code using tiktoken-compatible tokenizers. Recommended pattern: compute token_budget = model_context_length - estimated_response_tokens - safety_margin (e.g., 32 tokens).
- Stop sequences can truncate output earlier but are not guaranteed under heavy sampling. When streaming, deltas may emit stop tokens across chunks; your reassembly should detect final "stop" sequences in the last chunk, not assume a token boundary map.

C) Streaming semantics & structured output:
- Streaming returns incremental deltas. For structured (JSON) outputs we recommend two approaches:
  1) Strict schema enforcement: ask model to emit only JSON with a top-level "response" object and include an explicit finalization token (e.g., "\u0003END_JSON\u0003"). Redwood can optionally validate on the server and return an error if invalid (for Hosted customers).
  2) Heuristic reassembly: assemble deltas client-side, run a tolerant JSON reparsing step (balanced-brace recovery), then run schema validation.
- For tool-calling, prefer the structured tool-calling primitives (if you need deterministic parseable output). We can show both examples in the SDK.

D) Caching & KV prefixing:
- Cache keys should include: model_id + model_version + tokenizer_version + user_prefix_hash (if using prefix caching). For rerank, cache by embedding-id and query-hash.

E) Embeddings & rerank:
- Normalized vectors + dot product is fine. We'll include a short code snippet for batch scoring using BLAS-optimized dot-product; also an option to pre-normalize and use cosine equivalently.

F) Routing & failover:
- Provide examples for policy-based routing with fallbacks. If Novus wants EU-only storage, we recommend a region-aware rule that pins specific account IDs to EU clusters.
