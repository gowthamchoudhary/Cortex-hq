Thanks — quick technical sanity notes on the assumptions in Aisha's sheet:

- Avg tokens/request: 750 is fine for budgeting but please track the 90th percentile separately (we often see spikes up to ~2.5x on long-form). If procurement wants a conservative reserve, model a 1.6x uplift on tokens for a resilient commit.
- Cache hit rate: 20% is reasonable for request-level prefix caching. If Cirrus can provide explicit user-level warmup (e.g., sending user history), cache hit can go to 35–40% which materially reduces tokens per generated response.
- Batching: target 8–12ms window yields good throughput without hurting p95 much, but that depends on request arrival patterns. For interactive flows we recommend adaptive batching with a strict latency cap (e.g., force-flush at 150ms). In the model I included a scenario for smaller batches (avg 4ms) to show cost/latency tradeoffs.
- Quantization: 8-bit gives ~1.6–2x speedups depending on kernel; cost modeling assumes equivalent performance delta of ~1.7x vs fp16 in GPU throughput. If Cirrus requires top-qual outputs, we should model more fp16 usage.

I attached a short sensitivity list in the sheet and added a note column with 'risk if not instrumented' items. Specific ask for Cirrus: can you confirm whether you will send full user history for warm-cache during the pilot? That will change the conservative tokens/$ number substantially.
