Alex — thanks for the quick clarifications. Based on your answers, here's a short technical proposal (high level) for the pilot and things we'll demo in the workshop.

Pilot goal (2 weeks): validate tool-calling UX for clinician flows (calendar + reranker) and prove we can meet the reranker latency SLO in staging.

Proposed integration pattern A — Proxy + Tool Definitions (recommended for pilot):
- Architecture: Redwood-hosted inference routes calls to a small Mosaic proxy (deployed in staging) using mTLS + short-lived scoped tokens. Proxy is responsible for:
  - translating tool-calls into your internal reranker API,
  - invoking calendar API in EMR, and
  - performing auth to your internal systems.
- Tool definitions: JSON schema-driven definitions stored in Redwood Console; gateway verifies return types and structured output before forwarding to client.
- Error handling: proxy returns normalized errors; Redwood will retry idempotent calls (configurable backoff); non-idempotent ops (calendar invites) use confirm/compensate pattern (two-step commit).
- Observability: each tool call will emit a trace id; audit log contains call metadata (tool id, requester, timestamp) and a content hash for payload immutability.

Proposed integration pattern B — Server-side handlers (production target):
- Handlers live in Mosaic infra as server-side functions subscribed to tool events.
- Redwood will deliver structured tool payloads to an authenticated webhook; handlers respond with success/failure and details.
- Supports parallel tool fan-out and complex compensating transactions; recommended for latency-sensitive heavy load after pilot.

Specific asks for engineering prep:
- Please provide a staging reranker endpoint (w/ example query) and sample response schema.
- Confirm if EMR calendar accepts iCal invites or needs a proprietary payload.
- List allowed IP ranges for the proxy to avoid VPN blockers.
