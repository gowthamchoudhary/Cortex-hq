Alex / Jordan — answers inline + next steps. See also attached SDK snippets.

1) Vector dims: if VendorX is 1024-d and you keep models producing 1024, Redwood supports that happily. Quantizing to 768 may reduce retrieval recall depending on your model & eval sets — typical drop is 1-3% in top-k NDCG for semantic search but can be mitigated by re-tuning the retriever or hybrid reranking. We recommend running a small A/B on 2k queries to measure delta before committing.

2) Normalization: Redwood's vector store supports both raw and L2-normalized vectors. For cosine similarity you can either: (a) store raw vectors and enable query-time normalization (what you do today), or (b) pre-normalize at ingest and use dot-product — both are supported. Pre-normalizing slightly speeds queries and is simpler for cross-system parity. Recommend pre-normalizing if you can.

3) Batching: ingestion throughput depends on hardware. Rough guidance:
- n1-standard worker (cpu-bound): batch size 64-128 vectors per POST to keep memory steady.
- Dedicated GPU pool: batch size 512-2048 (depending on GPU memory + quantization).

Dev, Marissa — I left more granular perf knobs in the checklist: chunking, concurrent writes, and preferred retry semantics.

4) Migration approach: we strongly recommend dual-indexing + traffic split for live validation. Redwood Console supports canary splits at route-level and automatic fallback. Workflow:
- Create a staged index on Redwood and replicate a subset (10-20%) of writes.
- Run A/B queries between VendorX and Redwood using the same query set and collect recall/latency.
- If metrics align, ramp writes and traffic over a week.

Attachments include: sample curl + auth headers, SDK snippet for Node/Python, and a spreadsheet template for A/B metrics.
