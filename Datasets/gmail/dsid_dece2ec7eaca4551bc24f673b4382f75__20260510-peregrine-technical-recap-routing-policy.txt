Hi Anna / Jordan — digging into the technical plan and calling out concrete suggestions so your engs have a starting point. Longish email but I wanted to be explicit about tradeoffs.

1) SDK + auth
- Languages: we’ll provide quickstarts for Python (Requests + official SDK) and Node (fetch + SDK).
- Auth: short-lived API keys via our token service + KMS-backed signing recommended for private deployments. For Dedicated/VPC we support customer-managed KMS (bring-your-own) so you can rotate without touching app code.
- Token rotation: recommend 1h TTL for service tokens; client tokens can be 15m if you run in-browser components.

2) Routing and policy (core ask)
- Primary route (interactive rerank): model: rw-redwood-13b-v2 (fp16) in us-east. Policy: latency-primary — route to lowest-latency zone; p99 SLO 180ms.
- Fallback chain: if primary unavailable or p99 approaching SLO, fall back to rw-redwood-7b-q4a (quantized) for degraded but acceptable output.
- Cost-based tiering: background/batch re-ranks should be routed to cheaper compute (7b quant) or queued for batch windows (off-peak).
- Region failover: config policy to prefer us-east, fallback us-west, then eu-central (only if data residency allows).

3) Embeddings + reranker pattern
- Store embeddings in your vector DB (we have connectors for Milvus, Pinecone, and self-hosted PostgreSQL + pgvector).
- Scoring: candidate retrieval via ANN -> cross-encoder reranker call at request time for top-K (K=20 suggested). Cross-encoder uses rw-redwood-7b-xattn for cost-sensible quality; for highest-quality can switch to 13b-v2 on canary.
- KV/prefix cache: enable prefix KV caching for repeated context to reduce tokenization cost on short prompts.

4) Structured tool calling
- Use our function-calling schema to allow safe invocations of your connector layer. We can provide schema templates and sample request/response validators.
