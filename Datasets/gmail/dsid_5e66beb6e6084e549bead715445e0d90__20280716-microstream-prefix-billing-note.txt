Vanessa,

Notes from quick triage (math-first):
- Current billing unit: we charge per-call with a minimum quantum of 1 unit for short calls under streaming. Each unit maps to our configured "microcall quantum" (in ACME's profile it's 1 unit = 250 token-equivalent).
- Rounding: for streaming, we round up to the nearest microcall quantum per call (no cross-call aggregation unless the KV cache registers a reuse event within an amortization window).
- Prefix amortization: we maintain a prefix KV amortization window of 90s by default for hosted customers; Dedicated customers can set sticky routing to keep KV warm longer. Amortization only applies when the runtime can match the prefix hash to an existing warm KV cache on the serving host. If requests hit different hosts (round-robin or scale-out), amortization won't occur.

Applying to Margaret's numbers:
- Example call: 150 tokens -> 0.6 of a 250-token unit -> rounded up to 1 unit -> billed as 1.
- If same prefix is reused on the same host within 90s and the KV cache matches, we only bill incremental tokens beyond cached prefix; typical amortized charge could be ~0.1 unit (rounded to billing rules) depending on their configuration.

As quick fixes:
- We can enable stronger host affinity for ACME's Dedicated pool (reduces cross-host cold starts).
- For the pilot, recommend a temporary waiver/credit for June to offset the unexpected rounding while we apply the sticky routing.

I'm attaching a small CSV that shows modeled invoice lines with and without amortization — this should help procurement. If sticky routing is acceptable we'll also provide a short runbook for implementation and expected savings.
