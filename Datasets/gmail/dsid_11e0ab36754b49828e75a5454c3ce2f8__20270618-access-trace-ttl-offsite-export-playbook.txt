Tom —

Thanks for the clear list. High level answers up front:

- Export mode: Redwood supports both \"push\" (we can deliver encrypted bundles to a customer-owned S3 via an IAM role and server-side encryption) and \"pull\" (you can initiate an export job and we place files in a short-lived staging bucket for transfer). For regulated customers we recommend push using a customer role so you maintain bucket ownership.
- Formats: ndjson (line-delimited JSON) and Parquet are both supported; Parquet is recommended for large-volume analytics.
- TTL / retention: Access traces and audit logs are configurable independently. We currently expose retention windows in the console and via API (30/90/180/365 days) and support a custom TTL up to 7 years via enterprise policy.
- Proof of deletion: Each export job is logged and we can include a signed SHA256 manifest for every export. For retained logs, we provide a deletion certificate (timestamped, signed internal audit token) that you can store as proof.

I attached a short playbook and an S3 presigned template to get you started. Michael has a couple of operational notes below.

Tom — quick operational pointers from infra: 

1) Export cadence: we support ad-hoc, hourly, and daily exports. Hourly is preferred if you need near-real-time ingestion into your analytics; daily reduces object count/cost.
2) File partitioning: exports include partition keys (year/month/day/hour) for parquet; ndjson uses rolling files (<200MB recommended).
3) Encryption: exports are encrypted in transit (TLS) and at rest using your KMS CMK when using push delivery.
4) Integrity: every export includes a SHA256 manifest. We can optionally sign manifests with our key; if you need a third-party attestation we can timestamp manifests with an audit log event id.
4) Deletion evidence: when TTL expires, we mark objects for deletion, run a bucket lifecycle, and emit an export-deletion record (signed). We can also provide a one-off evidence ZIP containing manifests + deletion receipts.
