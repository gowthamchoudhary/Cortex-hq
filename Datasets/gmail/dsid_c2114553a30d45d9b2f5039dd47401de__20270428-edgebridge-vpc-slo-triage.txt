Priya — thanks for the diagram and the profile. A few technical notes from infra/serving that will shape the test plan: 

Network / Transport:
- Given MTU 1420 over overlays, please allow MSS adjustment or ensure DF bit handling; fragmentation will add latency for larger requests.
- Outbound ports: our runtime initiates TLS 443 to our egress IPs. Please ensure outbound 443 is allowed; we also recommend ICMP for probe tests (temporary).
- Keepalives: enable TCP keepalive on the bastion side with an idle of ~30s to prevent mid-test connection drops.
- BBR or congestion-aware pacing on your egress is preferred to reduce burst-induced queuing.

Redwood serving suggestions:
- We'll pre-warm model KV cache for the scheduled window and apply continuous batching tuned to your median token size (we expect batching to help p50 without hurting p95 if we keep target batch latency low).
- Fallbacks: we can configure a lower-cost, smaller-context model variant as an automatic spillover for sustained overloads (drops throughput but keeps streaming alive). We can also enable partial-response streaming to start token flow earlier.

Test plan highlights (will send as perf-test-plan.md):
1) Baseline traceroute & p95/p99 RTT probes from bastion to Redwood egress (5-minute continuous probes)
2) Gradual ramp: 0 -> 100 concurrent streams -> 200 over 20 minutes with realistic token distribution
3) Spike test: 300 concurrent short streams for 3 minutes to validate tail behavior and backpressure
4) Failover: disable peering for 5 minutes to validate public internet fallback and measure delta

Questions for you:
- Can you provide an SSH bastion user we can use for controlled probe runs?
- Do you prefer we use mutual TLS or standard TLS for the perf window? Mutual TLS is better for authentication but adds small handshake overhead.

I'll attach the draft perf-test-plan.md in a follow-up and sync with Priyom on the exact metrics we will capture (packet loss, jitter, per-hop latency, per-request token latency).
