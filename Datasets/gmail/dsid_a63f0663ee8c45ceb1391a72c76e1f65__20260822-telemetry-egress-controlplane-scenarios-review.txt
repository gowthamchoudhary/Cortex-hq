Marcus — thanks for the clear summary. Looping in our infra and security leads to give concrete patterns: Irene (control/telemetry), Karthik (egress/NATs), Aditya (runtime constraints) and Stephanie (customer-facing runbook).

High-level answers up front: 
1) Control plane: outbound-only connectivity is supported. We can operate with a customer-managed egress proxy (HTTP(s) proxy or TLS-forwarder) so long as TLS termination is end-to-end and we negotiate an allowlist for destination IPs/DNS and certificate pin, or alternatively use a private peering / PrivateLink-like tunnel if the customer prefers no Internet egress.
2) Data plane telemetry: three supported modes:
   - Local forwarder: customer runs a small edge collector (Fluentd/Vector) that receives local metrics/traces and forwards to their telemetry backend.
   - Redwood forwarder: run a Redwood-managed forwarder inside the customer's VPC (customer-managed host, our process) that batches and forwards to customer endpoint or to Redwood relay (for customers that want unified ingestion).
   - Push direct: inference nodes can push directly to customer SaaS endpoints when network policy allows, but we strongly recommend buffering & retries.
3) Intermittent connectivity: use a local collector with disk-based buffering + backpressure; Redwood's agent supports configurable batch windows and disk caps.

Sergio / Marcus — quick technical note from security/telemetry side.

On the control plane: we treat control-plane telemetry (health checks, control metrics) as lower volume but higher sensitivity. Recommended approach: 
- mTLS from control-plane components to a Redwood control-plane collector endpoint.
- If customer disallows direct egress, we can terminate at a customer-operated TLS relay that forwards over an internal peer link to Redwood.

On the data plane (inference nodes):
- Prefer the local-forwarder model. Deployment: Vector running as a sidecar or node agent; it writes to local disk (capped) and forwards to the collector. Buffer settings: 50MB disk cap default, batch window 10s, retry backoff up to 30m.
- Auth: If ACME wants their telemetry to go to a SaaS backend (Datadog/Splunk), we recommend customer-provided API keys embedded into the collector (customer-managed secret), or mTLS when supported. Avoid embedding keys in the inference process.

Network considerations: 
- Egress via NAT Gateway is ok; but if ACME wants highly restricted egress, configure a dedicated egress subnet + proxy with explicit allowlist.
- For sites with strict NAT, use the forwarder-in-VPC approach so that one host manages retries and reduces ephemeral port churn from thousands of nodes.

Also: privacy note — make sure ACME is aware of what telemetry includes. We can redact request payloads at the agent level if needed; this requires a short feature flag during onboarding.

Folks — following up with concrete network artifacts. Attached is a CSV with suggested egress IP ranges for the Redwood forwarder and an example ACL template for ACME's perimeter router. Key points: 

- If using a single NAT egress per site: recommend reserving a small, static range (e.g., /29) for forwarder & control-plane outbound to simplify allowlisting on customer firewalls.
- Example iptables snippet (high-level):
    iptables -t nat -A POSTROUTING -s 10.10.0.0/16 -o eth0 -j SNAT --to-source <NAT_PUBLIC_IP>
  (We typically suggest controlling SNAT at the VPC egress to avoid node-level churn.)
- For high-security sites: run the Redwood forwarder in an isolated egress subnet with a dedicated outbound proxy (Squid/TLS-forwarder). Forwarder talks to local proxy over mTLS; proxy terminates to external endpoints.
