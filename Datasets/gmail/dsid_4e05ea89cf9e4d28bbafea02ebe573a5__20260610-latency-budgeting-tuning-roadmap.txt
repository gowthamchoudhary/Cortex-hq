Danielle — great, thanks for the profile and SLO. Based on the numbers you shared, here’s a more concrete plan and the acceptance criteria we’ll use during the sprint: 

Sprint plan (2 weeks):
- Week 1: Baseline + switches
  - Baseline run against your sample set using q4_0. Measure p95, p99, and cost/tokens.
  - Enable KV prefix caching for exact-repeat and high-similarity queries. Initial TTL 5m; we’ll test 1m/10m in experiments.
  - Start continuous-batching experiments with target windows: 8ms, 16ms, 32ms. We’ll measure latency tail and token cost.
- Week 2: Quant + routing + productionization
  - Test int8-q4_0 and int8-q3_1; measure answer drift on a small eval set (we’ll use your redacted evals) and pick a production profile.
  - Implement routing policy: route interactive reads to the high-perf variant; if average queue depth exceeds threshold or p95 breaks, failover to cost-optimized variant.
  - Run a 2-hour soak at synthetic 80 qps to validate autoscaling and cache behavior.

Acceptance criteria (sign-off):
- P95 <= 160ms on baseline eval (we will target 150ms but allow a 10% buffer during tuning).
- Cost per 1k tokens within 15% of baseline after quantization and batching adjustments.
- No functional regressions on the eval set (we’ll surface any >3% semantic change for review).

Action items for AtlasAI before kickoff:
1) Provide a shared synthetic workload script (or confirm we can replay from the sample file).
2) Confirm whether you prefer a 5m or 10m caching TTL for high-hit routes (we recommend 5m to start).
3) Approve the two kickoff windows (we’ll send a calendar invite on confirmation).

I’ve also created a short shared runbook in Drive here: https://drive.google.com/open?id=1Xq_example_runbook — it includes the test checklist and our measurement spreadsheet.
