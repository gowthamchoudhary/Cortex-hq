Thanks again for the call this morning — great to sync on VertexHealth's streaming use case and the production constraints. Quick recap and next steps so we have a single source of truth.

Call highlights:
- Workload: live patient summarization pipeline, steady-state ~120 reqs/min, peaks to ~600 reqs/min during morning batch windows.
- Latency needs: target 200ms median for interactive UI, but streaming tail behavior matters for progressive render and perceived UX.
- Concurrency: plan to start at 64 concurrent streams; expect to scale to ~256 next quarter.
- Failure tolerance: application can handle short degradations if there is deterministic fallback; procurement requires clear remedies for sustained SLO breaches.

Proposed measurement approach (attachment: redwood-proposed-streaming-sla-v1.pdf):
- Measure at ingress edge (post request de-dup and auth) to capture real-user latency.
- Primary metric: p95 end-to-end time per request for the full response (non-streaming equivalent).
- Streaming metric: 98th-percentile per-chunk latency and time-to-first-byte (TTFB) for streams; also track time-to-last-byte for full completion.
- Exclusions: total outage windows from upstream provider (max documented 15m/day), customer-initiated rate-limit bursts beyond agreed concurrency, and maintenance windows with 72h notice.
- Reporting cadence: daily automated SLO report; formal monthly SLI digest and quarterly SLA review.
- Remedies: service credits tiered by duration and severity; immediate automatic fallback to CPU-backed replica when GPU pool is unavailable.

Sara — thanks for the quick questions. Short answers and an updated plan below. I've attached a one-page diff of the SLA proposal (redwood-proposed-streaming-sla-v1.pdf) with the measurement sections highlighted.

1) Streaming primary SLI: Agreed to make TTFB-p98 the primary streaming metric. We will also publish TTFB-p95 and TTFB-p99 for visibility, plus time-to-last-byte (completion) p95 for the full response.

2) "Upstream provider" definition: we mean third-party infrastructure or network events outside Redwood's controlled fleet (e.g., cloud provider region-wide network disruption).
