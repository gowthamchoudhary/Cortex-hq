Hi Bianca — thanks for flagging this early. Putting an implementation-focused reply below and attaching a lightweight sample SDK bundle + the onboarding milestones sheet for the migration plan. (See attachments: sample-sdk.zip, onboarding-milestones.xlsx)

High-level recommendations (summary):
- Idempotency: Always surface an idempotency-key header for state-changing endpoints (Idempotency-Key: <uuid>). Server will persist key for 24–72h depending on operation class; we recommend client generate v4 UUID per user action.
- Retry semantics: Default client SDK has exponential backoff with jitter (base 250ms, multiplier 2.0, max 8s) and a total retry budget of 3 attempts for idempotent-safe calls. For non-idempotent (payments/settlements) the SDK disables automatic retries by default.
- Timeouts: Default socket timeout 10s; overall request deadline 30s for long-running ops. For latency-sensitive requests we recommend socket 5s and deadline 15s.
- Duplicate-safety: Server honors Idempotency-Key and will return 409 when a conflicting request is detected; client should surface a distinct user-facing message and avoid automatic re-submit.
- Headers to inspect: Retry-After (on 429), X-RateLimit-Remaining, X-RateLimit-Limit, X-RateLimit-Reset (epoch seconds). We also expose X-Request-Id for tracing.

Cutover migration pattern we suggest:
1) Dual-write validation: send to v2 with a header X-Shadow-Write: true so v2 validates but does not commit.
2) Shadow-reads: periodically compare v1 vs v2 responses for a sample set.
3) Canary rollout: enable v2 for 5% traffic with idempotency keys strongly enforced, monitor for divergences for 48–72 hours.
4) Remove shadow header and shift increasing percentages.

Sample snippets (high level):
Node (idempotent POST):
```
const id = uuidv4();
await client.post('/v2/charge', body, { headers: { 'Idempotency-Key': id }, retry: { attempts: 0 } });
```
Python (safe retry wrapper):
```
with client.request('POST', '/v2/charge', json=payload, headers={'Idempotency-Key': id}) as r:
  if r.status_code == 409:
    # surface duplicate error to UX
```

On rate limiting: prefer client-side rate fences (token bucket) tuned to X-RateLimit-Limit and fall back on 429 handler with Retry-After. For high-volume embedding/stream endpoints we recommend batching with our SDK batching helper to reduce token usage.

Great questions — quick answers: 
1) SDK config: yes — per-endpoint retry policy is supported. Each client method accepts a retry config object; default is conservative but you can override retry.attempts / retry.backoff / retry.enabled per-call. See sample-sdk.zip / docs/README.md.
2) X-Shadow-Write: v2 will respond 200 with header X-Shadow-Response: snapshot and we add X-Shadow-Committed: false. Shadow writes intentionally do not persist — you should see a 200 with the same validation errors as a commit path, but nothing is committed. We publish a /v2/shadow-report endpoint to pull diffs for the sampled set.
3) Sandbox tokens: shared link to a scoped sandbox token (read/write test-set) is in the Drive link above. If you prefer per-engineer tokens we can issue them — Monica can coordinate.
4) Backoff metadata: the SDK surfaces a Retry-Metadata object on 429 that includes next_retry_ms and retry_attempts. We also emit X-Request-Id and return X-RateLimit-Remaining in response headers for live rate fences.
