Sam — thanks for the clear constraints. Short answers up front: yes, and yes, plus a third hybrid option. Below I've sketched three supported patterns and attached a concise CSR + handoff checklist for your ops team.

Options (tradeoffs summarized):
1) Customer-edge termination (your preference):
   - You terminate TLS at your perimeter proxy/LB (recommended when org policy requires egress inspection).
   - Redwood's private endpoint remains inside the VPC and speaks mTLS or plain TLS to your edge (you control the leaf certs).
   - You provide either the cert/key pair (rare, we prefer not to hold private keys) or you terminate entirely and present a proxied connection to Redwood.
   - Pros: meets enterprise policy, gives you full cert lifecycle control. Cons: you must map SNI/FQDNs and maintain the edge proxies.

2) Customer-managed certs installed on Redwood private-facing load balancer:
   - You generate certs using your PKI (CSR->cert), deliver PEM and chain to us; we install on the private endpoint.
   - Requires secure upload channel and acceptance of transfer during the maintenance window.
   - Pros: canonical TLS between public edge and Redwood with standard termination. Cons: private key handing implies additional compliance review.

3) Redwood-managed ACME sidecar (recommended when you want minimal ops):
   - We run an ACME agent inside the private VPC (ACME DNS-01 via delegated subdomain OR HTTP-01 via short-lived nat).
   - Requires a DNS delegation or an agreed transient connectivity path for validation.
   - Pros: automatic renewal, no key transfer. Cons: needs DNS delegation or NAT; not suitable for fully air-gapped environments.

Actionables and checklist (attached: onprem-tls-csr-checklist.pdf):
- If you want option 2, use the included csr-template.pem.txt and generate a cert with these SANs: *.private.greenfield.internal, redwood-api.private.greenfield.internal.
- If option 1, confirm the SNI list and update your proxy so it forwards X-Forwarded-Proto and preserves client cert headers if you enable mTLS.
- If option 3, we need one of: delegated _acme-challenge.<subdomain> write access, or a short maintenance window with a temporary NAT rule to allow ACME HTTP validation.

Looping in some implementation details from infra:

Karthik here — key notes for Greenfield ops:
- If you're doing customer-edge termination (Option 1), ensure your proxy preserves the TLS Client Hello SNI for backend routing, or configure an explicit mapping table. Redwood's private runtime binds to the private FQDNs; we route by SNI when multiple tenants share a gateway.
- For Option 2 (you hand us cert + key): we ask that your team uses PKCS#8 private key format, and P-256 or RSA-2048/3072. Please avoid RSA-4096 for performance-sensitive endpoints.
- For Option 3 (ACME sidecar): recommend delegating a short-lived subdomain (e.g., redwood-validation.greenfield.internal). We'll only request TXT records for DNS-01 and rotate no more than once every 60 days unless requested.
- mTLS: if you enable client certs on the perimeter, Redwood can validate on the private endpoint. We'll need the CA chain you trust (PEM) and the expected subject DN pattern.

Operational hints:
- Attachments we typically need: CSR template (we provided), FQDN to SNI mapping, list of IPs allowed to initiate ACME validation (if HTTP-01).
- If your security/compliance team requires we never store private keys, Option 1 is the safest operational model.
