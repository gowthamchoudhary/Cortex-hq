Paul — thanks, this is the right framing. Short answer: Dedicated is a good fit. Below is a pragmatic plan we can workshop, plus an initial sizing sketch and headroom assumptions. I attached a lightweight workbook with the math.

High-level constraints and assumptions
- Primary model: redwood-instruct-13B-q4 (recommended for deterministic outputs and lower cost). If you want to run a 30B variant we'll need ~2-2.5x the fleet.
- Typical sequence mix: 60% requests @ 128 tokens, 30% @ 256, 10% @ 512.
- Latency target: p99 <= 180ms (aiming for 150ms baseline to allow for network jitter).

Initial throughput math (sustained) — conservative baseline
- Measured throughput for 13B-q4 (seq=256, batch=8) on an A100-80GB: ~420 tokens/sec per GPU.
- At your profile (weighted avg seq ~200), realistic sustained per A100: ~480 tps.
- To hit 1,500 tps sustained: 1,500 / 480 ≈ 3.2 GPUs -> round up to 4 GPUs for redundancy and even workload distribution.

Burst/buffer sizing (to hit 3,000 tps for short windows)
- Burst strategy: autoscale with cold buffer + reserved burst capacity. Two options:
  1) Short-burst slab: provision 2 additional GPUs hot (total 6) to hit ~2,880 tps (close) and rely on batching improvements for the rest.
  2) Larger slab + pre-warm: provision 4 additional GPUs (total 8) to cover 3,840 tps with headroom.  
- Recommendation: start with option 1 (4 dedicated GPUs + 2 hot burst GPUs) and monitor actual burst shapes; we can push an autoscaling policy to pre-warm when throughput approaches 70% of reserved capacity.

Headroom and SLO mapping
- Sustained headroom: target 25% headroom for traffic variance and KV cache cold starts. That means template fleet for 1,500 tps should be sized to 1,875 tps capacity.
- Failure tolerance: recommend 1 N+1 spare GPU in the pool for maintenance/failover.

Operational notes
- Prefix/KV caching will improve effective throughput for long-lived sessions; we can enable warm-cache policies for your ingestion windows.
- We will instrument p99 latency at token-level and route older requests to a cheaper model variant if sustained p99 climbs above 200ms (configurable fallback).

Adding a bit more detail from the infra side — rough engineering math and variant comparatives so we don't over-promise.

Engine assumptions (measured on our private fleet, median metrics)
- 13B-q4: 480 tps/GPU @ seq200, batch 8 on A100-80GB; p50 token latency ~9ms, p99 token latency ~22ms. End-to-end generation latency for 128-token response ≈ 140-160ms depending on network.
- 30B-q4: ~180-220 tps/GPU at same profile (2.2x delta vs 13B).
- H100 lifts throughput ~1.6x relative to A100 for our kernels; so a 13B-q4 on H100 ~770 tps/GPU (est).

Sizing scenarios (fast check)
- Cost-efficient baseline: 4 x A100 -> nominal sustained capacity ~1,920 tps (with 25% headroom), meets 1,500 sustained and p99 latency target if batching is tuned.
- Lower-latency optimized: 2 x H100 (hot) + 2 x A100 (reserved) -> active mix yields ~2,500 tps of low-latency capacity and can cover many bursts; still recommend a 6-GPU max for 3,000 tps bursts.
- Conservative burst-ready: 8 x A100 -> ~3,840 tps sustained (ample headroom).

Operational patterns to hit p99 <=180ms
- Keep batch target low (4-8) for interactive use; increase batch for background bulk runs.
- Pre-warm KV cache 60s before predicted bursts using pre-warm hooks from your ingestion pipeline.
- Add a policy to fall back to a slightly smaller context or less expensive model variant if p99 >200ms for >3 consecutive 1-minute windows.
