Hi Olivia — great to hear NebulaData wants to pilot. I've pulled together a short Q&A below and attached a redacted subprocessor inventory and an annotated dataflow diagram. Quick summary up top: for EU tenants we default routing to eu-west-1 (AWS) or europe-west1 (GCP) depending on customer preference; we also offer a Private deployment option for full on-prem/VPC control. Details follow.

Q1) Where might inference requests be processed?
- Primary processing regions for EU customers: eu-west-1 (AWS Ireland), europe-west1 (GCP Belgium).
- Optional edge/ingress hops: CDN/edge caching (Fastly/Cloudflare) may see TLS-terminated requests if configured; these are optional and can be disabled.
- For Hosted customers we may route to the nearest healthy regional pool; for Dedicated/Private customers compute is pinned.

Q2) Subprocessors that can touch request data (inference path or logs)
- Cloud compute: AWS (EC2, EBS), GCP (GCE, Persistent Disk) — depending on region.
- Networking/CDN: Fastly, Cloudflare (optional).
- Metrics/Errors: Sentry (redacted view), Prometheus remote storage (managed partner).
- Storage & backups: AWS S3 / GCS buckets (encrypted at rest).
- Security & key management: HashiCorp Vault (for rotation), KMS providers per-region.
(See attached subprocessor-inventory-20280412.csv — it includes role, region, and data access level.)

Q3) Retention & deletion for customer data
- Request bodies: default retention 30 days for hosted API logs; configurable down to 0 days for enterprise contracts.
- Token-level inference logs (non-pii metrics): retained 90 days by default.
- KV cache & model context: ephemeral in-memory caches; persisted snapshots only for Dedicated/Private if enabled and then deleted on deprovision.
- Deletion process: for Hosted we support a delete request via Console/API. Deletion triggers (a) mark for deletion, (b) background purge jobs that zero out keys and remove objects, (c) replaceable snapshots overwritten per lifecycle policy. We provide a deletion certificate on request within the enterprise package.

Q4) Cross-border transfer mechanisms
- For Hosted customers we rely on: (1) region selection + strict routing policies to keep data in-customer-region pools, and (2) SCCs (standard contractual clauses) for transfers when non-adequacy transfers occur.
- We maintain an SCC addendum and can surface it in the contract.
- For customers requiring no transfers, Redwood Private or Dedicated deployments allow you to keep all compute within your VPC or contractually limited geography.

A) Region pinning: For Hosted we implement a routing policy that prefers the customer's nominated region by default; in edge failure scenarios requests may temporarily be routed to an adjacent regional pool within the same continent (we do not cross-continent unless customer allows it). We log routing decisions with a region tag and can provide aggregated routing histograms for the pilot period.

B) KV cache lifecycle: The KV cache is a local GPU-attached cache; it is not durable by default. For Dedicated we allow periodic encrypted snapshotting for warm-starts; snapshots are stored in the customer's selected region and are deleted on deprovision.

C) Logs and de-identification: We can supply redacted examples of the log format. We apply configurable field-level redaction (PII hash/strip) before any logs leave the customer's region unless otherwise configured.
