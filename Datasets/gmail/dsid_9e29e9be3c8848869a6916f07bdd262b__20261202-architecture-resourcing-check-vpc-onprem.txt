Thanks Aditya — I skimmed the scope. High-level comments:

1) Air-gapped on-prem: biggest unknown is whether the customer expects us to provide an installer that works without any outbound connectivity. Our current Private package assumes access to our artifact registry for kernel/weights. If they require a fully offline installer, that triggers a build-and-ship effort (we should quantify in days).

2) KMS / HSM: customer-managed KMS is doable but we need to know vendor (AWS KMS vs. Thales/Entrust HSM). HSM integrations often need low-level drivers and key wrapping flow changes — can add 2–3 sprint-level tasks if not already supported.

3) Model size / memory: 70B models will likely require multi-GPU nodes and NVLink topology awareness. If Acme wants low-latency (<200ms) for 70B unquantized, that increases GPU count per unit significantly. Suggest we propose a quantized path as a mitigation.

I uploaded a short runbook draft for the pilot (onprem-runbook-draft.md) with checklist items (network, install, fallback routes).

Adding initial resource/ops estimates based on what's in the scope and a typical pilot profile. See attached stub (resource_estimate_v1.xlsx). High-level:

- Two multi-GPU nodes (8x A100 80GB each) for the 70B baseline (can drop to 4x if customer accepts 4-bit quantization with small perf loss).
- Storage: ~3TB NVMe per node for model shards + 1TB for logs/KV cache snapshots.
- Network: private VPC peering for VPC option (TLS tunnels), and an ops box for the air-gapped site to carry software artifacts (if offline install is required).
- Ops time: onboarding + pilot run support ~ 2.5 FTE-weeks (SRE + SE time combined) across the 6 week pilot. If we must develop an offline installer and HSM drivers, add another 3–4 FTE-weeks for the delivery sprint.

Unknowns that change estimates a lot: expected QPS, exact models (sparse vs dense), and whether Acme will accept quantization. Please ask Sales for QPS SLA target and model names.
