Hi Chris —

Appreciate the clear ask and the timeline. Short answers up front:

- Yes, we support SAML role assertions for operator elevation. We accept an asserted attribute named `roles` (comma-separated) or `groups` and map those to PrivCP RBAC roles (operator, admin, read-only). For strict audit trails we recommend pairing SAML assertions with SCIM-provisioned service principals for long-lived access.

- For SCIM, we support push-based delta syncs and polling. Our recommended default for high-sensitivity operator accounts is an event-driven push into Redwood (webhook -> SCIM delta import) with a target processing latency of <= 2 minutes for operator changes; for regular users 15–60 minutes is typical.

Chris / Tessa — quick follow-ups from a runtime/security perspective:

- SAML path: we map incoming `roles` -> PrivCP roles via a customer-specific role mapping table (editable in the Console). We support both `urn:oid:2.5.4.42` style attributes and common `groups`/`roles` attributes.

- Delegated operator accounts: recommend a hybrid approach: SAML for ephemeral elevation (web console sessions / admin UI) + SCIM-provisioned service principal for CI/CD or long-lived automation (service tokens). This gives auditability (SCIM user/service principal) while preserving SAML-based session assertions for humans.

- SCIM delta handling: our private-controlplane connector supports incremental sync with an event buffer. Default backoff is exponential with a 1s base and a 2 minute max window for operator change spikes. If you need guaranteed <5 min for operators we can request priority processing on your Dedicated tenant config.

- Encryption/keys: if you want short-lived provisioning tokens for automation we will use your KMS-integrated signing key and rotate per your policy; we will document the call paths.
