Quick findings from the first pass against the logs Hannah dropped into the ticket:
- Node-3 shows intermittent NVMe SMART warnings (reallocated sectors) during the 18:50-19:30 UTC window — correlated with IO wait spikes.
- KV cache miss rate for the hot prefix increased 4x after 19:00 UTC; TTL evictions concurrently rose (suggests cache thrash after a small set of requests became heavier).
- Batching patterns: several clients' average batch sizes jumped to 32 for a ~20-minute window, which created longer decode stalls and amplified device IO pressure.
- No OOMs detected in kubelet logs, but there are a handful of long GC pauses from the runtime on Node-3 (120–300ms).

Suggested immediate mitigations (low-risk):
- Set max_batch=8 for the affected model variant and enable per-route batch timeout (200ms) — this should reduce tail latency while we investigate.
- Temporarily move Node-3 out of the hot-shard rotation and drain it for deeper forensic (smartctl + vendor diagnostics).
- Flip on short-circuit CPU fallback for tokenization for requests that exceed 1s in queue.

I attached a quick timeline visualization showing IO spikes and p95 correlation. If hardware diagnostics confirm NVMe degradation, we should treat this as a hardware incident and consider a node replacement cadence.
