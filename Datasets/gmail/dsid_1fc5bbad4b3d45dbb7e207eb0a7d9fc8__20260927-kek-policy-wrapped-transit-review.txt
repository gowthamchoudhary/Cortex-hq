Jordan — thanks for the draft. Quick initial notes (high-level):

1) Operator access: we MUST require sessioned, auditable bastion access (TACACS/SSO) for any operator commands that can unwrap or import KEKs. Add MFA + stepped approval for manual unwrapping.

2) KMIP vs REST: prefer KMIP over vendor REST for HSM interactions if available — KMIP gives clearer key lifecycle primitives for our audit tooling. If SecureHSM only exposes PKCS#11, we need a thin KMIP translation layer.

3) Audit events: policy needs explicit events for wrap/unwrap, key-create, key-rotate, key-delete and include operator id + justification token. Include retention policy (minimum 7 years for BrightBridge per the questionnaire).

4) Escrow: if BrightBridge requires offsite escrow, add a procedure for split custody (multisig escrow) and an attestable ceremony. Legal needs to sign off on chain-of-custody steps.

Adding operational detail from the ops side — pasted notes: 

- Rotation cadence: automation for 90d rotation is fine, but for zero-downtime we need a staged rewrap: 
  * Stage A: new KEK created and wrapped by HSM (kept with a prefix).
  * Stage B: live keys rewrapped to new KEK asynchronously with traffic slicing (~5–10% at a time).
  * Stage C: full cutover once rewrap hit rate > 99.9% and no active sessions using old KEK.

- Fallback: If rewrap fails, we revert to old KEK using a signed manual unwrapping procedure — must require 2-person approval and operator justification token.

- Egress: the key-wrap proxy must be hosted in a dedicated private subnet with egress only to the HSM IPs and to SecureHSM’s KMIP ports. No public internet egress otherwise.

- Telemetry: add token-level traces for rewrap progress and ops-runbooks for failure modes (timeouts on KMIP, partial rewrap, missing audit attestations).

Hi Jordan / team — thanks for including SecureHSM. A few clarifications on our side: 

- We support PKCS#11 and a KMIP front-end; both can emit signed KMIP audit records (we call them attestations). The attestations include HSM-signed hashes of the KMIP command and timestamp — good for tamper-evidence.

- Our KMIP supports wrap/unwrap and key-derive with AES-KW and RSA-OAEP. For high-volume rewraps the recommended pattern is AES-KW with ephemeral session keys and a persistent KEK wrapped by an HSM asymmetric key.

- PKCS#11 module: provided as a signed binary; we recommend running it in an isolated container with PID namespaces and fallback kill-switch for emergency zeroize.

Attaching our KMIP integration guide and a short whitepaper on signed attestations. Let us know if you want a short tech call/demo.
