Per our conversation, I pulled together a tight recommended slate for the POC along with practical tradeoffs (cost / latency / quality) and next steps to validate in your environment. The short version: we think three model candidates cover the spectrum you need for ranking/chat and generation tasks — one small/fast, one mid-size optimized for cost, and one high-capacity for coverage.

Recommended shortlist (rationale in bullets):

1) Redwood-7B-Quant (recommended for baseline & burst latency)
   - Why: sub-100ms P95 on our 80-token bench on V100-equivalent dedicated nodes; lowest per-token cost with quantized execution paths.
   - Tradeoffs: slightly lower factuality on long-tail queries in our prompt set (~3.8% hallucination rate on Aurora prompt pack).
   - When to pick: lightweight ranking, A/B tests, and when latency is the primary SLO.

2) OpenLlama-13B-QLORA (recommended balanced option)
   - Why: Good middle ground — ~220ms P95, much better task accuracy on Aurora evaluation prompts (top-line QA accuracy +8% vs 7B).
   - Tradeoffs: higher memory & unit cost, but supports longer contexts without material latency spikes. Requires warm KV cache for best throughput.
   - When to pick: multi-turn chat with moderate latency sensitivity and when you need improved QA/precision.

3) Titan-70B-Sparse (recommended for high-quality coverage)
   - Why: Best end-to-end quality on our evals (highest ROUGE / QA metrics), robust on long context and fewer hallucinations.
   - Tradeoffs: per-token cost is ~6-8x above 7B; P95 latency is higher (~650ms) and more sensitive to sequence length.
   - When to pick: final-stage evaluation for critical flows where quality trumps cost and you can accept higher tail latency or use async flows.

Hi Olivia — quick answers to the technical bits and proposed runner flags.

1) KV cache / multi-turn on Redwood-7B-Quant:
   - Yes — our quantized runtime preserves KV cache semantics. The main caveat is cold-starts after truncation; we recommend a 2-request warmup (simple ping with the same system prompt) to populate the cache for stable latency.

2) Titan-70B async thresholds:
   - For first-paint <500ms, we suggest the following hybrid approach:
      * Use Redwood-7B-Quant for first-pass low-latency response.
      * Kick off Titan-70B asynchronously for a higher-quality replacement that patches the response via client-side refresh.
   - This keeps the UX snappy while surfacing higher-quality answers when available.

3) Pilot pricing / PO:
   - Laura has included a conservative matrix in the attached PDF. For a short pilot (30 days, up to 5M tokens) we can issue a trial pilot quote without a long-term commitment; procurement can convert to a reserved pilot later. Samir — if you share a standard PO template we will attach the quote.

Prompt config note (short answers):
- For 7B runs where outputs are 1-2 tokens, set temperature=0.0, top_p=0.95 and constrain max_new_tokens=6. Also include a short completion stop sequence to avoid trailing noise. We included these flags in the runner config on the shared Drive (scripts/run_7b_flags.sh).
