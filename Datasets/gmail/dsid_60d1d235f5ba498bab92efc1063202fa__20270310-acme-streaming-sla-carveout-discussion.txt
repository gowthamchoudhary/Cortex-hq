Hi Tamara — I’m Evelyn (runtime lead); quick technical notes and the practical engineering constraints so you can see what a carveout would imply.

Why TTFT varies:
- Prefix/KV cache warmup: for chat sessions that reuse context we can serve first tokens much faster once KV cache is hot; cold sessions (new prompt + long context) need model KV population which increases TTFT.
- Scheduling & batching: in a multi-tenant hosted pool we batch small requests to increase throughput and utilization which can add to first-token latency at p99.
- Kernel/runtime path: certain optimized kernels for 8-bit quantized weights give better throughput but can slightly increase per-token latency; we pick kernels per model variant.

What we can do (configurable):
- Prefix caching: we can pin common prefixes for your flows (reduces TTFT for subsequent requests).
- Model variant recommendation: use the low-latency variant (we shipped a 1.7B low-latency build) for interactive flows; switch to a higher-throughput quantized model for background batching.
- Dedicated mini-pool: if you commit to a small Dedicated pool (e.g., 2 GPUs reserved), we can guarantee sustained 1.8k tokens/sec for short bursts and TTFT ~200–300ms (95th) for your chosen variant.

Tradeoffs and runbook for fallback:
1) If sustained token/sec crosses agreed threshold for >20s, we automatically triage to a queued non-streaming path (same model family) with clear client-side event indicating degraded streaming.
2) We provide a header in responses indicating 'redwood-fallback: queued' and an estimated ETA.
3) Ops play: we’ll set up trace-level logging and a small set of dashboards (per-route token/sec, TTFT p95/p99, queued rate) for the pilot.

I attached a small sample of your anonymized usage we reviewed (acme_mvp_usage.csv) — that informed the 2 GPU Dedicated sizing above. If you’d like, I can run a 48-hour soak in our staging cluster with your traces to produce concrete percentiles.
