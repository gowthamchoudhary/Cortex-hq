Emma / Hannah —

Quick technical note on how Redwood will measure TTFT and streaming latency so we're aligned before the dedicated run:

Measurement specifics (short):
- TTFT (time-to-first-token): measured client-side from request timestamp (t0) to first token byte received (t1). We will also log server-side dispatch time and kernel entry for correlation.
- Streaming latency: per-token inter-arrival times are recorded; we will compute p50/p95/p99 for the time from t0 to token_n for n=first, 10th, last.
- Concurrency strategy: run steady-state sessions (8) for 10 minutes after warm-up, then bump to 16 for 10 minutes. Each session will play randomized dialogue sequences from your replay.
- Batching and KV-cache: Two runs — (A) streaming mode with KV cache enabled and small continuous-batch (target batch size 4), (B) non-streaming batched (larger micro-batches). This will highlight TTFT vs aggregate throughput tradeoffs.

Pass criteria we will use for the MAP:
- p95 TTFT <= 120ms at 8 concurrent sessions (no errors).
- p99 token latency <= 350ms under 8 concurrent sessions.
- CPU/GPU metrics within expected bounds (<85% sustained GPU utilization for the profile).

We will produce a short HTML report and a CSV with raw timestamps. If you have specific markers for session priority or a subset of “high-value” dialogues, send that as we can highlight the metrics for those sessions.
