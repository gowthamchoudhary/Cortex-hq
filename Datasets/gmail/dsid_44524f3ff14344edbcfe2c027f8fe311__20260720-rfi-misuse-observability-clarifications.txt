Hi Laura — thanks for the clear questions. Below is a concise, RFP-friendly technical reply that you may attach directly to your RFI. I've included concrete metrics, integration options, and operational notes. I also attached a JSON example of our alert schema (alert_schema_example.json).

1) Detection coverage (out-of-the-box detectors)
- Hate / harassment / extremist content detection (model + policy filters)
- Violent wrongdoing planning & stepwise malign instruction detection
- Fraud patterns (social engineering prompts, credential harvesting attempts)
- PII exfiltration heuristics (regex + model-assisted PII scoring)
- Account takeover / impersonation indicators (behavioral signals + prompt similarity)
- Malicious code generation (dangerous shell commands, crypto-mining scripts)

Each detector combines lightweight rule-based checks with model classifiers. Customers can enable/disable categories at the tenant level.

2) Detection-to-alert SLA
- High-severity (P0/P1) events: default target median detection latency = 2s (95th percentile <= 5s) from request completion to alert emission for hosted deployments in our us-west region.
- Medium-severity: median <= 15s; Low-severity batched hourly.
- Measurement: timestamps include request_complete_ts, detector_eval_ts, alert_emit_ts; we compute distribution metrics and expose them in the Console.

3) Alert noise & tuning
- Suppression: alert deduplication window (configurable, default 60s) and per-tenant noise filters (min-occurrence thresholds).
- Replay & tuning: we provide a replay API that can re-run historical traffic through tuned detector thresholds for validation.
- Adaptive thresholding: optional ML-based dynamic thresholds that reduce alert spikes during model rollouts.

4) Evidence & auditability
- Investigation artifacts included in alert bundle: raw prompt, final model response, model id & version, decoding params, per-token log-probs (configurable), request metadata (client_id, route), trace id, KV-cache snapshot reference, nearest-neighbor match IDs (if retrieval augmentation enabled).
- Retention: default 90 days for full bundles; configurable up to 3 years for enterprise Dedicated/Private deployments. PII redaction policies can be applied before storage.

5) Integrations & sandboxing
- Push targets: HTTP(S) webhook, Splunk HEC, Datadog Events, S3/MinIO drop, SQS/SNS, Azure Event Grid.
- Pull access: S3 export of alert bundles or direct API query (with pagination and time-range filters).
- Sandbox: we provide a webhook sandbox endpoint and a test harness for replaying sample alerts (token-limited).

6) False positives & remediation playbook
- We ship a baseline triage playbook: 1) confirm evidence bundle; 2) check rate/recurrence window; 3) correlate with account signals; 4) assign severity and escalate to CS/Trust if necessary.
- Enrichment: alerts support custom enrichment fields (customer-supplied risk signals), which can be attached at ingestion or via our enrichment webhook before final dispatch.
- Escalation: built-in integration with PagerDuty and Jira (create incident ticket with pre-filled fields).

7) Compliance & evidence bundles
- SOC 2: we provide a SOC 2 summary (SOC2_summary.pdf) plus a list of controls mapped to alerting/monitoring responsibilities. Evidence bundles for incidents include hashed manifests and an audit chain.

Operational notes and limits
- Rateing: alerting throughput is subject to plan limits; Dedicated customers receive dedicated alerting pipelines with guaranteed throughput and delivery SLAs.
- Data residency: Private customers can store evidence bundles in customer-managed S3/VPC.
- PII handling: redaction and tokenization hooks are supported during ingestion.

Sample alert schema (high level)
- id, severity, detector_ids, request_complete_ts, alert_emit_ts, model_id, tenant_id, evidence_url, enrichment_fields[], suggested_actions[], triage_links[]
