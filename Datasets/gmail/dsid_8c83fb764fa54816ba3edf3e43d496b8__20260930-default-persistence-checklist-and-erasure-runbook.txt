Hi Sam,

Thanks — great questions. I've attached a one-page retention matrix (default_retention_matrix_v1.pdf) and summarized the defaults below. High level: hosted tenants see limited persistence by default; there are clear opt-ins and Private deployment options if you need zero persistence.

Summary (hosted, default settings):
- Prompts (raw user inputs): NOT persisted by default as a distinct indexed object. We persist request metadata (timestamp, model id, request size) and a hashed request id for traceability. Raw prompt text is persisted only when a customer enables "store_inputs" or when it's necessary for billing/debug (default off).
- Final completions / model outputs: Persisted by default for 45 days to support debugging, billing reconciliation, and quality monitoring. Outputs are tied to the request id and delete automatically at TTL expiry.
- Streaming token fragments: Transient in-memory buffers during the session. Streaming fragments are NOT written to the durable store unless the session is finalized and the customer has retention enabled; in that case only the final, assembled completion is retained.
- Derived artifacts (embeddings, indexes, reranks): NOT stored by default. The platform provides explicit APIs to create persistent embeddings/indexes; these are considered customer-managed resources and honor tenant-specified residency and retention.
- Geographic residency: Data stored for hosted tenants follows the region selected at tenant creation (US or EU). We do not replicate hosted tenant data across regions unless explicitly configured.
- Retention mechanism / deletion proof: Default TTL (45 days) with automated purge job that removes records and advances tombstones. For customers who require deletion evidence, we provide exportable deletion reports and a proof-of-deletion certificate on request (used for procurement/SOC2 evidence).

Hi Maria / Sam — looping back with the requested runbook and answers. I attached a short runbook (retention_runbook_clearview_v1.docx) and dropped a link to the shared folder above. Short answers: 

- Telemetry/aggregates: We retain high-level telemetry (error rates, latencies, token volume) for platform health, but aggregates are rolled up and do not include reconstructable prompt text. No pipelines retain raw prompts when store_inputs=false.
- Embeddings: Intermediate vectors used for model-side evaluation are ephemeral and not persisted as customer artifacts. Embeddings explicitly created via the embeddings API AND saved to your tenant index are customer-controlled; we do not persist unsaved vectors beyond short-lived evaluation caches.
- Configurable TTL & emergency purge: TTL is configurable per tenant (30/45/90 days or custom). We provide a manual immediate purge API and an erasure workflow that issues a deletion job, returns a job id, and produces a deletion report (job id, affected object counts, timestamps). Proof-of-deletion reports are generated in CSV and signed by our operations team for SOC2 evidence.
