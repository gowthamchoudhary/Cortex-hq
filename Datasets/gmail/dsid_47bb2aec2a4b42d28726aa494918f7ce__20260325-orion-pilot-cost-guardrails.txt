Hi all — attaching the token econ CSV (orion_token_econ_model.csv) and a short readme. High-level notes:

1) Baseline model assumptions (v0):
- Model: open-llm-alpha-16k (quantized variant) — tokens priced at $0.0009 per 1k tokens equivalent on hosted tier (example).
- Average prompt length: 180 tokens; average completion: 120 tokens => avg call ~300 tokens.
- Expected tokens/call (expected): 300; worst-case (long multi-turn): 1,200 tokens.

2) Caching assumptions:
- Prefix/KV cache is most effective when the first N tokens are repeated (we’ve seen 20–40% token savings for templated flows and up to 65% when long static context is reused).
- For your workflows (mix of repeated forms + dynamic content) we modeled two cache tiers: prefix cache (fast hit, 30% saving) and session KV reuse (moderate hit, 15% saving). The attached model includes toggles for both.

3) Batching guidance:
- Server-side batching helps when you can accept slight added latency (~50–150ms) and have many short calls. For your nightly ingestion, batching groups of ~8–12 reduces GPU overhead and can improve tokens/$ by ~12–18% on throughput limited runs.
- Note: batching has diminishing returns on long multi-turn flows; we included a scenario that disables batching for >=800-token calls.

4) Unit economics outputs included in CSV:
- tokens_per_call (expected/worst), calls_per_day, tokens_per_day, tokens_per_dollar, monthly_cost_estimate at different SLOs.

Liz / team — small addendum to the econ model with runtime details that affect tokens/$ and feasibility for your SLA: 

- Quantization: the recommended 4-bit quantized variant reduces GPU memory and cost by ~20–30% for inference while keeping accuracy loss <1.5% for most prompts (we include a column in the CSV showing tokens per GPU-second).
- KV cache hit model: assume a distribution where 40% sessions get a >60% prefix hit, 35% get a 20–40% hit, rest <10%. The model outputs expected token savings across that distribution.
- Batching latency impact: p50 latency increases ~30ms for batches of 10 on our test infra; p95 sees ~80ms uplift under high concurrency. We included both p50/p95 lines so procurement can see tradeoffs between cost and SLO.
