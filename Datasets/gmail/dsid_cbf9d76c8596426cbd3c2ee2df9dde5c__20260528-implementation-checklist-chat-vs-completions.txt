Subject: RE: Internal: Acme integration asks summary (chat vs completions, auth, routing, streaming)

High-level plan (concise):

1) Auth pattern
- Approach: support their short-lived tokens by accepting a signed bearer token issued by Acme's token service. We'll validate signature + expiry server-side. Optionally, offer a short-lived Redwood session token (STS) that maps to a customer id for routing/quota.
- SDK change: add helper to exchange customer STS for Redwood session token (1 function, backwards compatible). Example: GET /auth/exchange?token=<signed-token> -> returns session_token (expires in 5m).

2) Chat vs Completions recommendation
- Use Chat API for: multi-turn assistants, tool calls, and structured JSON with function/tool calling. Chat models preserve role/tokens and make tool calling simpler.
- Use Completions for: single-turn templated outputs where you control the prompt carefully (lower latency for ultra-simple tasks).
- Tokenization notes: both APIs are tokenized the same; advise conservative max_tokens. For structured JSON, reserve N tokens for the model output (e.g., if context ~6k, and max model context is 8k, set max_tokens=1500 cap).
- Stop sequences: for JSON we recommend using function-calling if available; otherwise supply a unique stop token ("\n--END_JSON--") and post-validate. Avoid relying solely on stop for correctness.

3) Streaming semantics for structured outputs
- Two options:
  a) Stream raw chunks: client receives partial UTF-8 chunks. Risk: partial JSON invalid until final chunk. We recommend a framing layer: send incremental JSON lines where each chunk is a complete partial object (e.g., chunked fields) or use the event stream with "delta" tokens and an end-of-message sentinel.
  b) Non-streamed final JSON: for critical deterministic flows, prefer non-streamed and validate on server before returning to client.
- Implementation: we can support chunked "json-patch" style streaming as an opt-in mode in the SDK so client can rehydrate and validate progressively.

4) Routing & fallback
- Policy suggestion: route by policy key in the session token. Default route -> cost-optimized variant (quantized model). If request includes header X-PII-FOCUS=true or scope=payments, route to pinned high-quality model in dedicated pool. Canary rollout: 5% traffic pinned then 25% based on success metrics. Automatic fallback: if pinned capacity unavailable, fall back to next compatible variant with graceful degradation header.

5) Embeddings & reranker
- Batch embeddings (512–1024 items per batch) to max out GPU throughput. For 2M docs, recommend offline indexing pipeline with incremental updates. For reranking at 100 qps, use a two-step pattern: lightweight similarity candidate retrieval (FAISS) -> model-based reranker for top-K, keep reranker model small (distilled) for latency.
