Q1 — Geographic storage for request/response and derived artifacts- Hosted API model execution and transient artifacts are executed in the region you specify at request time (choices: us, eu). By default tenant data for free/self-serve signups is served from US regions (us-west). For enterprise customers (including AcmeSoft) we can pin hosted workloads to EU-only or US-only zones via account-level configuration; enforcement is by routing and storage policies that restrict data plane resources and audit logs to the selected region.

Q2 — Default retention windows (hosted API):
- Request/Response payloads: retained up to 30 days by default to power debugging, abuse detection, and short-term tooling.
- Embeddings and vector indexes created by the hosted API: retained up to 30 days unless the customer elects persistent storage for search workflows.
- Inference logs (model latency, token-level costs): aggregated metrics retained 13 months; raw logs used for billing/diagnostics retained 90 days by default.
- KV/prefix caches: ephemeral; kept in-memory or local to the serving node for the duration of the session and not written to long-term storage (deleted immediately after the request lifecycle completes).
- Backups & snapshots: encrypted backups of service metadata exist for recovery; retention window for backups is up to 90 days.

Q3 — Deletion workflow & SLAs:
- Customer-initiated deletion (primary stores): requests submitted via support + data-deletion API are acknowledged immediately; primary data purge completed within 48 hours in normal operations.
- Backups & cold archives: may require up to 90 days for complete removal due to snapshot lifecycle; customers are informed of this window during the deletion confirmation.
- Verification: we provide a deletion confirmation report (signed/hashed) and a machine-readable audit entry in the account's audit log once deletion completes.

Q4 — Exceptions / legal holds:
- Data required for active legal holds, litigation, or regulatory retention will be preserved as required; Redwood will notify customers of any compulsory holds and the legal basis.

Q5 — Region selection & enforcement: same as Q1 — account-level pinning or per-request region selector. For EU-only enforcement on hosted tier we restrict model-serving endpoints and persistent stores to EU regions and do not mirror data to other regions.

Encryption & access control notes:
- All stored data is encrypted at rest using keys managed by Redwood KMS; for enterprise customers we offer customer-managed keys (CMK) integrated with common KMS providers.
- Data in transit is TLS 1.2+ with mutual TLS available for private links.
- Access to customer data is role-based and audited; support/engineers require Just-in-Time access and approvals for any manual data access.

Hi Sam — quick clarifications:

1) Embeddings persistence: Redwood does not persist embeddings for customer accounts by default outside the short default retention window (30 days). For customers who enable Redwood-managed semantic search or vector stores we persist embeddings in the chosen region; persistence is an explicit account-level feature and is reflected in the UI/API and billing. If you want zero-persistence on hosted API we can set the account flag to disable Redwood-managed vector stores; you can still compute embeddings client-side and store them in your own systems.

2) KV/prefix cache durability: caches live in-memory on serving nodes. We do not write prefix caches to long-term disks. In the rare event of host-level crash diagnostics, memory captures are only generated with engineering approval and are treated as high-sensitivity artifacts (subject to the same deletion flows and access approvals). We also ensure swap space is encrypted at the host level; by default we avoid swapping persistent inference caches.

3) Recreation risk after deletion: deleting historical artifacts removes the stored vectors and request logs; however, identical new requests will produce new derived artifacts (new embeddings) because embeddings are deterministic only to the model + tokenization and often differ with model versions. If your concern is re-materialization, recommend pairing deletion with: (a) account-level rate limits during the purge window, and (b) a short-term policy to route suspect traffic to a deleted-data-safe pathway during confirmation. We can operationalize both for the enterprise onboarding.
