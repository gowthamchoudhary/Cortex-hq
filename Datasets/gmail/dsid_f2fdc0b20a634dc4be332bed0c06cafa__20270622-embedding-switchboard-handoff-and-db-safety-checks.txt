Alex / team — adding the technical tradeoffs so Searchly can confirm constraints. TL;DR: incremental backfill + prefix caching is lowest risk; full rebuild fastest to final state but needs maintenance window and more I/O.

Vector DB and operational notes:
- Access model: we recommend using our VPC peering path for indexing RPCs. Index writers are limited to service accounts we register for your tenant; see access-matrix.csv. No human accounts are given write privileges.
- Encryption: TLS 1.3 in transit; AES-256 at rest on Redwood-managed volumes. If you require customer-managed keys (KMS/HSM), we support that on Private deployments — let us know.
- DB choices: (a) Redwood-managed vectorstore (default) — simpler, managed snapshots and hot fallbacks; (b) self-hosted vector DB (we support Faiss/Weaviate/Annoy connectors) — more control, you manage snapshot/restore.
- Throughput: with Dedicated x2 + autoscale, expect ~200k docs/hour (average doc size ~1KB). Performance varies with embedding dimension and network egress.
- Fail-safe: we'll create a write-ahead index and a read-only mirror during the final pass to allow immediate rollback to previous read path.

Operational checklist highlights (also in preflight):
- Confirm service accounts + CIDR ranges for peering.
- Confirm retention window for fallback index (recommended 72h).
- Run a smoke evaluation with a target prompt set (we propose 50 eval queries) and observe MAP/recall deltas before/after.

If Searchly is open to it, we can run a brief load test tomorrow morning (2-hour window) to baseline throughput numbers against your exact dataset.
