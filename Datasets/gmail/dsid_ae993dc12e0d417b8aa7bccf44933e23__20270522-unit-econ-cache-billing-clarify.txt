Lena — thanks for the context and the clear asks. I promised a short worked example and a plain-English note on caching vs billed tokens, so here goes. I’ve also attached a concise pricing export (.xlsx) and a scoped SOW draft for the pilot.

1) Metrics mapping example (approx):
- Your reported characters -> approximate tokens: rough heuristic = characters / 4. So 600 characters ≈ 150 tokens; 300 characters ≈ 75 tokens. This varies by language/whitespace but is a practical conversion for planning.
- Token sides: we bill for total model tokens = prompt tokens + completion tokens (both count).
- Requests: each API call is a request unit. If you make 1.5M interactions, that’s 1.5M request units irrespective of token size (requests meters and rate limits are separate from token billing).

2) Unit economics example at headline pricing: (illustrative only — final depends on model selection & committed tiers)
- Example price: $X per 1K tokens (we’ll use $0.50 / 1K tokens as a demo number).
- For an average interaction above: prompt 150 tokens + completion 75 tokens = 225 billed tokens per interaction.
- 225 tokens × 1.5M interactions = 337,500,000 tokens = 337.5M tokens.
- At $0.50 / 1K tokens -> cost = (337.5M / 1K) * $0.50 = $168,750.
- Stated another way: $0.50 per 1K tokens -> $500 per 1M tokens. So your target $/1M metric translates directly to that.

3) Caching / prompt reuse note (important):
- If you have repeated static prompts (e.g., identical system prompts, boilerplate instructions, or shared context stored outside model calls), Redwood can apply prefix/KV caching to avoid re-sending/re-billing those tokens on subsequent requests to compatible sessions.
- Caching reduces billed prompt tokens but does NOT change completion tokens — completions are always billed.
- Caching effectiveness example: if 60% of prompt tokens are static and cacheable, effective billed tokens per request could drop from 225 → 150 (only dynamic prompt + completion billed). That would lower your costs proportionally.

4) Requests vs characters vs tokens — TL;DR:
- Characters: a client-side measure useful for estimation; convert to tokens for billing planning (chars/4).
- Tokens: the billing unit (prompt + completion).
- Requests: number of API calls (affects rate limits and per-request costs when applicable, but not token billing except when you have per-request add-ons).
