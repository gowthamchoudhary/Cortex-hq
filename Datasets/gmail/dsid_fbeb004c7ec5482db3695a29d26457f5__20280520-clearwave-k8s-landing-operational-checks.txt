Thanks — good starting point. I validated the rack/network constraints from the inventory and have a few adjustments and operational notes below. Quoting the draft where helpful.

On node counts & sizing (recommended):
- gpu-inference (G): 3–4 nodes, each with 4 x A100-40GB (or 2 x H100 if available), 1.5–2TB RAM recommended if you expect large batched contexts. CPU: 32 physical cores per node (hyperthreads ok). NIC: prefer 100G uplink per node for high-throughput KV sync and multi-GPU RDMA if you enable GPUDirect. Local NVMe: 4 x 2TB NVMe (software RAID0 for cache) — total ~8TB fast local.
- services-cpu (S): 6–10 nodes, 48 cores / 384GB RAM, 4TB NVMe; these host sidecars, batching workers, and non-model services.
- infra-ssd (I): 3 nodes on SAN for heavy IO (NetApp LUNs). Keep one node as an admin/ops bastion that also runs Velero and backup jobs.

Storage/Critical configuration:
- Use CSI driver for NetApp (Block) for model artifacts; mount models read-only into inference pods and copy to local disk on cold-start to avoid NFS saturation.
- Local PVs via CSI local-volume for NVMe caches. Reclaim policy: Retain for debug, but automated TTL cleanup at the orchestration layer (we manage lifecycle).
- Backup cadence: nightly incremental, full weekly; retention: 90d for customer data; audit logs: retain 2y (ship to your long-term storage).
- Kubelet eviction: set evictionHard imagefs.available<15%, memory.available<200Mi to avoid noisy-evictions during bursts. Tune kube-reserved and system-reserved to preserve GPU processes.

Networking and performance gating:
- MTU 9000 (jumbo) recommended across cluster fabric.
- Ensure at least 2x100G uplink for GPU nodes; enable SR-IOV if you plan dedicated NICs per GPU worker for lower latency.

Operational runbook highlights:
- Canary rollout: start with 10% of traffic to a single GPU node pool; wire in canary metrics (latency P95, token throughput, GPU utilization).
- Chaos tests: drain a GPU node and validate KV cache warmup time and request latency.
- Upgrade plan: control-plane first, then infra, services, GPU last; 30-minute rollback window per step.

Tests to run during staging:
- Load: gradual ramp to 2x expected peak for 30 minutes; validate autoscaler behavior and latency SLOs.
- Failure injection: simulate single rack failure and verify fallback to second rack (we'll validate pod disruption budgets and anti-affinity).

Dependencies we need from Clearwave for staging:
- Access to NetApp management for provisioning LUNs / storageclass creation
- A KMS endpoint or certificate exchange procedure for any keys we store (if you require HSM-backed keys, please surface vendor contact)
- A short-lived VPN tunnel or bastion IP allowlist for Redwood operations (we'll provide IPs).
