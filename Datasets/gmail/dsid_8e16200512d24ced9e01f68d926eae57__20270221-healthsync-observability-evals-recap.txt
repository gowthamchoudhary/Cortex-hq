High-level pain points you described:
- Intermittent latency spikes on your public API that correlate with specific prompt templates (users see timeouts ~500ms+ above baseline).
- No reliable way to detect semantic regressions after model updates — current health checks are token-level only.
- Fragmented telemetry: inference logs live in S3, metrics in Datadog, and there is no end-to-end tracing from user query → model response.

Current stack you shared:
- In-house LLM proxy that fans out to multiple model variants; Redis for lightweight KV cache; Datadog APM for service metrics; Postgres for events.

Success criteria you listed:
- Latency: p50 <100ms, p95 <300ms for customer-facing endpoints under normal load.
- Quality: measurable semantic regression <= 5% (embedding-based drift) after model changes.
- Ops: single-pane dashboard for latency, error rates, KV cache hit rate, and prompt-level failure traces.

Specific observability & eval asks we captured:
1) Dashboards: error-rate (500/502/timeout) over time, prefix latency p50/p95, KV cache hit rate + TTL distribution, per-prompt success rate.
2) Tracing hooks: request/span IDs passed through the LLM proxy, ability to attach prompt metadata (prompt_id, customer_id, flow) to spans.
3) Golden prompt sets: 30 "golden" prompts across happy path + 15 edge cases that we can run on every model roll.
4) Regression alerts: automatic alerts when embedding-cosine drop > 0.08 on golden set OR when per-route success rate drops >1.5% absolute.
5) Rollout guardrails: canary at low traffic with automatic rollback if semantic regression exceeds threshold.
