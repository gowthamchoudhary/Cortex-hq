Team,

I'm kicking off a short review of an approach I've been prototyping to make our private deployments (VPC/on-prem) more immutable and audit-friendly across Terraform, Helm, and Ansible. The goal is to reduce configuration drift, make rollbacks safer, and shorten evidence time for SOC-type requests.

High-level proposal (attached - immu-env-proposal-v2.pdf):
- Enforce module version pinning at the pipeline boundary (tf module pins + checksum verification).
- Artifact signing for Helm charts and Ansible roles (CI step using our signing key, verify at deploy).
- A "replace-not-mutate" pattern for critical infra (bastions, control-plane components): new infra is provisioned and traffic flipped via LB/route update.
- Drift detection job that auto-creates a remediation PR (read-only enforcement flag in prod).
- CI gating: terraform plan must pass a policy check (OPA rules) and Helm chart must have provenance.

I'm attaching a small patch showing how the pinset would look (tf-module-pinset.patch) and a pipeline diagram for the canary/flip flow. I need feedback on two concrete things from you:
1) Are there any operational blockers for replace-not-mutate in our on-prem playbooks?
2) Any security evidence gaps for artifact signing or provenance verification that would prevent us from recommending this to customers?

Can you review this week? I want to capture a consolidated set of requirements and open CI tickets so we can start a small pilot with Acme next sprint.

Diego — thanks for the clean write-up. Quick read-through below and a few pragmatic suggestions. I'm attaching a short checklist and a tiny example of a Helm provenance workflow (I also pasted comments into your proposal PDF).

Summary of Marissa's comments:
- Replace-not-mutate: workable but depends on stateful components. For stateful services we need a database migration strategy (zero-downtime or schema compatibility), otherwise immutable flips will be rejected by downstream owners. Add a mandatory migration plan for any module that changes DB schemas.
- Pinning: pin at both module and provider versions. We should make provider pinning part of the module linters; otherwise drift comes from provider upgrades.
- Artifact signing: recommend using cosign for Helm charts and signed checksums for tarball artifacts; we should store provenance metadata in the module registry and our audit log.
- Ansible: favor immutable AMI/OS images where possible; but where we must run ad-hoc ansible, require a read-only guard in the control plane that flags mutating playbooks in prod.

Operational blockers I see:
- Our private on-prem pipelines currently allow manual variable overrides at deploy time; we need to lock deploy variables for the prod orgs and move overrides into an approved secrets change workflow.
- The flip window requires coordination with networking (LB updates) — suggest an automated rollback timer and health checks baked into the pipeline.

Next steps (my proposal):
- Create three tickets: RDW-4821 (module pin enforcement), RDW-4822 (artifact signing integration), RDW-4823 (canary flip flow + health gating).
- Pilot with Acme in our staging environment next sprint.

I'll add owners in the follow-up. If Kim or Neha have concerns on the compliance side please call them out.

Samira, great questions — answering inline and proposing concrete owners: 

1) Key management: For private (VPC/on-prem) pilots we propose customer-managed KMS/HSM. Redwood's control plane will support HSM-backed key references (we do not import customer private keys). Action: Kim to document KMS integration patterns and gap list.

2) Audit trail: The pipeline will emit a signed deployment receipt (cosign + pipeline run ID) and publish a copy to the customer's SIEM via secure syslog/HTTPS ingestion. Action: Neha to scope SIEM integration and retention options.

3) Rollback guarantees: Our plan is a canary flip with a short rollback timer. If the canary health check fails we will automatically revert the LB/route change and run remediation steps. We can commit to an internal SLO of rollback < 5 minutes for control-plane flips in dedicated/private capacity, subject to agreed health-check thresholds and network propagation times. Action: Diego to write the rollback runbook and automation (RDW-4823).

Operational notes for our team: 
- We will mark prod deploy variables as immutable via a locked pipeline configuration; runtime overrides route through an "approved-change" ticket.
- For DB-related changes, we will require a migration compatibility sign-off and an automated migration plan run in staging before canary.

I'll open the three tickets Marissa suggested and assign initial owners. If Acme has follow-up constraints please flag them and we'll incorporate them into the pilot scope.
