Summary of quick triage:
- Reproduced the traffic pattern in staging using the same session-length distribution.
- Root cause (probable): an automated config rollout (quota-window-optimizer v2) expanded aggregation windows for tenant burst accounting. That change increased how quickly a tenant exhausts their short-term burst credits under certain interleaved long-context workloads. Effect: requests hit the tenant safety gate more aggressively and the serving runtime routed more requests to the lower-capacity fallback variants, increasing latency and 429s.
- Evidence: quota-config-snapshot.yaml attached (shows new window: 600s -> 1800s for burst accounting), and the logs show repeated short-window replenishment failures.

Mitigations applied (14:30–14:35 UTC):
1) Rolled back the rollout for quota-window-optimizer v2 for production routing policies (stop further config propagation).
2) Short-term policy patch: temporarily increased tenant burst headroom by +30% for VantageIQ namespace to allow in-flight requests to clear (config patch id: patch-burst-20261118).
3) Enabled an aggressive KV cache heal for long-context sessions for the affected hosts to reduce token synth cost.

Immediate impact: error rate dropped from 12% -> 3% in 10 minutes; p99 back to ~380ms but still above baseline. We need to monitor for a full return to baseline and perform a deeper postmortem to avoid recurrence.

Attachments: quota-config-snapshot.yaml
