Folks — reading Sophie's note, a few quick thoughts and hard limits from the runtime side: 

1) Deterministic inflight budget: we can enforce a per-tenant inflight cap at the proxy layer. Suggested starting point: max-inflight=6 (matches their ask). That will bound queueing but increases risk of fairness preemption under saturation; we should pair with a token-bucket admission policy and backpressure TTL.

2) Queue shaping / FIFO per tenant: we can implement strict per-tenant FIFO queues for the pilot. We'll need to pin to a compatible model variant (no dynamic KV evictions or quantization changes) to reduce variability. Recommend we use one stable model (gpt-2.7b-classic) they already validated locally.

3) Observability: we can push 99/99.9/100 latency histograms and KV cache hit metrics to a HeliosPay DataDog endpoint via our metrics exporter. Need an API key and contact.

4) Resource estimate: for HeliosPay's projected peak (they sent sample: 350 qps at median 12 tokens/request) we'd provision 4 reserved GPUs for the pilot with autoscaling disabled. That means a small infra delta for ops. 48h smoke replay + 4-week live window is doable but requires 1.5 FTE infra + 0.5 FTE runtime engineer for the pilot duration to tune admission/eviction thresholds.

5) SLA carveout: we can agree to a temporary 'pilot SLO' (latency target with a relaxed penalty structure) and commit to weekly checkpoints rather than standard credits. If HeliosPay wants formal credits, commercial should weigh in.

I'll draft a brief technical appendix for the pilot runbook. Marissa — can you own the customer facing doc and credit language? If legal wants an MOU template, we can attach a simple pilot MOU (no long-term SLA changes, only temporary pilot carveouts).
