Hi Jordan — quick answers, then next steps.

1) Storage & latency tradeoffs (384d -> 512d):
- Storage: +33% raw vector storage (512/384 - 1). With typical quantization (8-bit), delta in bytes is smaller but still ~25% uplift. For 1.2M docs that’s ~120GB additional raw bytes before any disk compression/codec adjustments.
- Latency: NN search p95 increases depending on your ANN index config; with HNSW and tuned ef/search params, p50 impact is negligible, p95 can be ~10–20% higher if you keep the same efConstruction/efSearch. Recommendation: increase efSearch by 20% and tune index shards; we’ll run these numbers in Step C.

2) Quantization accuracy (rw-emb-512q):
- In our internal tests quantized 512d loses ~0.01–0.03 MRR compared to float32 512d on paraphrase-heavy sets — often within tolerance when balanced by cost savings. Worst-case on niche phrase-matching tests we’ve seen up to 0.05 MRR drop.
- We’ll produce per-query deltas so you can see which query types regress; the regression harness will surface top-10 queries that cross the threshold.

3) Dataset / POA / PII:
- We can accept a redacted dump. We will not persist raw PII in plain text and can sign your POA/NDA. Our standard handling: ephemeral bench container, results only stored in your Drive / S3 (whichever you prefer).
