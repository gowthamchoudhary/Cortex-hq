Hi all — technical follow-up and attachments. See notes and artifacts attached.

Summary of produced artifacts (attached):
- data-residency-matrix.csv — region -> storage tier -> backup residency.
- s3_lifecycle_policy.txt — canonical lifecycle rule we apply for logs and artifacts (includes expiration days and transition actions).
- playbook-erasure-steps.pdf — step-by-step operator playbook for manual and automated erasures (includes SLA timings and verification steps).
- deletion-audit-sample.log — redacted sample showing a customer deletion request id, worker id, timestamps for request/ack/delete, and confirmation event.

Notes on evidence / mapping to controls:
- Retention: We have policy-driven lifecycle rules for ephemeral request logs (default 30 days), embeddings (configurable per-customer, default 90 days), and backups (90 days with region-specific residency). We can provide per-customer overrides on request and evidence of the override in the account configuration.
- Deletion proof: Our deletion workflow records a: deletion_request_id -> queue handoff -> worker execution -> object tombstone -> verification event. The delete is irreversible once tombstone garbage collection runs (we include the GC timestamp in logs). The sample log demonstrates the full chain; customer identifiers are hashed.
- Residency: Primary storage is region-local (e.g., us-east-1 for US customers). Cross-region backups occur only if the customer opts in or for DR with a documented justification. The residency matrix enumerates these settings.

Security note: we’ve redacted customer identifiers in the sample logs and replaced raw ids with salted hashes per our redaction policy. If auditors need different redaction (e.g., tokenized but reversible under NDA), we can arrange that through legal.

Deliverables attached here: s3_lifecycle_policy.txt, deletion-audit-sample.log, data-residency-matrix.csv, playbook-erasure-steps.pdf
