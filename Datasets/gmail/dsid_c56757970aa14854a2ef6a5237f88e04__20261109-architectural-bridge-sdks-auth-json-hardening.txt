Runtime patterns I recommend for reliability:

- Client-side validation: run ajv (or equivalent) against the raw output and, if validation fails, trigger a bounded retry with added context (higher temperature 0.0 -> for deterministic decoding, we actually bump decoding constraints — see below).
- Idempotency: include a request_id so retries are deduplicated server-side.

Hi all — attached is a first-pass JSON schema (json-schema-v1.json) for the endpoint we discussed. Key decisions called out in the schema comments:

- Use explicit enums for status fields and typed arrays for the candidates array (maxItems: 10) so the downstream pipeline never sees an unexpected shape.
- Include a `metadata.version` field that we increment per rollout to make regression detection easier.
- Recommend returning `candidate_scores` as an array of objects with explicit `score_normalized` in [0,1] to avoid float-precision assumptions.

Validation + retry pattern (concrete):
1) SDK call -> runtime returns structured JSON or a parse error with code: OUTPUT_SCHEMA_VIOLATION and payload containing raw_text and tokenizer offsets.
2) Client runs ajv; if ajv fails, call a special `/retry-decode` route (same request_id) that triggers constrained decoding with the runtime using a deterministic beam (k=4) and a lower temperature.
3) If `/retry-decode` fails after 2 attempts, mark the item for manual review and increment a metric `schema.failures` for alerting.
