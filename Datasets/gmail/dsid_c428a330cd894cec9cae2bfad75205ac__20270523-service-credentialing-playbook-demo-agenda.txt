Elise — thanks for the list. Quick answers inline and a recommended credentialing approach: 

1) Short-lived credentials + KMS integration (recommended):
   - Pattern: Customer-managed service account keys or OIDC-signed tokens exchanged for Redwood short-lived tokens (TTL 15m–1h).
   - Rotation/revocation: Centralized control plane via your KMS; we support asymmetric key verification and an emergency revocation endpoint. We can publish a revocation webhook that triggers immediate invalidation of in-memory caches on Redwood side.
   - Benefit: No long-lived secrets stored in your app; easier to comply with rotation policies.

2) API keys with automated rotation (alternative):
   - Pattern: Long-lived API key stored in KMS + automated rotation job (we provide sample rotation script). Revocation requires key deletion + short cache TTL on our side (recommended 5 min).
   - When to pick: If your environment doesn't support automated token exchange for short-lived tokens or for simple server-to-server setups.

3) Cross-region routing and PII handling:
   - Policy controls: Requests are routed according to a per-tenant policy. We can configure strict region pinning (deny cross-region fallback) or allow fallback to compatible variants if a region is completely out of capacity.
   - Data residency: We support tenant-level residency constraints and will annotate logs to flag any cross-region routing decisions; we can also provide audit traces for each request.

4) Sample JWT/OAuth flow + SDK snippet:
   - Link: https://gist.github.com/redwood/9f8a7e-sdk-auth-snippets (includes server-side token exchange + python/node examples).
