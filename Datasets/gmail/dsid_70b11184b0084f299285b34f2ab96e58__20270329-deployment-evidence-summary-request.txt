Hi Evelyn — looping in a few technical artifacts you asked for and answering the detailed questions below. I've attached a CSV-format answer table (sig_answer_table_v2.csv) and a network diagram that highlights the boundary differences between Hosted and Dedicated (network-diagram-hosted-dedicated.png).

Concise technical mapping (for SIG entries):
- Hosted (Redwood API): Multi-tenant runtime hosted by Redwood. Tenant isolation is logical: request routing and per-tenant access controls separate tenants. Data at rest for model artifacts and persistent caches are encrypted with customer-managed keys for enterprise customers; log/metrics retention defaults to 90 days and can be shortened by request or extended under contract for Dedicated/Private.
- Dedicated (Reserved capacity): Dedicated GPU pools and dedicated storage volumes assigned to the customer. Network and disk-level isolation are enforced; customers can request physical host-level isolation in sensitive deployments. We provide pod/node labels and allocation records as evidence for Dedicated pools.
- Private/VPC or On-Prem: Control plane and/or data plane components can be deployed into the customer's VPC or as an on-prem binary bundle. In this mode the customer controls the network perimeter and KMS; Redwood provides configuration guides, signed attestations of the artifacts we ship, and an ops runbook for onboarding.

About KV cache / inference state: KV caches are ephemeral per-session by default and are not persisted centrally for hosted tenants. For Dedicated/Private customers we provide options to persist caches to customer-managed volumes if the workload requires it; otherwise caches are ephemeral and flushed at session termination.
