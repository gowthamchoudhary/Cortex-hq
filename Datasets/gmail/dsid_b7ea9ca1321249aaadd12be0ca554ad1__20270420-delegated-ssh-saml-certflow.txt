Following our call last week, I put together a lightweight proposal for how teams at Acme could get short-lived SSH access into customer-managed on-prem/private control plane instances without opening long-lived host accounts. The goal: let Acme engineers/ops use your IdP (SAML) + SCIM group sync to mint ephemeral SSH certificates that are accepted by the private control plane bastion. Key points: compact summary below, diagram attached.

What we want to validate with you:
- Acceptable SAML attribute mapping for role -> SSH principal (groups, eduPersonEntitlement, or custom claim)
- SCIM cadence and group-to-RBAC mapping (we propose 15m sync window + delta sync)
- Network requirements: egress, reverse-proxy, and whether Acme requires mTLS between bastion and Redwood agent
- Audit/logging: token/claim capture, certificate issuance logs, and central retention requirements

High-level flow (attached diagram):
1) User signs in to Acme IdP and requests SSH via internal portal (or CLI shim).
2) IdP issues SAML assertion with attributes for groups and expiration.
3) A short-lived certificate authority (CA) in the private control plane mints an SSH cert after validating the SAML assertion via an assertion-proxy (we can host the proxy inside the VPC).
4) SCIM sync keeps group membership aligned to control-plane RBAC so long-lived role bindings are maintained.

Thanks Diego — useful summary. A few quick constraints/questions from Acme Sec: 

1) Network: we cannot allow any uncontrolled outbound traffic from the customer bastion to public internet endpoints. If the assertion-proxy needs to validate with Redwood, it must either run entirely inside our VPC (preferred) or communicate via an approved proxy over mTLS.

2) Audit: we need immutable issuance logs with user principal, assertion id, CA serial, and a tamper-evident digest. Will your PoC produce logs we can ship to our SIEM (Splunk) over syslog or HTTPS?

3) Short-lived certs: acceptable TTL is 15m-1h. Prefer 15m for admin access, 1h for low-privilege jobs.

4) SAML claims: our IdP (Okta) can emit group DNs and custom attributes. We prefer group-based mapping using SCIM groups. However, we will not expose raw SAML assertions outside our VPC — the assertion-proxy must be able to verify assertions without sending the raw assertion elsewhere.

Hi Tim — thanks, noted. I pulled together a short runbook and mapping that should address the points below (see runbook-delegated-ssh.md attached). Summary highlights here inline: 

- Local deployment model: assertion-proxy and short-lived CA run inside customer VPC (AMI/container we provide). No outbound requests required to Redwood core for validation — proxy validates SAML via IdP metadata and local keys.

- SCIM sync: we recommend SCIM 2.0 push/pull with a delta-sync every 15 minutes. Sample mapping in scim-group-mapping-sample.json: SCIM group -> control-plane role (admin, operator, viewer). We also include a fallback mapping for nested groups.

- Auditing: the proxy writes signed issuance events locally and ships a compact envelope to your SIEM over HTTPS or syslog via an outbound, customer-managed collector in the VPC. We include a reproducible hash (SHA256) of the assertion and cert serial in the envelope for tamper-evidence.

- Key management: private deployments support HSM-backed CA via customer KMS/HSM (AWS CloudHSM or customer HSM appliance). CA rotation is configurable; our suggested default rotation window is 90 days with automated rollovers and an overlap grace period for cert validation.

- Example SAML->SSH mapping: 
  - SAML attribute: groups -> control-plane role
  - SAML attribute: email -> ssh principal username
  - Custom claim: acme:scoped_role -> granular RBAC scope
