Thanks, this is super useful context. I've attached the hosted rate card (PDF) and a CSV with a couple of worked examples using the exact profile you sent. High level answers below; tagging our billing and metering experts for a precise clause you can drop into the SOW.

High level (hosted API, list rates):
- Baseline list pricing: $0.012 per 1k input tokens, $0.018 per 1k output tokens. (We provide volume discounts in committed Reserved / enterprise plans — happy to scope.)
- System messages (assistant/system prompts) are counted as input tokens.
- Tokens produced by the model as part of function_call serialization (the JSON payload the model emits to call a tool) are counted as output tokens.
- Tool responses that are sent back into the conversation and tokenized by the model (textual tool outputs) are counted as output tokens. If a tool returns non-tokenized binary (e.g., an attachment blob) we bill only for the model tokens used to request/parse that tool output, not the binary itself (we include an attachment stub in logs).
- Streaming: metering occurs as tokens are emitted by the model. We aggregate at the request level and bill the sum of input and output tokens for that request. Billing granularity is per-token (no 100-token buckets). In other words we bill at 1-token resolution based on our server-side token counts for the request/response pair.

Ben —

Thanks for the draft. Edits below (in plain language we can paste into the SOW paragraph), plus a worked example that matches Susan's profile. We should be conservative in wording to avoid surprises.

Final SOW paragraph we recommend: 
"Redwood measures and bills token usage per request. Input tokens comprise system messages (including any hidden assistant/system prompts), user prompts, and any explicit tool inputs sent to the model. Output tokens comprise model-generated completions, tokens emitted as part of model function_call serialization, and any textual tool responses that are returned to the conversation and processed by Redwood's tokenizer. Tokens are counted by Redwood's server-side tokenizer and billed at per-token granularity. For streaming responses, tokens are metered as they are emitted by the model; the billed token count for a request is the sum of input and output tokens recorded for that request. Binary blobs returned by tools (non-tokenized attachments) are not billed as tokens, though any textual metadata or captions associated with those blobs are billed as output tokens. Retries caused by client/network errors are billed per request; automatic server-side fallbacks to alternate model variants will result in billing for the total tokens consumed across the server-side invocations, unless otherwise specified in an agreed fallback SLA."

Worked example (Cartwheel profile):
- Profile: input (user + system) = 180 tokens; model completion = 420 tokens; occasional tool response = 100 tokens.
- Per-request counts: input = 180 tokens; output = 420 (model) + 100 (tool textual response) = 520 output tokens.
- Total tokens per request = 180 + 520 = 700 tokens.
- Using list rates Ben quoted: input cost = (180 / 1000) * $0.012 = $0.00216 per request; output cost = (520 / 1000) * $0.018 = $0.00936 per request; total = $0.01152 per request.
- For 50M requests/month the nominal spend (list rates) = 50,000,000 * $0.01152 = $576,000/month.

Edge cases / clarifications:
- Hidden/system prompts: counted as input. Good to call out explicitly (we did).
- Function calls: the tokens that the model emits to perform the call count as output tokens; any textual payload returned by the tool and then tokenized is counted as output tokens. If the tool returns structured data that the model ingests as input for a subsequent call in the same request, those tokens are counted in the input for that subsequent invocation (effectively billed to the same overall request).
- Streaming: we meter tokens as emitted; there is no per-100-token rounding or buckets. We bill at 1-token granularity.
- Retries/failures: client-initiated retries are billed for each request processed. Server-side automatic fallbacks are billed for combined tokens across invocations; we typically only see this for capacity-based fallbacks—if a customer wants an alternate behavior (e.g., do not bill for fallback attempts) we can negotiate in the contract.
