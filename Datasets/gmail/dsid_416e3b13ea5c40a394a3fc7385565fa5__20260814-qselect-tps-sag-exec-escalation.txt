On it. Quick findings from infra telemetry:
- FastCommerce traffic was routed to kernel variant qselect-v2 at 2026-08-13T16:22:14Z (can provide routing logs).
- qselect-v2 uses an aggressive 4-bit quant profile for the last-layer GEMM and a kernel scheduling change that increases micro-batching (better for throughput generally).
- For long-context gen (avg seq len ~1.2k) we've surfaced a drop in tokens/sec when KV cache hit patterns are heavy — micro-batching + the new kernel's memory-access pattern is causing CPU-side stalls in host-thread IO for these tenants.

Proposed immediate mitigation:
1) Pin FastCommerce to qselect-v1 (previous kernel/quant profile) — should return to baseline.
2) If pin unavailable, route to a near-equivalent older variant in the same region.
