Appreciate the details, Alex. Short answers before Karthik provides sizing:
- Yes, we support a lightweight edge gateway (Redwood Edge Gateway) that can run in a VM/container within customer-managed infra — it manages warm pools and routing. For model shards, we have two patterns: shard + local KV cache (best for very low-latency p50/p90) or local warm pool + cloud KV fallback (simpler to operate). Sharding requires slightly more ops and consistent local capacity.
- Cold-start mitigation: warm pools + prefix caching reduces cold start impact for common triage templates; we’ve seen p95 improve by ~30–45% across similar customers when warm pools are sized to expected burst concurrency.

Alex / Irene / Monica — following up with an initial topology sketch and sizing assumptions based on your burst profile. High level:
- Option A (Hybrid edge + cloud fallback) — recommended for TeleMedPro
  - Per-region Redwood Edge Gateway (k3s/ami) running as containerized controller; keeps a warm pool of 2x small GPUs (A10s or equivalent) per region for hot-path triage model (quantized 13B).
  - KV prefix cache deployed on local NVMe (read-heavy) for session context up to 1k tokens; cache hit expected ~65% for triage templates.
  - Cloud fallback: scalable pool (reserved + autoscale) in primary region to absorb overflow and heavy summarization workloads.
  - Expected performance: triage p95 <=110–130ms (dependent on network RTT for remote clinics); summarization p95 <=250–350ms when using cloud fallback for large context.

- Option B (Cloud-only, aggressive caching) — lower ops overhead but higher network dependence
  - Centralized cloud serving with aggressive KV prefix caching and prioritization queues. Warm pools sized to handle baseline 40 qps; burst handled by autoscale with graceful degradation (prioritization).
  - Expected performance: triage p95 ~140–220ms for remote clinics; better for regions close to cloud.
