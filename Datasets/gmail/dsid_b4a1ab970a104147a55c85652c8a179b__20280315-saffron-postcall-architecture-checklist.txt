Emily — appreciate the clarifications. Quick technical notes on the items you called out.

End-to-end p95: we will measure at the API gateway level in-customer VPC (agent container that proxies to the Redwood model endpoint). Our latency budget will include network hop inside the VPC; for planning I will assume ~20-40ms network overhead for intra-region traffic.

KV-cache warmup: yes — we can support proactive KV-cache population for the triage model. Options:
- Warmup job inside the VPC that runs 15 minutes before business hours to prime common prefixes.
- Persistent warm caches pinned to the Dedicated pool for hot replicas (recommended for sub-150ms p95).

Topology variants (brief):
1) Fully private: control plane in Redwood but with private connectors; model runtime entirely in Saffron VPC on customer-managed nodes. Pros: lowest egress risk; Cons: higher ops surface.
2) Hybrid (recommended PoC): model runtime in Redwood Dedicated pool inside same region, routing via a private peering link; private control plane components still live in customer VPC. Pros: faster autoscale and simpler rollback.

Sizing back-of-envelope for PoC: to meet p95 <= 150ms for 256 tokens at 800 rpm sustained with bursts to 2k rpm, we recommend a Dedicated pool of 6x A100-equivalent machines with continuous batching tuned to 30-50ms batch latency and KV-cache enabled. We will instrument token-level cost so you can see the per-transaction unit economics.
