Team —

Thanks for the bridge this morning. Summary of what we observed and preliminary root cause (draft):

1) Symptom set
- Intermittent 500s concentrated on checkout POST /v1/checkout when sessions exceeded ~1,000 tokens.
- Tail latency increases from 120ms P95 to >1.2s during surges; token generation timeouts reported on several hosts.

2) Immediate mitigations applied during bridge (status: DONE)
- Enabled stable-variant fallback routing for checkout traffic (reduced 500s by ~70%).
- Increased autoscaler aggressiveness for the affected pool (scale target +25% for burst window).
- Turned on per-request KV-cache bypass for suspect sessions to avoid stale prefix merges.

3) Preliminary root cause hypothesis
- We saw KV cache fragmentation combined with a recent micro-optimization in the serving runtime that changed the kernel selection path for long sequences. Under certain long-session patterns the quantized attention path triggered memory pressure, causing OOM and non-graceful failures (500s). The autoscaler thresholds were tuned for steady-state load and did not react fast enough to the burst pattern.

4) Remediation plan (owners + ETA)
- Short-term (0–72 hours): keep fallback routing enabled; tune autoscaler thresholds + add surge buffer (Owner: infra-sre — ETA: 24 hours).
- Medium-term (1–2 weeks): revert the recent kernel fallback tweak for long-seq workloads and add sequence-length-aware kernel selection (Owner: serving-runtime eng — ETA: 7–14 days).
- Long-term (4–8 weeks): add per-account sequence-profile based autoscaling and KV compaction heuristic to prevent fragmentation (Owner: runtime team + product)

5) Validation plan
- Synthetic load tests that mimic NovusLine checkout session profiles (Owner: performance eng)
- Post-deploy smoke windows and observability dashboards (Owner: ops)
