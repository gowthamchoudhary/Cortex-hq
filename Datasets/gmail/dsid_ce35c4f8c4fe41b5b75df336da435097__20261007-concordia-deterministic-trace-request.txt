Thanks for the context, Lauren. A few clarifying questions before we propose scope: 

1) Deterministic trace id — do they need cryptographic immutability, or is a collision-resistant request id that we propagate through existing headers sufficient?
2) Export format — JSON lines vs CSV? Do they require field-level redaction (PII) prior to export?
3) Activation SLO — is the request for reserved GPUs/warm pool for the tenant only, or a higher-priority routing across the shared pool?

Notes on feasibility:
- Propagating a request id through the API gateway and including it in runtime logs is straightforward (low-risk).
- Generating a deterministic id that remains stable across retries and routing changes requires a small change to the routing layer (seed from upstream metadata) — medium effort.
- The on-demand export pipeline is the heavier lift: we need a durable index keyed by tenant+date and an admin-run export job. We can do a narrow MVP (store minimal trace payload + token/trace refs) and export that; full fidelity request payloads will take additional storage and redaction work.

If Concordia only needs a stable trace id + lightweight export (timestamp, path, status, latency, trace id) we can likely scope this to a 4–6 week sprint (product + 2 engineers + one infra support). Full trace capture and redact/export pipeline is 10–12 weeks.

I'll draft a minimal spec if folks agree on target MVP.

Echoing Markus — technical feasibility looks good for a scoped MVP. Quick engineering take: 

MVP (opt-in tenant flag):
- Wire a tenant-scoped deterministic id generated at gateway (HMAC over tenant_id + request_ts + nonce) and propagate via X-Redwood-Trace header. (2 dev-weeks)
- Runtime: record minimal trace envelope {trace_id, ts, route, latency_ms, status_code} into a compact time-partitioned store (append-only). (2–3 dev-weeks + infra config)
- Admin export endpoint: admin-authenticated job to materialize tenant+range export as ndjson to S3. (1 dev-week)
- Activation SLO: short-term priority routing by marking requests from tenant as high-priority and allocating from a warm pool for first 72h. This needs a small scheduler change and capacity reservation toggle. (2 dev-weeks infra/ops)

Conservative ETA: 6 weeks end-to-end if we can allocate a small eng pod and get product spec this week. Risk: the export store will add modest write load during peak; we should make the per-tenant opt-in to avoid global perf hit.
