Folks — drafted two sizing options below based on Peter's forecast and the requested guarantees. Assumptions: 1 H100 node = ~2.8x token throughput vs A100 for their Llama-derivative model with our optimized kernels; quantized FP4 path assumed for cost-forward variant. Sustained numbers include 48% p95 concurrency headroom for variance.

Option A — Conservative (sustained + 30% buffer):
- US: Sustained 600k/day -> ~8 H100 nodes reserved; Buffer: +3 nodes for burst/failure -> Total reserved US = 11 H100 nodes
- EU: Sustained 240k/day -> ~4 H100 nodes reserved; Buffer: +2 nodes -> Total reserved EU = 6 H100 nodes (all EU-local for residency)
- APAC: Sustained 90k/day -> ~2 H100 nodes reserved; APAC burst lane: +6 ephemeral H100 nodes (prioritized, billed separately) -> Total reserved APAC = 2 H100 nodes + burst policy (6 ephemeral)

Option B — Lean (sustained + 10% buffer):
- US: 9 H100 nodes (7 sustained + 2 buffer)
- EU: 5 H100 nodes (4 sustained + 1 buffer, EU-local)
- APAC: 3 H100 nodes (2 sustained + 1 buffer) + burst lane 4 ephemeral H100 nodes

Notes / tradeoffs:
- Cost delta between A/B ~ 22% monthly. Option A provides more headroom for marketing bursts without immediate overage.
- If Lumina accepts a mixed fleet (A100 for sustained + H100 for burst), we can reduce monthly cost ~12% but pay a latency penalty for persistent requests.
- For API-level SLOs, we recommend a canary + staged rollout with a 2-week monitoring period before firming SLOs in the SOW.
