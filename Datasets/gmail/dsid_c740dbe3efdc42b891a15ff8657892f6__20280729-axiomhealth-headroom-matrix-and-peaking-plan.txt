Quick technical sketch (draft):

Assumptions pulled from CSV: average tokens per request = 200 (prompt+completion), average tokens/sec per active session = 10–15 (typical interactive session bursts), baseline RPS 120 -> token/sec baseline ~24k t/s, peak burst RPS 1,100 -> peak token/sec 220k t/s.

Model choice: their accuracy requirements point to a 13B encoder-decoder variant we validated — runs at ~4.5k t/s on an A100-80G equiv with p95 ~300ms in our hosted profile when batching to 16 and with warmed KV cache. Using quantized int8 (LlamaQ-style) we can squeeze ~1.6x throughput with modest quality delta.

Sizing scenarios (high level):
1) Conservative commit (steady-state): target 30k t/s to cover baseline + modest growth -> requires ~7 A100-80G equivalents (7 x 4.5k = 31.5k t/s). Expected p95 ~280–330ms with batching tuned and caches enabled.
2) Commit + small burst lane: reserve 7 GPUs for steady-state + 3 GPUs as burst lane (pure preemptible dedicated or burst pool) -> burst headroom ~20k t/s additional (total ~51.5k t/s). This covers moderate spikes; p95 under burst depends on warm cache. Cold-start tail ~1.2–2.0s.
3) Commit + aggressive burst + prewarm cache: reserve 7 GPUs + 8 GPUs in burst lane + proactive KV prefix warming for top routes (20–30 minutes warm window) -> total ~7+8 = 15 GPUs -> ~67.5k t/s baseline+burst. To hit 220k t/s peak we'd need autoscale to add more ephemeral GPUs (additional 30–40 GPUs) — not feasible as pure reserved commitment.

Tradeoffs and mitigations:
- Prefill KV cache for the top 30% of queries reduces effective tokens/sec demand by ~20% for repeated prompts.
- Use a smaller model variant (7B quantized) as fallback for low-cost, high-concurrency routes; 7B can provide ~2.5x t/s per GPU vs 13B with lower latency but slightly lower quality. Recommend canary rollout of fallback mapping per route.
- Client-side rate shaping & queuing windows (30s backoff for bursty non-critical routes) reduces required headroom dramatically.

Ops notes: for minute-scale spikes we should combine a modest burst lane + active prewarming + fallbacks. If Axiom wants a strong SLA during spikes, they'd need a larger reserved commit or a contract that allows a predictable burst pool (monthly billed).

I'll assemble a simple headroom table (tokens/sec -> GPUs -> expected p95) and send back.
