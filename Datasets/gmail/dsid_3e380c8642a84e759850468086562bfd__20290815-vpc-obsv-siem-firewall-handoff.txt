Hi Asha — thanks for the clear constraints and the requirements doc. Looping our private-deploy and compliance leads (Kimberly, Jonas, Tessa) to own the technical handoff. Below is a concise plan and the artifacts we'll deliver as a starting point.

Executive plan (short):
- Pattern A (recommended): Customer-forwarder model
  - Redwood runtime pushes logs/metrics/traces over mTLS to a customer-managed forwarder (Splunk HEC / syslog). No external egress from customer VPC except to the forwarder endpoint inside the VPC.
  - Benefits: minimal network changes, encapsulated customer control, easier evidence collection.
- Pattern B (alternative): Collector pull via customer-managed pull-proxy (rare)
  - Customer exposes an authenticated, ephemeral HTTPS endpoint inside the VPC that our agent polls. This is used only when a forwarder cannot be installed.

Deliverables (we will attach as files and links):
- private-obsv-runbook-v1.md — runbook with step-by-step: DNS, certs/mTLS, port matrix, syslog/HEC example payloads, and rollout checklist.
- evidence-checklist.xlsx — SOC2-aligned checklist with sample logs to provide, retention statements, and masking guidance.
- port-and-protocol-matrix (inline below).

Minimal port+protocol summary (customer-managed collector inside VPC):
- Outbound from runtime pods/instances to collector IP/hostname: TCP 443 (HTTPS, mTLS) — REQUIRED
- Optional metrics aggregation (Prometheus remote_write): TCP 9091 (TLS) — CONFIGURABLE
- Syslog over TLS: TCP 6514 (if using syslog-ng endpoint) — OPTIONAL

Tracing guidance:
- Include request_id, route_id, model_version; strip any patient identifiers before sending.
- Sampling: default 1% for heavy inference workloads, configurable per route with local override.
- We will include a trace-hook test harness you can run in staging to validate headers and sampling behavior.
