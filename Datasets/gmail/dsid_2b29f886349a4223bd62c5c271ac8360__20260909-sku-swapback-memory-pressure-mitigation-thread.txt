Hannah / team — ran a quick sim using the attached sample and our perf profiles. Below is a condensed recommendation intended for procurement and ops. This is an internal technical recommendation but short enough to paste into an external note.

Summary recommendation (concise):
- Target pool: start with a 32-slot dedicated pool. Mix: 50% L4 (16 slots), 31% A100-40G (10 slots), 19% H100-80G (6 slots).
  - Rationale: L4 handles high-volume short chats at best cost-per-token with excellent P99 latency for short prompts. A100 provides a balance for medium-length flows and is significantly cheaper than H100 for mid-sized batches. H100 is reserved for long-context summarization and peak single-request throughput as it offers the memory headroom and higher throughput for long sequences.
- Memory and OOM mitigations: implement an active swapback policy:
  1) Prefix/KV caching: aggressively cache prefixes for short-chat flows on L4 to reduce compute.
  2) Elastic per-request slot escalation: if a request on L4 is predicted to exceed config memory threshold (based on sequence-length header), route to A100. If still beyond A100 headroom, route to H100.
  3) Soft-fail to truncated summary mode with explicit user-facing signal when even H100 would exceed configured max_seq (policy-controlled). This preserves availability over silent OOMs.
  4) Instrumented pre-flight checks (sequence-length histograms + OOM rate alert at >0.1% over 1h) and automatic swapback scaling priority for H100 pool.
- Canary and rollouts: 48–72 hour canary with 5% traffic on the new pool, synthetic load that mimics long-context tails, and a playbook that includes rollback to hosted fallback (compatible model) if latency or error-rate exceeds thresholds. Attached is a quick Ops checklist (canary-run-checklist.pdf).
- Cost estimate: starting monthly committed cost delta vs H100-only: ~-42% token-cost (mix-driven), expected 12–18% infra premium for maintaining three SKUs due to fragmentation. Exact numbers in redwood-sku-swapback-proposal.xlsx.
