Hi Taylor — thanks for the detail and the usage sheet. High level response below, attaching a short proposal (Redwood SLA Proposal v3) with banded pricing and an example surge-credit calculation.

Summary of options we recommend:
1) Performance Tiering
   - Standard: 99.9% uptime, 100ms median token latency SLA.
   - Premium: 99.99% uptime, 60ms median token latency SLA, prioritized scheduling during capacity contention.
2) Surge Credits (short windows)
   - For bounded peaks (<=72 hours) we offer a surge credit pool. Credits are consumed against peak tokens; if pool exhausted, excess billed at a capped premium rate (no surprise unlimited burst charges).
   - Example model in attached PDF shows credit allocation scaled to committed capacity and historical peak multiple.
3) Emergency On-call & Escalation
   - 24/7 on-call for Premium tier with 30-minute initial acknowledgement and 2-hour remediation window for infrastructure-impacting incidents.
   - Named on-call contact + escalation ladder (SE -> Ops -> VP Eng) included in contract.
4) Commitment Discounting
   - 12-month Dedicated commit: standard 10% off list for the SLA pack + increased surge-credit pool.
   - Multi-year (24+ months) or larger reserved GPU commits can be priced separately.

Assumptions (rounded):
- Baseline: 2,000,000 tokens/day -> ~60M tokens/month.
- Premium reserved capacity = commit sized for 2.5M tokens/day (headroom) -> monthly reserved tokens = 75M.
- Surge credit pool (Premium + 12mo commit) = 40M tokens/month (banked, can be used across spikes).

72-hour 6x spike in month 3:
- Actual tokens during spike: 2M/day * 6 * 3 days = 36M tokens in spike window (above baseline).
- Using reserved headroom: first 15M absorbed by reserved headroom (difference between 75M reserved and 60M baseline).
- Remaining 21M drawn from surge credit pool (40M) -> after event pool left = 19M.
- No excess billing in this scenario. If peak had been 9x, excess billing would kick in at a capped premium rate (example cap = 2.5x list token rate).
