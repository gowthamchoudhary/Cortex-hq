Quick triage notes (runtime inspection + logs Alex sent):
- Observed rapid growth of KV cache entries for model 'redwood-open-lite-v2' leading to OOM pressure on 2 of 6 GPUs in the cluster.
- Decoder queue backlog correlates with an increased number of long sequences from a new nightly batch job (looks like an indexing job from Seastone).
- Several 502s come from our decoder worker process hitting a soft failure when memory allocation fails during attention kernel selection.

Temporary mitigations I recommend (low-risk, reversible):
1) Set concurrency_per_gpu=2 for the affected node pool (current is 6) — immediate effect on mem pressure.
2) Reduce max_batch_tokens for that model to 256 (current 1024) and disable continuous batching for that tenant for 30 minutes.
3) Enable model-variant fallback to a smaller quantized variant (redwood-open-lite-v2-q4_0) for new requests only.
4) Apply a runtime patch to reduce prefetch window from 4->1 (JIRA-OPS-9876 created).

I'll prepare a small rollout that updates node config and switches fallback for new traffic. This should reduce 502s quickly; plan to monitor p95 and error-rate for 15m windows after each change.

Estimated time to implement: 20–35 minutes once we have customer approval for a brief maintenance window.
