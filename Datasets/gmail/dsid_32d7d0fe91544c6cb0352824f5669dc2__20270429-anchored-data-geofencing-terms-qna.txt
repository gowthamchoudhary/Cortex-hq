Carlos — quick operational summary from a solutions standpoint and proposed next steps: 

1) Region lock controls (what we configure):
   - Control plane enforces storage affinity by tenant ID. Storage volumes and object stores are created only in the selected region unless an admin enables replication.
   - Network egress is restricted by VPC routing and security groups (no managed-service egress to alternative regions).

2) Backups & snapshots:
   - Automated snapshots are stored in-region.
   - Optional cross-region replication is an explicit feature (documented and billable).

3) Deletion lifecycle (operational flow):
   - Step 1: Customer initiates tenant offboarding request (API + signed confirmation).
   - Step 2: System executes a logical wipe and revokes access keys; we capture snapshot metadata and mark snapshots for deletion.
   - Step 3: Within the agreed purge window we perform physical deletion of blobs and overwrite metadata tombstones.
   - Step 4: Redwood issues a signed purge attestation with timestamps and dataset identifiers.

4) Evidence we can provide for the contract:
   - Purge attestation PDF, snapshot IDs + hashes (for non-sensitive metadata), and an audit log extract showing deletion operations.

Carlos — adding the security specifics you asked for. Short answers first, followed by proof items we can include in the MSA/SOW.

- Key management: Customer-managed CMKs via the customer's KMS are supported for Private/VPC deployments. If you use your KMS/HSM, snapshots and stored objects are encrypted with keys that you control; Redwood never retains plaintext key material.
- Backups/snapshots replication: If cross-region replication is enabled, the replication path is logged, and we require explicit change control and approval from the customer's ops owner. By default replication is disabled.
- Logical vs physical deletion: Logical deletion marks objects and snapshots as tombstoned; physical deletion runs as a purging job that overwrites object storage blocks and removes metadata. For object stores that do not natively support immediate block overwrite, we provide an attestable purge sequence and confirmation of zeroed metadata entries.
- Evidence items we can provide for contract:
   1) Signed purge attestation (PDF) with list of dataset IDs and purge timestamps.
   2) Audit log extract (immutable stream) demonstrating the purge steps.
   3) Snapshot manifest (IDs + checksums) showing lifecycle state transitions.
   4) KMS key IDs used for encryption and a confirmation that keys were disabled/rotated per customer request.

Operational caveats to call out in SOW: if customer requests immediate physical byte-level overwrite in air-gapped on-prem configs we may require a brief maintenance window; cloud-provider object stores have eventual consistency semantics that affect instantaneous proof. We'll include precise timing commitments in the SOW.
