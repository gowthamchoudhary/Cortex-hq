Alex —

Thanks for the clear list. Below are concise answers and I'm attaching a tenant-to-site mapping PDF plus our tenant wipe checklist workbook. High level answers first; we can expand any point on a call.

1) Physical/site binding: FinWell's Dedicated tenant is pinned to the US-EAST site (site id: us-e-3). Primary runtime data (in-memory models/kv-caches) and ephemeral storage are only on nodes within that site. Persistent blobs (request logs, model cache artifacts) are archived to the same site by default. See attachment: redwood-dedicated-data-map.pdf for the cluster-to-dc mapping and rack-level boundaries.

2) Backups & snapshots: We take tenant-level snapshots every 24 hours. Snapshots are stored encrypted at rest in the same regional site by default. Cross-region replication is opt-in; we do not replicate FinWell snapshots outside US-EAST unless you enable geo-replication. Retention default is 30 days; we can customize per contract.

3) Deletion/wipe evidence: Tenant wipe includes: (a) live data eviction from nodes, (b) deletion of tenant metadata and indexes, (c) overwrite of KV cache markers, and (d) removal of snapshots. We produce a time-stamped audit bundle (signed event log + deletion manifest) that includes per-step checksums. SLA: full wipe completion target is 72 hours for the standard wipe (includes snapshots). For expedited erasure (legal order), we run an accelerated pipeline and aim for 24 hours.

4) Logical isolation: No tenant-shared persistent volumes are used for FinWell. There is a small amount of global, aggregated telemetry (rollup metrics) that is scrubbed of tenant identifiers. Customer-identifiable logs remain tenant-scoped. We can provide a telemetry scrub policy excerpt.

5) Emergency/incident: For legal hold / forensic freeze, submit requests to ops-security@redwood.ai and we will: suspend scheduled deletions, snapshot the current state (retention trap), and assign an incident lead. Escalation contacts: Dev Patel (dev.patel@redwood.ai) and Marissa Cole (marissa.cole@redwood.ai).

Attachments: redwood-dedicated-data-map.pdf, tenant-wipe-checklist.xlsx

Hi Alex — quick technical clarifications to back Sofia's answers and give you the artifacts you'll need for audit:

- Snapshot architecture: snapshots are filesystem-level, created from a consistent point-in-time on the tenant's logical volume. Snapshots are encrypted with a tenant-specific data key derived from your tenant id and a KMS root. The manifest includes the KMS key id, snapshot GUID, and SHA256 checksums for each object.

- Storage location & replication: default writes and snapshot storage remain in us-e-3. If you choose cross-region replication we create a second encrypted copy under a separate KMS envelope in the target region; replication is disabled by default for FinWell.

- Proof-of-deletion artifact: when a wipe completes we emit a signed deletion-manifest JSON (we included a sample in the drive link). The manifest contains: wipe_start/finish timestamps, snapshot GUIDs removed, list of affected object GUIDs and SHA256, node eviction records, and the operator run id. The manifest is signed by our platform signing key (x509) and stored in the customer's audit bucket for 90 days.

- Backup retention on S3-compatible store: s3 lifecycle rules are tenant-scoped and operate inside the regional tenant bucket. Cross-tenant keys are never used.

Operational notes:
- If you request a legal-hold we pause the lifecycle expiration for affected snapshots and tag them legal-hold-<req-id>.
- For full cryptographic proof we can provide the signed manifest and a PKI chain.

Let me know if you want a short demo of the manifest verification process.
