Thanks again for the renewal conversation last week. I pulled a short usage snapshot for Pulse Analytics and wanted to propose a lightweight amendment that automatically tops up Dedicated GPU capacity when 7-day sustained utilization breaches a configurable threshold. The intent is to avoid sudden latency impacts during recurring spikes while keeping your committed spend aligned with steady-state usage.

Key ideas (high level):
- Trigger: 7-day rolling average GPU utilization > 70% for two consecutive days
- Action: Add a small fixed slab (e.g., 8 A100-equivalent GPUs) for up to 14 days to relieve pressure, then re-evaluate
- Limits: Annual cap on auto-topups and an opt-out window so Pulse retains control
- Billing: prorated on reserved capacity plus a small transient surcharge while the slab is active

Sara —

Great questions. Quick answers below, and Ben/Karthik added detail where relevant.

1) Per-pool thresholds: Yes. The amendment language supports pool-level thresholds. By default we propose a conservative global threshold (70%), but we can set per-pool triggers for inference (e.g., 65%), batch (80%), ingest (75%).

2) Slab selection: The runtime will provision a slab matching the dominant model profile for the pool. For mixed-memory pools we recommend an ensemble slab (mix of higher-memory instances) — Karthik flagged an algorithm that picks the minimal set of capacity that meets >90% of recent allocation needs. Implementation note: this is non-disruptive to pinned instances.

3) Alerts & audit trail: Yes. When a top-up triggers Pulse receives: (a) an alert email, (b) a one-click opt-out in the Console, and (c) an auditable event with timestamps and cost impact in your account activity log. DocuSign-friendly amendment will include explicit opt-out SLA and notification timing.

Sara, David —

Short answer on surcharge: for short-lived slabs (<=14 days) we propose a 10-18% transient premium on top of the pro-rated reserved rate to cover burst provisioning and preemption risk. Exact band depends on slab size and region. Example: an 8-GPU A100-equivalent slab in us-west would be +12% for up to 14 days.

Operational notes:
- Slab sizing algorithm favors memory headroom first; for mixed pools it will provision an 8-GPU slab with two high-memory instances and six standard if >60% of recent allocations need the larger memory footprint.
- We expose the trigger and the opt-out toggle in the Console; customers get an event with timestamps and estimated cost impact before charges finalize.
