Tom/Kim — I dug into the logs you attached (thanks). Summary of findings:

- Root cause: In ~82% of the failed samples the runtime's content-safety filter triggered during the model's tool-calling step. When that happens our current behavior is to replace the tool-call structured payload with a short human-readable explanation ("Tool call suppressed due to content policy") instead of the expected JSON blob.
- Why: This behavior is by design to avoid returning policy-violating artifacts. It prevents unsafe content from being included in downstream tool invocations, but it also means the structured output shape changes and many client parsers cannot handle it.
- Impact: Based on BlueAnchor's traffic patterns in the sample, the effective functional failure rate is ~0.07% of requests but concentrated on longer sequences and certain claim categories.

Options: 
A) Short-term: enable a guarded retry path for BlueAnchor where suppressed tool-calls trigger an automated second attempt with a more conservative safety profile (risk: potential exposure to borderline content — requires customer opt-in and monitoring).
B) Medium-term: add an explicit structured-output fallback envelope that preserves JSON schema while flagging the filtered fields (this would be backward-compatible but needs ~2-3 weeks dev work).
C) Contractual: we can define a narrow SLA addendum that treats filter-induced structured-output transformation as a carve-out from standard uptime/JSON-delivery guarantees, with a capped credit formula tied to occurrence rate.

I'll prepare wording for the addendum and a technical mitigation plan. If BlueAnchor wants to run A temporarily I can enable it and add monitoring.
