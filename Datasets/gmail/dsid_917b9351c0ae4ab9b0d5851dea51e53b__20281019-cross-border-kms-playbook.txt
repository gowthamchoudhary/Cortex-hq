Thanks for the summary, Nikhil. A few practical notes from an ops/networking perspective:

- Network egress: if we keep a single control-plane (hosted) and customer data in regionally isolated worker clusters, we must ensure worker-to-control TLS sessions never include key material and that control-plane telemetry avoids sensitive payloads. That is doable but requires per-region egress ACLs and mask policies.
- Routing/failover: automated cross-region failover that moves compute from EU->APAC during an outage will require either (A) re-provisioning the EU key in APAC (not allowed), (B) a pre-shared emergency key escrow that is also EU-resident (legal review), or (C) an application-level degraded mode where cached tokens allow short-lived reads until manual recovery.
- Proposal: for Acme I'd recommend an islanded dual-deployment with a warm-standby in APAC. Warm-standby uses encrypted snapshot replication (SSE-KMS), and we document clear RTO/RPO and manual steps to rehydrate keys within EU boundaries.

I've attached a routing matrix that maps interconnect options and latency trade-offs (vpc-routing-matrix.csv). If legal says escrow is acceptable we can reduce recovery time, but that is a contractual ask.

On timelines: PoC to validate replication + manual failover steps = 3 weeks (infra + security sign-off).

Sarah — thanks, that's clear and appreciated. Based on the constraints, here is a recommended path (technical + program):

Option A (recommended for compliance with minimal customer overhead):
- Two separate private deployments: EU primary, APAC warm-standby cluster.
- KMS: Customer-managed KMS keys in EU for the EU cluster (either Acme's KMS or Redwood-managed but EU-resident with HSM). No key export.
- Replication: Encrypted snapshots (SSE-KMS) pushed to a secure S3 bucket. Snapshots are encrypted with the EU KMS key. APAC warm-standby stores snapshots but cannot decrypt without a legal-approved procedure.
- Failover: Manual, documented handover. Steps include legal sign-off, key-reprovisioning (if using customer KMS token exchange) or activation of pre-authorized EU-held escrow (if both sides agree).

Operational timeline (PoC):
- Week 0: Confirm KMS approach & sign T&Cs for escrow if used.
- Week 1–2: Stand up EU private cluster + configure encrypted snapshot replication.
- Week 3: Stand up APAC warm-standby and run restore dry-runs under controlled conditions. Execute acceptance tests.

Cost note: warm-standby implies reserved capacity on APAC side for faster recovery. We can publish a minimal configuration estimate after we confirm required throughput and RTO targets.
