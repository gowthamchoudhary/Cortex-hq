Thanks for the traces — I ran a quick pass. Preliminary findings: the canary variant activates a quantization path that increases memory pressure on the KV cache under certain request size distributions. That triggers slightly longer GC cycles on the serving nodes, causing the observed tail latency and transient 502s during peak concurrent requests.

Mitigation options (short term):
- Automatic fallback to the previous quantized variant (v1.7-quant) for this route — preserves latest model improvements but uses a safer runtime path.
- Hard pin the route to v1.7 (non-quantized) until we deploy a perf fix.

I support a temporary pin while we debug, with these guardrails:
1) Pin allowed for up to 48 hours or until we ship a targeted perf patch (whichever is sooner).
2) Disable traffic bursts above current baseline for the affected route (traffic cap).
