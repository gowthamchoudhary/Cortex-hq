Thanks Sofia — adding a few technical clarifications for Alex & Priya:

Operational checklist highlights (technical):
- Egress IPs: please confirm the static egress CIDRs for allowlisting. We cannot accept ephemeral egress ranges.
- Peering: if using VPC peering, provide route tables and expected ASN for BGP (if applicable). For transit or IGW-based designs, outline NAT behavior.
- Ports & ports policy:  
  - Control plane: 443 (outbound to redwood-control.redwood.ai), 22 restricted for bastion-day0 only.
  - Model serving: 7000-7099 (internal), TLS required.
- KMS: Provide key ARNs and key rotation cadence. For HSM-backed keys, include proof of HSM tenancy and a contact for KMS admin.
- Logs & retention: we require an audit log export location or a push mechanism; default retention must be at least 90 days for initial acceptance.

Deliverables checklist (what we'll expect from EdgeHealth):
- Completed network-evidence-template.pdf
- Signed credentialing matrix (tab 2 of XLSX) with at least one technical and one security approver.
- KMS info and access admin contact.
- Confirmation of maintenance window for Day-0 smoke (2 hour window).

If EdgeHealth wants, we can run an automated validation script against the supplied CIDRs prior to Day-0 to pre-flag any routing issues — I can scope that once we get the filled template.
