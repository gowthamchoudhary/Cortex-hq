I broke it into discrete phases with recommended "safe defaults" (so procurement has numbers) and the telemetry checks we'll use during canary and rollout.

Phase 0 — Kickoff / Data collection (1–3 days)
- Kickoff call: align on success metrics (latency p50/p95, cost / 1k tokens, error budget).
- Collect representative traces (you already shared staging traces — perfect). Also request 48h of production-like requests if possible.
- Deliverable: baseline perf report (latency, token counts, sequence length distribution).

Phase 1 — Baseline & profiling (2–4 days)
- Run baseline on your preferred model variant (fp16 / fp32) to establish current latency/cost.
- Generate per-sequence latency distribution and memory/KV cache hit patterns.
- Deliverable: perf profile + recommended quantization candidates.

Phase 2 — Quantization experiments (3–7 days, iterative)
- Safe default (procurement): assume FP16 runtime, per-token cost estimate based on q4_0-like quantization gains (conservative) — estimate: $0.22 / 1k tokens without caching; with realistic caching expect to get near your $0.15 target.
- Stepwise plan: test q4 variants first (balance quality/latency) then aggressive int8-like configs if quality is acceptable on your eval prompts. For each profile we’ll capture ROUGE/EMB similarity and latency & memory footprint.
- Canary approach: A/B split 95/5 for 48–72 hours; if quality regression < threshold and latency/cost improvements as expected, expand to 25% then 100% with staged rollback conditions.

Phase 3 — Batching & dynamic batching (2–5 days)
- Default for initial rollout: dynamic batching with max batch size = 8 and per-request latency cap = 200ms to keep p95 under target.
- We’ll tune batching window (5–15ms) based on your QPS and observed token lengths. If bursts occur, autoscale + temporary larger batching for throughput-intensive paths.

Phase 4 — Caching strategy (1–3 days)
- Safe default TTL: 30s for prefix caching on identical start-of-conversation prompts; evaluate per-route TTLs based on hit-rate.
- Implement prefix/KV caching plus a small LRU for repeated short prompts — should reduce token consumption and push effective cost closer to your $0.15 target.

Phase 5 — Routing policy & rollout (ongoing)
- Routing: latency-sensitive routes -> low-latency pool (higher unit cost), background or thrift routes -> cost-optimized pool (quantized, batched).
- Fallbacks: automatic fallback to fp16 / lower-quant model in case of quality regressions or sudden latency spikes.

Observability & guardrails (continuous)
- Dashboards: per-route p50/p95, token usage, cost per 1k tokens, model quality metrics on eval prompts, cache hit rate.
- Alerts: p95 > 300ms for 15min, quality regression > threshold, cost per 1k > budget for 1 hour.
- Canary rollback policy: immediate rollback on quality regression or sustained error rate increase >1% over baseline during canary window.

Deliverables: onboarding checklist (attached: redwood-onboard-checklist.pdf), perf baseline report, quantization A/B logs, and a canary runbook.
