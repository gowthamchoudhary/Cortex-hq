Rachel — notes below and attached artifacts. I kept answers short so you can paste into the questionnaire.

Supported HSMs/Models
- Redwood-managed: AWS CloudHSM (cluster-based), Azure Dedicated HSM (Thales Luna equivalent in marketplace), and Yubico Luna in our Dedicated appliance program.
- Customer-managed: we have validated integrations with AWS CloudHSM, Google Cloud External HSM and Thales Luna networks — customers can bring their own HSM/VPC endpoint.

BYOK flows
- Import (Customer-supplied key material): We support an import API where the customer generates key material locally, wraps it with a Redwood public-wrapping key, and uploads a wrapped key. The unwrapped material never leaves the customer's environment.
- Wrap-only (Customer-managed master key): For customers preferring not to import raw key material, Redwood supports a wrap-only flow: we generate a data key in our KMS, and the customer provides a master-wrapping key (managed in their HSM) to wrap/un-wrap data keys on demand via API calls.
- Escrow: Redwood does not escrow customer private key material for BYOK imports. We retain metadata (key IDs, rotation schedule), not raw material.

Rotation automation and rollbacks
- Service keys: automatic rotation by default every 90 days; configurable to 30–365 days for Hosted customers.
- Customer-managed BYOK: rotation must be initiated by the customer in their key-store; Redwood supports a rotate API that triggers re-wrapping and a rolling deploy across nodes.
- Minimum rotation window: 24 hours between key creation and scheduled rotation for operational safety.
- Rollback: supported for service keys within a 72-hour window via roll-forward/rollback mechanism; rollbacks for customer-supplied keys require the customer to re-import previous key material (we provide instructions and a rollback endpoint but cannot re-create customer private material).
- KV-cache invalidation: rotation triggers prefix-based KV cache eviction; we support zero-downtime draining with a short dual-signing window (configurable, default 15 minutes).

Dual-control / split knowledge
- We offer multi-actor approval flows for exporting key-wrapping credentials and for any bulk export operations. Export requires two distinct admin approvals (RBAC + audit trail).

TLS / cipher support
- Supported: TLS 1.2 and TLS 1.3 (TLS 1.3 preferred).
- Recommended production posture: TLS 1.3 only where client stacks allow.
- Cipher list (attached tls-cipherlist-2026.txt) — includes AEAD suites only; weak legacy ciphers disabled by default.
- FIPS mode: We can run FIPS-validated TLS stacks in Private deployments; Redwood-hosted FIPS options are available for Dedicated customers with appropriate contractual terms.
