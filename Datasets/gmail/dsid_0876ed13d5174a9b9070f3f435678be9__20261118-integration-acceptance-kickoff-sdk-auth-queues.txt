2) Routing & concurrency strategy:
- Route by endpoint: /v1/generate for generator, /v1/embeddings, /v1/rerank. Each route gets a separate logical queue.
- Concurrency: start pilots with per-instance concurrency 8 for generator, 16 for embeddings worker (vectorization is cheaper), 6 for heavy reranker models — these are conservative; we can tune after a day of traffic.
- Queueing: use two-tier queues: steady (guaranteed capacity) + burst (best-effort). Bursts are rate-limited by overall pool headroom.

3) Autoscale & throughput sizing:
- Proposed Dedicated pool: 4 x A100-class GPUs (NVIDIA A100 or comparable) initially. Expect baseline throughput roughly 4500 generator tokens/s across the pool; embeddings throughput ~9k vectors/hr.
- Autoscale policy: scale up at sustained CPU/GPU utilization > 70% for 5 minutes; scale down after 15m at < 40%.
- We’ll provide a runbook to simulate load and verify p95 latency.

4) Structured output / tool-calling:
- We’ll return a canonical tool invocation envelope: {tool_name, args, metadata}. SDK will surface a helper to execute tool calls and return resolved results.
- Retries: idempotent tool calls will be retried once with exponential backoff; non-idempotent calls will return an explicit error.
