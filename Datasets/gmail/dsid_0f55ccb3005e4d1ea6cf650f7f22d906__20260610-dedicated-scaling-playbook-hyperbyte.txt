Hi all — digging into the projections. I attached a quick capacity plan (capacity_plan_v1.xlsx) with three profiles: conservative, recommended, and aggressive. Notes below are the recommended (middle) profile and the operational knobs we’d use.

Recommended profile (middle):
- Base pool: 4 x A100-80GB equiv (handles baseline 30 concurrent sessions with batching).
- Burst pool: +6 x A100-80GB equiv, pre-warmed; warm-up time ~8–12 minutes if nodes are cold, so pre-warming is required for Demo Day.
- Autoscale: scale-up threshold = 70% GPU utilization, scale-down threshold = 40% utilization. Cooldown: scale-up = 60s, scale-down = 600s (10m).
- Warm cache policy: keep KV cache warm for top 25% of active users to reduce token recomputation during bursts.
- Batching: dynamic batching with max batch size tuned to latency SLO (target p95 < 400ms for interactive flows).
- Fallbacks: route low-priority traffic to quantized model variant to preserve core capacity.

Cost and billing model:
- Burst-as-add-on: supported; we can define a capped burst budget for a window (e.g., 3 hours at N nodes) with a per-hour overage rate.
- If procurement prefers predictable costs, we can offer a short-term reserved top-up (e.g., 3-month add-on) at a reduced hourly rate.

Operational checklist for Demo Day (what we need from HyperByte):
1) Confirm exact start window and expected concurrent sessions by 48h prior.
2) Approve pre-warm time and confirm whether we can pre-warm within your network constraints.
3) Approve a capped burst spend and fallback routing policy.
