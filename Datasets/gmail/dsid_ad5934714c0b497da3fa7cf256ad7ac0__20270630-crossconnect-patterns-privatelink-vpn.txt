Logan / team —

Thanks for the details (and Alice for the site summary). Given the constraints (cannot renumber, moderate throughput with 500 Mbps peaks, existing Direct Connect available) here are succinct tradeoffs and a recommended pattern.

Summary tradeoffs (short):
- VPC Peering:
  Pros: low-latency, simple routing, no extra proxies.
  Cons: cannot work if address spaces overlap without NAT; peering is non-transitive (adds complexity for multi-account topologies); cross-region peering has limitations and potential egress charges.

- AWS PrivateLink (Endpoint Service):
  Pros: preserves customer IP addressing (no route table changes on their side), provides per-service access controls, traffic stays on AWS network, reduces blast radius to service-level, easy for security to reason about.
  Cons: ENI costs + per-GB data processing fees; doesn’t provide full L3 network adjacency so some use-cases (e.g., shared KVs or internal console access) may need extra work.

- Site-to-site VPN (IPSec tunnels) + Transit Gateway or TGW attachments:
  Pros: works with NAT when addresses overlap, lower up-front cost, flexible.
  Cons: higher latency/variable throughput vs Direct Connect, throughput limits on software VPN endpoints unless you provision appliances or AWS-managed VPNs with HA; operational overhead.

Recommended patterns for StellarPay: 
1) Preferred (Production target): Activate the existing Direct Connect, attach to a Transit Gateway in us-west-2, and expose Redwood's inference endpoints via PrivateLink for the control/API plane. Rationale: satisfies compliance (no public internet), supports high throughput, and avoids renumbering. PrivateLink limits exposure and makes access control easier.

2) Pilot (fast path / cost-conscious): Start with Site-to-site VPN with NAT for the pilot (works with overlapping IPs). Use a Transit Gateway to centralize routing and plan a migration runbook to move to Direct Connect+PrivateLink once budget/approval is in place.
