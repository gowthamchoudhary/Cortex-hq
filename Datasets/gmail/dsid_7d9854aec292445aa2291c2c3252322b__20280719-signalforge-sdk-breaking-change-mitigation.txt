Tessa,

Quick technical take after a rapid review:
- The adapter layer we ship for partners sits in our ingress path as a lightweight translation filter (not on the GPU runtime). Translating the auth header and re-mapping the endpoint path is straightforward from a code-change perspective.
- Perf: for our p50 tokenized requests the latency delta is negligible (~3-6ms) if we keep the shim minimal (no heavy crypto). If we implement token exchange flows we would expect higher delta.
- Stability: adding a feature-flagged shim behind the routing layer is the lowest-risk approach. We can gate by customer, account, or HubSpot deal id.

Constraints / asks from infra/runtime:
1) Sandbox credentials + sample signed requests (so we can create fixtures).
2) Compatibility matrix (list of affected endpoints + auth variants) — the CSV Elena sent is a good start but we need request/response examples.
3) Clear rollback signal (error rates, 5xx threshold + latency SLA breach) — we will supply a minimal SLO template for the canary.

If SignalForge is comfortable with a 6-month compatibility shim behind a feature flag, we can schedule the shim for staging in 10 business days and a production dark canary in 3 weeks. If they insist on 90-day deprecation without a shim, we’ll likely have to prioritize which tenants to migrate first (based on usage telemetry).

I will sketch a minimal shim implementation plan and share it in the RFC.
