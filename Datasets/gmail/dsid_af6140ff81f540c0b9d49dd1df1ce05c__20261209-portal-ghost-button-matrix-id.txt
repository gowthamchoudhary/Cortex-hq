Hi all — I dug into the HAR and server traces. Summary + immediate mitigation below.

TL;DR: The request flow shows a tenant binding step that validates matrix_id against a transient routing table. When the matrix_id returned by the upstream redirect doesn't match the tenant mapping we render a lightweight client-side overlay (intended as a telemetry gate) that can intercept the final click handler — effectively swallowing the accept action and leaving a blank fragment in the response body. This explains the 302 -> 200 HTML fragment.

What I checked:
- Server logs (accept endpoint): we issued redirect 302 to /accept/complete?matrix_id=HL-52c7b, downstream proxy returned a 200 with a small html snippet ("<div data-gating>") where the client overlay is injected.
- Console trace in the HAR shows an XHR to /_telemetry/check?matrix_id=HL-52c7b returning "mismatch".
- We reproduced locally by forcing a matrix_id mismatch.

Immediate mitigation (fast):
1) I can generate a one-time accept token for Harbor Logistics. Use: https://supplier.redwood.com/accept_token?token=OT-9f2b7c (expires in 4 hours). That bypasses the matrix_id gating and completes the acceptance flow.
2) As a temporary server-side patch I can disable the client overlay for requests from the affected redirector host; I can push this to staging and prod within 2 hours if we approve.

Permanent fix plan:
- INF-8721 created to make gating resilient: validate on server and render deterministic redirect instead of client overlay; deliver in next sprint (ETA 2 weeks). I've assigned to the onboarding team and included a regression test.
