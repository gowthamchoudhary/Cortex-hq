Thanks for the tag, Rachel — quick triage from Integrations/Runtime.

What I see from the logs (we pulled the request trace for Liam's invite id) is a rejected POST to /portal/consent returning 403 with message: "invalid origin". The flow is doing an external redirect from our SAML callback domain (sso.redwood.com) back to the tenant portal (wscc.redwood-portal.com). In several browsers the Referer header is being stripped during the cross-site redirect and our CSRF check (we rely on Referer + token) is rejecting the request. This looks like a SameSite cookie + redirect boundary problem rather than a user error.

Workarounds (ranked):
1) Generate a one-time "sso-less" onboarding link (token in query) that skips the SAML redirect and lands directly on the tenant portal with a valid session cookie set server-side. This bypasses the Referer check.
2) Ask the vendor to use an incognito/private window and retry the original invite (sometimes old cross-site cookies interfere).
3) Reissue invite from legacy flow (Marissa) which attaches an explicit token in the path (not via redirect).

I can produce option (1) now. Creating a small support ticket INF-3421 to track the root cause — we should update the portal to accept stricter Origin-less POSTs from the SAML callback or switch to double-submit cookie CSRF to be resilient to redirect stripping.

I attached the trimmed trace showing the failing headers. If Ops generates the direct invite, I'll watch the trace in real time.
