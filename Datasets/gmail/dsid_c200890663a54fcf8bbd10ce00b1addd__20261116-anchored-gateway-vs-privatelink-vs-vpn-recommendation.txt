Thanks Rishi — quick notes below. I kept it high-level so we can hand it to EdgeHealth netops.

Summary recommendation (short):
- Primary: AWS PrivateLink (interface VPC endpoints) from EdgeHealth VPCs into our RedCloud service endpoints.
- Fallback / DR: S2S VPN between EdgeHealth and their on-prem DC for batch/fallback traffic.
- Avoid: cross-account VPC peering as the long-term primary for this use case (we can support it as a short-term pilot).

Why PrivateLink as primary (pros):
- Strong isolation: no routable cross-account routes — customer keeps control of their IP space and allows only interface endpoints.
- Easier to meet SOC2 allowlisting/audit requirements: VPC endpoint IDs and endpoint policies are scannable and auditable.
- Predictable Egress posture for customer — less firewall churn vs peering.
- We can present a per-connection bandwidth estimate and token-level cost projection tied to their throughput.

Tradeoffs / cons for PrivateLink:
- Slightly higher per-GB cost vs peering in some regions.
- Potentially more complex cross-region setups (we'll need regional endpoints or multi-region interconnect).
- Endpoint scaling must be considered; recommend autoscale rules on our side and a small initial throughput cap.

Why not Peering as primary:
- Peering requires route management across accounts which increases blast radius and operational coupling.
- Peering exposes whole CIDR ranges unless we do very tight routing, which customers are wary of for regulated data.
- Troubleshooting cross-account route issues is often slower and more error-prone in customer orgs.

When to use S2S VPN:
- Short-term proof-of-concept when customer cannot create PrivateLink endpoints immediately (e.g., policy requirements).
- Disaster recovery / fall back for intermittent bulk jobs where latency is less critical.

Operational checklist (brief):
1) Confirm VPC CIDRs and restricted subnets for endpoint placement.
2) Share endpoint policy template and example SG rules with customer.
3) Pilot in us-west-2 with one API route and a 1TB/month throughput cap.
4) Define monitoring: token-level latency, endpoint error rates, and bytes transferred per endpoint.
5) Run an intra-week latency test run (we'll use the attached benchmarks as baseline).

Notes on latency: our microbenchmarks show PrivateLink adds ~3–8ms median compared to internal peering on the same region; still within customer SLA target for typical inference sizes. See latency-benchmarks.csv for the sample matrix.

Sarah — thanks, answering inline and proposing next steps.

1) Interface endpoint creation / cross-account roles:
- You can create interface endpoints purely via your console using our service name (no cross-account IAM role required). We'll provide the service name and an endpoint policy you can paste into the console. If you prefer automation, we can share a CloudFormation module that your cloud team can run under their account.

2) mTLS and PrivateLink:
- PrivateLink is purely a network transport; it does not terminate or bypass app-layer auth. Your API gateway will still see the original TLS connection. We recommend retaining mTLS at the gateway edge. On our side we'll validate inbound certificates at the application layer (mutual auth) or accept token-based auth depending on the route.

3) Sizing VPN for DR/bursts:
- For active inference bursts, aim for at least 200 Mbps per 50 concurrent calls (rough heuristic). For larger models or batch re-ranking, bump to 500 Mbps. We'll run a small traffic profile during pilot to refine numbers.
