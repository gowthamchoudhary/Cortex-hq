Elena — thanks for the quick review and the CAB notes. Really helpful. I pulled together concise answers below and attached an updated runbook that includes an explicit role matrix and a SAML attribute map. High level:

- IAM roles (operator flows):
  * redwood-priv-operator-readonly: read-only on control plane resources (list/get for connectors, service-accounts, and audit logs).
  * redwood-priv-operator-describe: describe and list rights plus token creation permissions limited to scoped operator service accounts.
  * redwood-priv-operator-admin: ability to create/update operator-related service accounts, rotate certs, and manage the Redwood agent deployment objects.

  We documented the minimal API calls allowed for each role in the attached runbook (see appendix B).

- SAML attributes: required: email, name, subject (NameID). Optional but recommended: groups, email_verified, uid. We do not require edupersonPrincipalName; if you prefer it we can accept it but won't depend on it.

- SCIM behavior: by default our SCIM provisioning only manages membership for existing groups (we don't auto-create top-level groups unless the customer opts-in). We included a toggle and migration path in the runbook so teams can enable group creation during a staged rollout.

- Certificate rotation: our recommended standard is a zero-downtime rolling rotation; operator-admin role is used to push new certs and update the agent config one host at a time. We document an expected 2–4 minute failover per agent during heavy load as the agent restarts and re-establishes TLS to the control plane.

Elena — quick technical notes to supplement Marissa's summary:  

- Role-to-API mapping: we included exact GCP/AWS/Azure IAM actions for each logical role in appendix B. For customers who run on-prem with our agent, the "operator-admin" is implemented as a scoped service account with short-lived tokens minted via the control plane — we never embed long-lived keys in the agent.

- SAML attributes: our SAML consumer accepts groups as a multi-valued attribute (array) and maps to SCIM group membership. If Acme's IdP emits groups as URI-encoded strings we have a normalizer step in the sync process; I'll add a short note in the runbook about common encodings.

- SCIM provisioning: to be extra clear — group creation can be enabled, but if enabled we create groups with prefix "rw-" and the runbook contains a reconciliation plan to de-duplicate pre-existing groups. This avoids accidental collisions.

- Cert rotation: the control plane supports an overlap window where both old and new certificates are accepted for 24 hours. Agents attempt TLS handshake with the new cert first and fallback to old, so you can stage rotation without service interruption. The 2–4 minute per-agent blip Marissa mentioned is a worst-case during heavy GC on the host.
