Naomi — technical reply below, copied Priyom for orchestration notes.

Short answer: yes, we can support the behavior Jordan described. Details and caveats:

1) Auto-revert triggers and timing
   - Triggers: p50 latency delta >25% over a rolling 10-minute baseline OR request error rate >0.8% sustained for 5 minutes.
   - When a trigger fires we will:
     a) immediately divert new traffic for the canary cohort away from the new variant (instant).
     b) gracefully let in-flight requests finish (max tail up to 2s per request depending on model).
     c) re-route the cohort to the pinned previous model binary.
   - Expected visible impact: <30s for new requests to start hitting the pinned version; worst-case additional tail latencies during the in-flight window.

2) Pinning semantics
   - We can pin a customer-token to the prior model variant for a configurable window (default 48 hours).
   - Pinning is per-API-key + session cookie; it does not reserve GPU capacity — load will continue to be multiplexed across shared pools. If Acme has a Dedicated pool, pinning guarantees the variant is available without cross-tenant interference.

3) Observability exposed to Acme
   - We'll provide a read-only dashboard URL showing canary vs baseline p50/p95, error rate, throughput.
   - We'll also surface the rollback event (who/what triggered it), affected cohort size, and which variant was pinned.

4) Edge cases / risks
   - If a pinned variant is subsequently deprecated for security reasons, we will require an emergency plan; this should be spelled out in the SLA addendum.
   - Network partitions between regions can delay rollout/revert propagation; we'll document expected propagation windows per region.
