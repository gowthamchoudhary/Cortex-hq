Jordan / team — I ran a quick footprint calc with conservative KV cache assumptions. Key assumptions up front:
- Model: gen-70k-v1 (architecture similar to LLaMA derivative), baseline FP16 weights ~60GB.
- KV cache: 2 bytes per token (compressed) for quantized KV-friendly runtimes; full uncompressed ~8 bytes/token for older paths. We should assume 4 bytes/token midline.
- Active context: 70k tokens for long path; 8k tokens for fast path.
- Concurrency mix: peak concurrency for long jobs ~8 concurrent long sessions; short path concurrency up to 120 qps burst, average 30 qps.

Memory per replica (rough):
- Full FP16 weights: 60GB weights + 70k * 4 bytes KV ~0.28GB + activation overhead and CUDA workspace => plan 68–72GB total -> fits on 80GB GPU (A100/H100 class) but leaves minimal headroom.
- BF16/FP16 with 8-bit quantized weights (per-layer 8-bit): effective weights ~15–18GB + KV 0.28GB + workspace => ~18.5–22GB. This maps well to 40GB GPUs when combined with memory partitioning.
- 4-bit/QLoRA-like packing (aggressive): weights ~9–11GB + KV 0.28GB + extra CPU-side decode => ~12–14GB. Good fit for 24–32GB GPUs for the fast path but long path may need careful KV offload/prefix-caching.

Throughput & GPU counts (very approximate for committed pool sized to 1M tokens/month):
- Traffic breakdown assumptions: 10k short QPS-month equivalents vs 400 long-job-days (each long job ~80k tokens).
- Token-month calculation: short path dominates QPS but tokens are small; long path accounts for ~32M tokens/month under naive calc — that exceeds 1M target. To match their 1M token budget we should work with their estimate: assume long jobs are sampled (400 long requests/day * 80k tokens = 32M/month). If they only want 1M committed tokens, we size for baseline throughput and provide burst capacity for long runs (metered).

Concrete commit recommendation to align with 1M token reserved:
- Reserve 4x 40GB GPUs (quantized 8-bit variant) as the committed pool. Rationale: 40GB cards hold quantized weights + KV for medium-length contexts, support autoscaling to burst nodes. This gives nominal sustained throughput for short path and a cost-efficient base.
- Long 70k context jobs should be routed to on-demand high-memory hosts (80GB+) and billed as overage or moved to a separate dedicated long-job pool.
- If Genomix wants long-run inclusion in commit, propose an add-on: 1–2x 80GB reserved GPUs (H100) for long path.

Numbers:
- 4x 40GB (committed): handles baseline short-path qps and limited batching for medium contexts; estimated steady-state token throughput ~10–20M tokens/month depending on batching (this overshoots their 1M target but allows headroom for QPS).
- 1x 80GB on-demand (recommended for long jobs) or 1x 80GB reserved for an add-on if they want fixed SLA.

Adding performance & tradeoffs:
- 8-bit (symmetric/asymmetric) is our sweet spot for cost vs latency for most customers. For Genomix, 8-bit yields ~60–70% weight memory reduction and minimal latency regression on our optimized kernels. We recommend 8-bit as default for the committed 40GB pool.
- 4-bit gets you another ~40% reduction but comes with variable kernel support and ~20–40% CPU-side overhead on batching/formatting. For long 70k contexts, 4-bit + KV offload to CPU might still be required and will increase tail latency. Good as a non-critical background path.
- KV caching strategy: recommend a shared prefix cache for common reference segments (saves ~50–70% of KV memory for repeated runs). If Genomix can identify stable prefixes, we can reduce KV footprint on the long path significantly.

Latency notes for committed pool (estimated p95):
- Short path (8k context) on 40GB quantized 8-bit replica: p95 ~120–180ms with batching.
- Long path (70k) on 80GB FP16 replica: p95 depends on batching, expect 1.2–2.5s p95 with appropriate KV caching.

Operational recommendation:
- Ship commit with 4x 40GB reserved nodes (8-bit default) + SLA on-burst to 80GB family. Add an opt-in reserved 80GB node if procurement wants predictable latency for long jobs.
- Include an appendix (one-pager) in the procurement pack with: model table, memory assumptions, routing policy, and overage billing rates.
