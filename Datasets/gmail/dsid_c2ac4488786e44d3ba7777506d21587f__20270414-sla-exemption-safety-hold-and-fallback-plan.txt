Paul — appreciate the clear list. We've reviewed Evergreen's matrix; attached is a first-draft addendum that attempts to balance your need for predictability with our operational safety practices (redwood_sla_canary_addendum_v1.docx). High-level summary of our proposal: 

1) Canary Safety-Hold: For any canary or A/B rollout, Redwood will maintain an automated health monitor based on latency, error-rate, and output validity signals. If the canary exceeds defined thresholds for X consecutive 5-minute buckets, traffic is automatically routed away from the canary to the last-stable variant (auto-fallback).

2) Pinning: Customers can request a manual pin of a model variant. In addition, we offer an automatic pin option: if auto-fallback triggers, the previous stable variant is pinned for a configurable hold period (we propose 60 minutes) unless the customer explicitly approves re-try.

3) SLA impact & credits: Credits for SLA deviations during an identified canary window will be calculated pro-rata over affected requests, with a carveout only if the canary window was mutually agreed in advance or flagged in the control plane. We included explicit examples in the doc.

4) Telemetry & audit: All canary rollouts will record audit logs (trial IDs, telemetry snapshots, and the exact time of auto-fallback) and we will share those logs on request for investigations.

Paul — adding a few technical guardrails so the addendum maps to operational behavior: 

- Signals used: p50/p95 latency, 5xx rate, percent of requests failing output validation checks (we have model-level checkers for hallucination rate on structured tasks).
- Threshold proposal (initial, can be calibrated in trial): auto-fallback if p95 > 2x baseline AND 5xx rate > 0.5% for 3 consecutive 5-minute buckets.
- Canary scope: canaries default to 5% user traffic unless Evergreen requests a smaller window.
- Pin behavior: after auto-fallback, we will pin the stable variant for 60 minutes (auto), with the option for Evergreen to request an immediate manual pin for longer retention. Manual pins require a support ticket and confirmation from both parties.
- Fail-open vs fail-closed: by default we route to the last-stable variant (fail-open to conservative baseline).

Operational notes: we use KV cache warmup and prefix caching to limit cold-start regressions. If Evergreen prefers, we can add a clause that probe traffic and synthetic checks do not count toward SLA credit calculations if they are run at times agreed in advance.

Paul — thanks for the questions. Here's a compact proposal that we think is workable for contracting: 

A) Credits: If a service-impacting event occurs outside a pre-scheduled canary window, SLA credits will apply starting at the timestamp of the first affected request, prorated to impacted tokens/requests. If the event occurred during a mutually pre-notified canary window, credits will not apply provided the canary met the pre-notification requirements in the addendum.

B) Time-to-fallback commitment: Redwood proposes a contractual auto-fallback bound of "<= 15 minutes" for 95% of auto-fallback events triggered by the defined thresholds. The operational median is typically under 5 minutes; we want to keep a conservative contractual bound that includes detection, routing, and cache warmup.

C) Pin controls: We can expose a console-level emergency pin button for customers with Dedicated or Private deployments. For Hosted API (standard accounts) the pin action requires a support ticket to avoid accidental global pinning.
