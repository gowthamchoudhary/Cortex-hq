Folks — technical confirmation and playbook notes below. Attaching the canary playbook (redwood_canary_playbook_v1.pdf).

Feasibility: Yes — runtime supports automated rollback and pinned endpoints. Implementation details:
- Detection: we’ll run a short-lived SLO-checker that evaluates error-rate and latency windows (as Stephanie outlined). The checker emits a signal to the routing tier; routing will execute a weighted shift back to v1 with exponential backoff if necessary.
- Revert time: warm path restores traffic to v1 within ~90–120s in lab; in production plan conservatively assumes 2 minutes.
- Fallback pin: we’ll create a customer-scoped pinned endpoint (stable-v1-novacorp) that bypasses canary routing and serves the locked model.
- Safety nets: health-checked pre-warm on the pinned instance, KV cache warm-up strategy to avoid cold-start latency spikes, and staged traffic reductions (10% -> 5% -> 0% if repeated failures).
- Observability: we’ll publish a Tableau-like dashboard for p50/p95/p99 and request/err-rate. Webhook subscriptions for your pager are supported.

Operational caveats:
- The temporary SLA carveout is required because automatic rollback relies on our detection thresholds and the pinned fallback; during the 7-day window the SLA will be scoped to exclude incidents caused by the canary traffic shift if the auto-failover rules were in effect and executed.
- If NovaCorp elects to use manual pin routing, the carveout must still be processed (we need the legal acknowledgment).

I recommend the following acceptance criteria for the 72-hour run:
- No user-visible errors above 0.5% overall
- p95 within 1.5x baseline after 1 hour post-shift
- Post-run retro and metric export within 48 hours
