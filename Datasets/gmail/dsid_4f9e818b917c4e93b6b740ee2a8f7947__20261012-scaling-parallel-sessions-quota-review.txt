Hi Max / team —

Thanks for the clear targets. Below are our technical recommendations and an initial proposal for quotas and fallback behavior. High-level approach first, then specific numbers.

Technical recommendations
- Connection pooling: For token-streaming workloads we recommend HTTP/2 with long-lived keep-alive connections and multiplexing. In practice, aim for ~1 active TCP connection per 8–12 simultaneous streams from each ingestion tier; this minimizes TCP/TLS handshake overhead while letting HTTP/2 multiplexing handle parallel requests.
- Parallel requests: Given your pattern (avg 400 QPS, peaks @1,200 QPS, 350 concurrent sessions) we recommend configuring the client pool to allow up to 6 parallel requests per active session for power users but enforce a per-API-key concurrent-request cap at the gateway.
- Gateway rate limits: initial provisional limits we can *reserve* for the POC: 1,500 concurrent requests (global for your tenant), 4,000 requests/min sustained burst window (60s), token-rate limit of 200K tokens/min. If we observe headroom and stable behavior during the POC, we can raise the concurrent cap before production.
- Batching & caching: Enable prefix/KV caching for repeated prompts; use 8–16 token prefetch/batching threshold to get significant cost/throughput gains while preserving latency for streaming.
- Fallback policy: configure automatic fallback to a smaller, quantized model variant when queueing exceeds a safe threshold (e.g., >85% of reserved concurrency for >30s). We suggest fallback to redwood-13b-quant (lower cost, slightly higher latency) to avoid full outages.

Why these numbers?
- 1,500 concurrent requests covers steady-state (roughly 400 QPS) with headroom for bursts when combined with HTTP/2 multiplexing; it assumes average request concurrency of ~0.3s per token-window for streaming calls.
- 4,000 requests/min gives cushion for short elastic bursts without immediate throttling; the gateway will apply soft-queuing then enforced rate-limit responses after sustained exceed.

Operational notes
- Canary / POC plan: We can start with a limited traffic slice (10% of production traffic from a single region) and progressively ramp to 100% over 48 hours if metrics look healthy.
- Metrics to capture during POC: p50/p90/p99 latency (token-level), connection count, active streams, gateway queue length, error-rate (5xx and 429).
- Logging: we will provide per-request trace ids and an S3 export of request/response metadata for the POC window.
