Samir — thanks for the clear numbers. Quick response with an actionable starting point (attachment: telemetryx-transient-capacity-matrix-v1.xlsx). High level:

1) Safety matrix approach (summary)- Commit a small reserved slab sized to steady-state + 20% (so 25 qps -> slab ~= 30 qps).- Complement with an ephemeral burst pool sized for the expected peak minus slab (for your numbers: target burst headroom ~= 170 qps).- Limit sustained burst eligibility to defined windows (15/30/45 min buckets) so we avoid long-running overcommit.

2) Autoscale + warmup policy recommendations- Pre-warm: allow a fast pre-warm handshake up to 20% of the burst pool (cold-start fast-path for commonly used routes) — the goal is <150ms median additive warmup for hot keys.- Scale step: geometric 2x steps with a 60s stabilization cooldown; max scale actions per minute = 3 to prevent oscillation.- Fallback: if burst pool exhausted, route to lower-cost quantized variant (same model family) with a graceful degradation policy.

3) Cost and procurement mapping- Provide three cost buckets in the attached one-pager: Baseline (reserved slab), Pilot burst (ephemeral hourly spends), Contingency credits (for exceptional days).

Looping in infra recommendations from the runtime side — copying Samir for visibility. TL;DR: matrix looks good; a few concrete knobs to avoid surprises during pilot.

Recommendations (runtime/infra):
- Reserved slab sizing: agree with slab ~= steady + 20%. For your 25 qps baseline, we recommend reserving 1 N GPU slab (optimistic) but map to per-model throughput — see workbook.
- Burst pool sizing: carve an ephemeral pool of specialized instances (mixed T4/NVIDIA future-gen) that can be reclaimed after 30–45 min of inactivity.
- Eviction policy: prefer LRU over TTL for prefix cache eviction during noisy bursts to preserve hot-session latency.
- Autoscale controls: cooldown 60s, max parallel scaleups = 3, max instances per customer during pilot = 8 (to bound blast radius).
- Telemetry: enable request-level tracing + token-level cost breakdown for the pilot so we can reconcile cost vs latency per window.

Operational ask: we should add a per-day burst cap (in pilot contract) and a mechanism for temporary crediting if telemetry shows an experiment run that legitimately exceeded the cap. That gives procurement comfort.

I attached a quick sizing sketch in the telemetryx workbook. If procurement wants hard numbers, Ben — can you produce a cost run for the pilot using the three buckets Laura outlined?
