> Quick notes in-line:
> - Isolation model: multi-tenant compute instances run in tenant-bounded pools. We use network namespaces + sidecar proxies per tenant group, and strict RBAC at the control plane to prevent cross-tenant KV cache access.
> - Egress controls: per-tenant egress policies via VPC routes, DNS filtering, and egress NAT per availability zone. We implement default-deny egress for hosted customers and mandatory egress breakouts for dedicated/private deployments.
> - Incident containment (first 60 min): 1) enact tenant circuit-breaker (quarantine compute pool) 2) revoke session tokens and block new control-plane joins 3) initiate KMS key rotation for impacted model keys 4) snapshot and export KV cache read-only for forensics 5) enable enhanced audit sampling and forward logs to a cold archive for the incident window.

> Hi Elena — attaching the annotated network diagram (network-diagram-supplychain-annotated.png) and a short technical appendix in the docx with specific firewall rules we recommend for interconnect. Key clarifications: 
>
> 1) Control vs data plane: the control plane (auth, model routing, admin APIs) is logically separated and runs in a customer-scoped control domain. Customer workloads never receive control-plane credentials by default.
> 2) KV cache: each tenant has an encrypted, tenant-scoped KV cache namespace. KVs are stored encrypted-at-rest with tenant-specific DEKs protected by KMS. Access is mediated by sidecars; sidecars authenticate with short-lived mTLS to the cache pool.
> 3) Autoscaling and containment: when a tenant pool scales, new nodes are provisioned into the tenant's network namespace with ephemeral network policies applied prior to joining the mesh. That pre-join gating is the primary containment control for noisy or anomalous scaling events.
> 4) Egress mitigation options: conditional egress blackholing, per-tenant NAT IP rotation, and temporary egress proxies that drop non-whitelisted destinations. We can script a short runbook for your ops to hit the API and quarantine an environment.
>

> Hi Elena — short answers to your asks: 
> 1) Logs:
>    - Hot pipeline (30 days default): auth events, control-plane API traces, token issuance/rotation events, sidecar mTLS handshake logs, KV access logs at a sampling rate configurable per-tenant.
>    - Warm (30–180 days): aggregated metrics, tail-sampled traces used in anomaly scoring.
>    - Cold archive (>=180 days): full audit bundles exported as compressed WORM objects (SHA256 checksums provided).
>
> 2) Quarantine API sequence (example):
>    - POST /api/v1/tenants/{tenant_id}/actions/quarantine {reason}
>    - POST /api/v1/tenants/{tenant_id}/keys/rotate?scope=session_tokens
>    - POST /api/v1/tenants/{tenant_id}/egress/blocklist {cidrs}
>    - GET /api/v1/tenants/{tenant_id}/cache/snapshot?read_only=true -> stream to S3 for forensics
>    - POST /api/v1/audit/export?tenant_id={tenant_id}&window=last_60min -> provide download link to requester
