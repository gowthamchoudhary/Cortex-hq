Tina — thanks for the clear ask. Attaching a compact snapshot and an updated diagram (see attachment stubs below). I kept the language intentionally short so it can be dropped into the SIG/CAIQ.

Quick narrative (summary):
- Tenant isolation: Customers on Dedicated get reserved GPU pools and network namespaces. The control plane (hosted by Redwood) is logically separated from the customer data plane; control plane communications are authenticated with mTLS and limited to management endpoints. Private (VPC/on‑prem) customers run a customer-managed control plane or a customer-provisioned control-plane connector; in that case, our control-plane calls are tunneled over a customer-approved management channel.

- Data plane boundaries: Model serving occurs in isolated tenant pools. For Dedicated, tenant pods run in separate node pools with enforced network policies; for Private, we rely on customer VPCs and subnets. KV cache and model artifacts are stored in tenant-scoped volumes; shared caches are disabled unless explicitly opted-in and logged.

- Egress & filtering: All outbound traffic from serving instances is routed through an egress proxy (Dedicated edge) where outbound allowlists and content-name-based filtering apply. For Private, egress is controlled by the customer's network; we provide recommended firewall rules and an egress ACL template.

- KMS/HSM boundaries: For hosted control plane we integrate with a Redwood-managed KMS; customers can opt for a customer-managed KMS via cross-account key grants. For Private deployments we support KMS/HSM inside the customer's network — keys never leave the customer's HSM.

- Failover & fallback: Routing policies allow automatic fallback to a lower-cost model variant in a different region or to an on-prem replicate if network partitioning occurs. Rollbacks are orchestrated via a canary-first rollout with automatic health checks; critical traffic shifts to a pre-provisioned standby pool during incidents.

Hannah — adding a couple technical clarifications for the auditor's checklist. Quoting your bullets above for context:

> - Tenant isolation: Customers on Dedicated get reserved GPU pools and network namespaces. The control plane (hosted by Redwood) is logically separated from the customer data plane; control plane communications are authenticated with mTLS and limited to management endpoints.

- Implementation note: for Dedicated we use node-pool level taints + Kubernetes NetworkPolicies to prevent cross-tenant pod-to-pod communication. The NVMe-backed model artifacts are scoped via per-tenant IAM roles; access is tokenized with short TTLs.

> - Data plane boundaries: Model serving occurs in isolated tenant pools. For Dedicated, tenant pods run in separate node pools with enforced network policies; for Private, we rely on customer VPCs and subnets. KV cache and model artifacts are stored in tenant-scoped volumes; shared caches are disabled unless explicitly opted-in and logged.

- Implementation note: cache isolation for Dedicated uses namespaced redis instances with ACLs; we instrument cache-hit telemetry for auditing. For Private on-prem installs we provide a config profile that disables cross-tenant cache sharding by default.

> - Egress & filtering: All outbound traffic from serving instances is routed through an egress proxy (Dedicated edge) where outbound allowlists and content-name-based filtering apply. For Private, egress is controlled by the customer's network; we provide recommended firewall rules and an egress ACL template.

- Implementation note: egress proxy supports TLS inspection and SNI-based allowlists for outbound model artifact fetches. We also surface egress logs to the customer's logging collector (Syslog/ELK) for compliance audits.

> - KMS/HSM boundaries: For hosted control plane we integrate with a Redwood-managed KMS; customers can opt for a customer-managed KMS via cross-account key grants. For Private deployments we support KMS/HSM inside the customer's network — keys never leave the customer's HSM.

- Implementation note: we support both envelope encryption (customer key wrapping) and direct HSM integration for Private; documentation includes examples for AWS CloudHSM, Azure Key Vault HSM, and Transit HSM patterns.
