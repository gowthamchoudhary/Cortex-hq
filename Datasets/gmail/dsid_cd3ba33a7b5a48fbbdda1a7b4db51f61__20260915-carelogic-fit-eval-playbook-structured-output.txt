Thanks Sam — quick technical answers and a concrete fallback pattern we recommend.

1) JSON validation behavior
- Primary flow: we run a JSON Schema validator on the model's output server-side. If the output passes, it's forwarded to your consumer with metadata (trace_id, model, token_cost, latency).
- On schema failure: we attempt up to 2 automated retries with incremental prompt relaxation: 
  • Retry 1: re-run same model with the validator-aware instruction + "Must respond in exact schema" and include the prior model output as context.
  • Retry 2: downgrade to the alternate model (open/llama3-8k) and add an explicit field-level confirmation step (e.g., "Confirm priority is one of [P0,P1,P2]").
- If retries all fail, we return a structured error object that conforms to your error schema (error.code, error.reason, last_model, trace_id) and tag the event as "needs_manual_review".

2) Retry control and logging
- Yes: retry policy is configurable per route in Redwood Console; you can set 0/1/2 and choose fallback models.
- Logs: for every attempt we will store a single-line audit entry with trace_id and a reference to full payload in your private audit bucket (encrypted). We can surface the first 200 chars of prompts in the dashboard; full prompts are available on request under a contract.

3) PII/redaction
- We strongly recommend you pre-redact before sending production data for the eval. For the sandbox run, Redwood can run an optional pre-filter that masks common PII patterns (emails, credit card, SSN) but this is best-effort and not a replacement for client-side redaction.

Attached: json_schema_checks.yaml — contains example schema + sample validator rules we use during the eval.
