Hi Olivia — thanks for the clear questions. TL;DR: we offer configurable behaviors (notify-only, soft-throttle, or hard-block) plus a 72-hour grace window by default for new overages; billing is handled via a true-up invoice at the end of the billing cycle unless you opt into immediate invoicing. Details below and next steps at the bottom.

What we do by default (hosted API):
- Notifications: email + webhook after 80% and 95% of your committed/expected spend. Real-time usage is available in the Console.
- Grace window: a 72-hour soft-grace period where requests continue but rate-limited to protect latency SLOs. This gives customers a short runway to remediate before stricter enforcement.
- Enforcement modes (configurable per-account or per-API-key):
  * notify-only (no immediate enforcement)
  * soft-throttle (requests still succeed but throughput reduced to a configurable percentage; we typically recommend 30–50% for portal-protection use cases)
  * hard-block (new requests return 402 Payment Required / 429 Too Many Requests until billing cleared or cap increased)
- Billing: overages are included on the next monthly invoice as a true-up by default. If you need immediate billing, we can enable immediate invoicing for overage events (generates an invoice when threshold breached). All overage tokens are billed at the active rate for the model used; discounts that apply to committed usage do NOT automatically apply to unpaid overages unless covered in the contract amendment.

Per-API-key caps: yes — we can scope enforcement to API keys or routes. Typical setup for customers that want portal protection: set a hard-block at the public key level and a higher soft-cap for internal keys. We can include a runbook and sample configuration in the SOW.

Other practical notes:
- Auto-fallback: we can optionally configure automatic routing to a lower-cost model variant when a threshold is hit (risk-based; can be enabled per-route).
- Webhooks: we push events for threshold-crossings so your ops can take automated action.
- Audit logs: all enforcement events are logged and available for export (useful for finance and compliance).

Attachments: I attached our current exceed-policy summary and the latest AMA rate card for hosted API so you have the numbers to run internally.

Next steps / options for Atlas:
1) If you want a simple safety net: we can enable notify-only + webhook + 72-hour grace.
2) If you want portal protection: we recommend per-key hard-block for public keys + soft-throttle for internal keys.
3) If you prefer billing behavior changes: add a contract amendment to define immediate invoicing for overages or to apply committed-discount rates to overage up to an agreed limit.

Hi Olivia — jumping in with the technical implementation details Jordan mentioned and example snippets you can hand to your eng team.

Soft-throttle example behavior (recommended):
- When threshold reached, we start returning 429 Too Many Requests for requests above the configured throughput. We include two headers you can use:
  * X-Redwood-Quota-Remaining: tokens remaining in the current window
  * X-Redwood-Throttle-Rate: current enforced percentage (e.g., 40 for 40%)
- We also optionally inject an informative JSON body: {\n  \"error\": \"quota_exceeded\",\n  \"recommended_action\": \"reduce_batch_size or fallback to cheaper-model\"\n}
(we'll provide exact sample payloads in the runbook).

Per-key enforcement: fully supported. Suggested setup for Atlas:
- Public key: hard-block at 100% of the portal allocation (returns 402/429).
- Internal keys: soft-throttle at 40% with webhook notifications to your ops channel.
- Routing: automatic — we can bind enforcement policy to API key metadata; no manual intervention needed once the policy is in place.

Billing specifics:
- Default true-up: the next invoice will show the full overage amount for the billing period (not a delta). If you prefer a delta-only line item, we can produce a custom invoice template; ask Commercial Ops.
- Discounts: overages are billed at the active model rate. Applying committed-discounts to overage requires explicit contract language — we can include a capped overage allowance in an amendment (e.g., first $2k overage at committed discount).

Operational options to reduce friction:
- We can enable an automated fallback to a lower-cost model variant for certain endpoints (helps avoid hard outages).
- Webhook + PagerDuty integration for immediate ops response.
