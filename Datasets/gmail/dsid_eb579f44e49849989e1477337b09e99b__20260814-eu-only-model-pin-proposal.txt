TL;DR: technically possible but operationally risky if we do a hard no-fallback on hosted infra. Details below.

Notes and assumptions:
- Pinning: We can add a routing policy that maps HealthSync's api-key to a model-pinned tag (redwood-instruct-7b-eu-quant) and region restriction to eu-west-1/2 endpoints.
- Capacity: If this model is quantized and smaller (7B), it's reasonable, but we need expected qps to size autoscaling. Without a Dedicated commit, the control plane cannot guarantee capacity during cloud pressure; that means a real outage risk if there is a cluster pressure event.
- No-fallback risk: If we disable fallback, any node-level issue causing that model variant to be unavailable will result in 100% request failures rather than falling back to a compatible model. We need an agreed SLA downgrade or emergency fallback policy (manual or automatic with approval).

Operational requirements to proceed:
1) Signed addendum explicitly authorizing region-only enforcement and acceptance of outage risk if fallback is disabled.
2) Runbook with approved rollback steps (we can implement an automated rollback toggle that product/ops can hit).
3) Canary plan: 48-hour canary at 5% traffic, followed by 100% only after stability checks (error rate, p95 latency).
4) Deployment window: 45 minute change window during low traffic (we recommend 02:00–03:00 UTC).

Estimated timeline (with infra resources):
- Prep + config change (policy + pin mapping): 3 business days
- Canary monitoring + verification: 2 days
- Full flip: 1 business day (after signoff)

Attachments: route_config_diff.patch (config diff stub)

If HealthSync is unwilling to accept the risk of no-fallback on hosted, recommend Dedicated lanes (we can reserve capacity and provide SLA guarantees). I'm happy to run the change with infra on-call and ensure the toggle for emergency rollback is in place.
