Team — did a quick first-pass footprint and options. I kept the math conservative and included assumptions so we can adjust. High level takeaways first, then numbers.

Assumptions (rounded):
- Model class: 70B parameters. FP16 full weights ≈ 140 GB. Quantized q4_0 weights ≈ 38–45 GB depending on format/packing; q8-ish variant ≈ 70–80 GB.
- KV cache: long-context (32k tokens) per concurrent session ≈ 20–28 GB of KV memory (depends on layer count and per-token KV footprint). I used 24 GB/session for estimates.
- Serving config: we aim for p50 latency targets under 400 ms for short flows and under 700 ms for long RAG (with retrieval).
- GPU options considered: H100 80GB, A100 80GB, and 48GB-class (for burst/offload). H100 and A100 behave similarly for memory accounting; H100 gives better multistream performance.

Option A — Performance-first (recommended for pilot with predictable latency):
- Use H100 80GB reserved pool. Each GPU can host one 70B q4_0 model + 1 long-context concurrent session (32k) without KV offload.
- Per-instance memory budget: q4 weights 40 GB + KV 24 GB + runtime/overhead ~8 GB => ~72 GB total.
- To meet concurrency 20 long-context sessions concurrently => 20 GPUs. Add 20% headroom => 24 H100 GPUs reserved.
- Short-context q8 variants: colocate as separate containers (weights ~75 GB) — can squeeze one q8 short-worker per H100 if not contending with long flows, otherwise prefer mixing via routing policies.

Option B — Cost-optimized committed + burst to hosted:
- Reserve A100 80GB equivalent, size for baseline concurrency 12 long-context sessions (12 GPUs) + 25% headroom => 15 GPUs reserved. Peak handled by bursting to Redwood hosted tier or by autoscaling non-committed GPU pool.
- Aggressive quantization: if the customer is willing to accept q4 for the short-variant as well, we can pack 1.5–2x short-serving containers per GPU for baseline traffic.
- Tradeoff: q4 reduces model size ~3x vs FP16 but can introduce subtle generation quality differences for the most sensitive prompts — plan for an evaluation harness and a small A/B test before full switch.

Option C — Mixed offload strategy (lower capex footprint):
- Use 48GB-class GPUs in the reserved pool and rely on KV offload (NVMe/host memory) for long-context requests. That reduces reserved GPU count but increases p95 latency ~200–400ms and operational complexity. Estimated reserved count: 28 x 48GB GPUs to cover 20 concurrent long-context sessions with KV offload and higher CPU/IO provisioning.

Numbers summary table (rounded):
- Performance-first (H100): reserved = 24 H100 80GB (commit) — supports 20 concurrent 32k long sessions with 20% runway.
- Cost-optimized (A100 + burst): reserved = 15 A100 80GB (commit) + hosted burst.
- Offload (48GB): reserved = 28 x 48GB + NVMe offload.

Quality/quantization notes:
- q4_0 gives the largest memory win (weights drop ~3x) making single-GPU serving for 70B + 32k context feasible. However, q4 artifacts can appear on edge cases (hallucination patterns, tokenization differences). Recommend a 2-week eval on a representative prompt set.
- q8-ish formats have smaller memory savings but preserve fidelity better — a good middle ground for customer-facing flows that are quality-sensitive.
- KV offload is viable but increases tail latency and operational surface (monitoring of NVMe throughput and failure modes).
