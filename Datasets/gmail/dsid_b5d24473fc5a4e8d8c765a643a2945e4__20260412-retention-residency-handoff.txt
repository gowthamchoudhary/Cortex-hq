Marissa / team —

Thanks — here are the technical notes and a proposed delivery plan for the MVP scope: 

1) Per-tenant retention
- Implementation: retention TTL stored in metadata per tenant. Background retention worker runs once/hour applying TTL to object store keys and DB rows. For low latency deletes we use an async index + SQS-style queue to batch purge to avoid tail-latency spikes.
- Storage: object artifacts live in S3-compatible buckets partitioned by region. Metadata in our primary DB (Postgres).
- Edge cases: partial objects (KV cache) vs persisted logs — need to clearly mark what "retention" applies to.

2) Regional pinning
- Implementation: policy layer that picks bucket/region per tenant at write time. For hosted customers we can create logical partitions in our multi-region infra; for Dedicated/Private we rely on customer-provided VPC region.
- Cross-region failover: by default we won't replicate across regions for pinned tenants; we do provide optional DR if requested (higher cost).

3) Deletion API + audit
- Delete API: immediate logical delete + enqueue physical purge job.
- Audit trail: immutable audit-log events written to append-only store (WORM-like S3 prefix) and available for export; include requestor, timestamp, object ids, purge job id.

Security notes: 
- KMS: keys must be region-bound; need to coordinate with KMS team for per-region key usage and key rotation policies.
- Proof of deletion: we can provide signed manifests of deleted object IDs and purge job timestamps; legal team should validate format.

Effort estimate (rough) for MVP: 
- Design + spec: 1 week (INF-4521)
- Implementation + infra changes: 4 weeks (core retention worker + APIs + region routing)
- Tests + canary + docs: 2 weeks
Total: ~7 weeks.

Open questions for product/security sign-off: 
- Allowed maximum custom TTL? (e.g., up to 7 years)
- Default retention for hosted accounts (e.g., 365 days)
- Required retention proof format for legal.
