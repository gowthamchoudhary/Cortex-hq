Thanks for the signal and logs. I pulled the attached trace — initial read indicates a mismatch between the SDK streaming handshake and the HTTP path. Specifics:

- The SDK uses a persistent streaming connection and sends a client-side session-id in the initial handshake metadata. In a subset of cases the runtime's routing layer drops that header for background replays (we see a missing X-Client-Session header on subsequent chunked requests).
- The missing header causes the request router to fall back to variant selection heuristics which can pick a legacy variant with shorter context window — hence the truncation.
- The 500s appear tied to a KV-cache invalidation race when a streaming request arrives without a valid session key. We get a short-lived exception that surfaces as a 500 in the public API.

Immediate actions I propose:
1) Short-term: add per-account routing override (disable-session-stickiness=true) — we can expose this today as a config flag in the routing table and flip it for Crosswind. No code change required; operational configuration only. I can coordinate the flip and a rollback window.
2) Mid-term: patch the streaming handshake path to ensure X-Client-Session is upserted on every chunked request path. Karthik, can you scope the patch/work? My estimate: small runtime change, but we need a canary and cycle (~2 dev days + validation).

- repro: python sdk-sample-repro.py --token <redacted> --concurrency 40
- toggle: rwctl routing set --account crosswind --disable-session-stickiness=true
