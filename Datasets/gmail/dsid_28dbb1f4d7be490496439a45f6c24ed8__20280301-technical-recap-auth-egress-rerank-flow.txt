Hi Alex — thanks for the great questions. Short answers up front, then a few implementation notes and an ask for your security contact so we can share a brief architecture note.

1) VPC endpoint behavior
- If we use an AWS VPC endpoint (PrivateLink) for inference, the inference data path stays within your AWS environment. The compute that runs the model is in Redwood's dedicated runtime but the network hop for API calls can be over PrivateLink; no public ingress required for inference traffic. Control plane telemetry (billing/usage) needs an outbound to Redwood control plane endpoints — we can either proxy control plane telemetry via a customer-configured egress proxy or bundle minimal telemetry into the PrivateLink path depending on your compliance posture.

2) mTLS and client certs
- We support mutual TLS with customer-supplied certs; your internal PKI certs are acceptable, provided the certs are presented in X.509 PEM format. Redwood only needs to trust the issuing CA; we can exchange the CA bundle during provisioning. No need to use a Redwood CA.

3) Embeddings-only node in customer VPC
- We offer an embeddings-hosted-in-VPC pattern for enterprise POCs. That node stores vectors in customer-owned storage (you can bring your own S3 bucket) and talks to Redwood's serving runtime over a secured private connection (PrivateLink / peering). We will provide a compliance checklist for encryption-at-rest and KMS integration.

4) Reranker determinism
- You can pin model version, tokenization library version, quantization profile, and random seed in the reranker config. We recommend storing the deterministic config in a commit in your repo (we can inject a reproducibility hash into logs).
