Hi Matt — thanks again for the call earlier. Quick recap and proposed next steps for the POC (focused on private connectivity and deployment mode):

Summary of options we discussed:
- Hosted API: fastest to start; no VPC changes required but outbound traffic traverses Redwood-managed endpoints. Good for early functional tests.
- Dedicated capacity: reserved GPU pool with predictable throughput + isolation; still uses Redwood network but can be combined with private connectivity in some cases.
- Private VPC (PrivateLink or VPC peering / reverse proxy): best for strict egress/allowlist requirements and compliance — recommended for Ledgerly POC given your security posture.

Our recommendation for the POC: start with PrivateLink (AWS PrivateLink style) for the following reasons:
- Minimal routing changes on your side (no peering route propagation),
- No shared public egress IPs — we provide a specific set of ENI-backed endpoints and static egress IPs for outbound responses,
- Faster security review for teams that cannot accept peering or cross-account route tables.

Action items we need from Ledgerly to get the PrivateLink POC ready:

4) Any certificate/CNAME preferences (do you want Redwood-managed TLS certs or customer-managed certs + CNAME?).
