Hi Maya / team — great questions. Below are concrete answers and pointers; I’ve included the operational playbook and vendor matrix as attachments for your security team to review.

1) BYOK export/import behavior
- Import: Customers can import key material (PKCS#12 or wrapped key) into Dedicated/Private via an administrative import workflow that leverages envelope wrapping with an HSM master key. For Private appliance installs, keys can be imported locally via the admin console or using our offline import tool.
- Export: Live export of unwrapped private key material is not supported from Redwood-hosted services. For Private deployments where customers manage the appliance and HSM, you may export keys according to your appliance controls if your HSM vendor and policy allow it; Redwood will not perform unwrapped key exports for Hosted or Dedicated tenants.
- Rotation: Keys are versioned. New keys are marked active; previous key versions are retained based on retention policy and can decrypt historic ciphertext until you trigger a purge. Default retention for rotated keys is 180 days; configurable per-customer up to 730 days for Dedicated/Private with corresponding audit controls.

2) HSM attestation and vendor compatibility
- Attestation: For Private appliances we can provide device attestation blobs signed by the HSM vendor (where supported) plus our local attestation summary. For cloud Dedicated (e.g., CloudHSM), we provide vendor attestation reports and the derived key identifiers; we can also provide a redacted attestation sample for your review under NDA.
- Vendors: Supported vendors include AWS CloudHSM, Thales nShield, and selected FIPS-certified modules in on-prem racks. See hsm_vendor_compat_matrix.xlsx for details by model and firmware.

3) Key wrapping and algorithms
- Envelope encryption: We use customer data keys (CDK) wrapped by a master key held in HSMs. Supported wrapping algorithms: AES-KW (RFC 3394), RSA-OAEP (for legacy import flows), and AES-GCM wrapping for specific flows. Data encryption algorithms supported: AES-256-GCM by default.
- Memory/storage: Unwrapped plaintext keys exist briefly in memory inside HSM or inside a tightly controlled encrypted process memory region during import/unwrapping. We do not persist unencrypted key material to disk.

4) Audit and retention
- Key operation logs: All key operations (import, rotate, wrap/unwrap, export attempts) are logged and immutable in our audit stream. Default retention for audit logs is 365 days for Hosted; Dedicated/Private can be configured per contract. Audit exports can be provided as CSV or via secure S3 transfer.

5) TLS and cipher specifics
- Minimum TLS version: TLS 1.2 (1.3 recommended).
- Cipher suites (representative): TLS_AES_128_GCM_SHA256 (TLS1.3), TLS_AES_256_GCM_SHA384 (TLS1.3), TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 (TLS1.2), TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384 (TLS1.2).
- We disable RSA key exchange and legacy CBC ciphers by default for enterprise tenants. Perfect Forward Secrecy (ECDHE) is enforced.
- mTLS: Supported for Private and Dedicated via customer-managed certificates; Hosted mTLS is available for enterprise customers on a per-account basis.

6) Attestation / signed statements
- We maintain a short KMS Statement of Practice (SOP) that covers roles and responsibilities, operational windows, and key handling procedures. We can sign a standard attestation via DocuSign; Aisha will follow up with the DocuSign link for your legal/procurement team.
