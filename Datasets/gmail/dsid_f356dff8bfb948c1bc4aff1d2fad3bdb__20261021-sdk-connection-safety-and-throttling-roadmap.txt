Hi Alex — great to see this scoped. Quick answers up front, then a short plan and attachments.

Defaults we recommend (hosted API):
- Connection timeout (initial TCP connect): 5s.
- Read/idle timeout (socket): 30s for normal generation calls; 90s for long-stream jobs.
- Retry policy (idempotent calls like embedding/ranking): up to 3 retries with exponential backoff (base 300ms, factor 2, jitter).
- For streaming/text-generation: avoid automatic request-level retries; instead implement client-side reconnect logic with resume tokens.

Rate shaping:
- Tenant-level token quota: suggest starting with 10 TPS (tokens/s) soft limit per tenant, enforced client-side + 429 guardrails server-side.
- Burst window: allow short bursts up to 3x for 10s then smooth to steady rate.

Endpoint migration sequence (suggested):
1) Canary (5%): route non-critical traffic, no cache prime.
2) Warm prefix cache: run synthetic prime requests for top 10 prompts under the canary pool.
3) Ramp (5->40% over 4 hours): monitor latency and 429s.
4) Full shift (overnight window): final cutover and deprecate legacy endpoints.

Hi Alex — adding telemetry and ops details so your SREs know what to look for.

Key telemetry to enable before ramp:
- 95th/99th token latency per model variant (30m buckets).
- 429 count and 5xx spikes per endpoint and per-tenant.
- Prefix cache hit ratio (this will surface how effective warmup is).
- Concurrent KV cache entries and memory churn events (if you use client-side caching patterns).

Alert thresholds (starter):
- 5xx rate > 0.5% sustained for 10m -> priority-1 paging.
- 429 spikes > 1% and sustained for 5m -> paging + auto-throttle engagement.
- Token latency 99th > 2x baseline -> warn; >3x baseline -> page.

Operational suggestions:
- Synthetic warmers: run them from your canary region using the same client config to replicate connection behavior.
- Backoff tuning: on 429 return, have clients wait 1s * (2^attempt) with full jitter and cap at 8s.
- Graceful degradation: implement a cached best-effort response path for non-critical requests.

Alex — quick responses to your points and a compact checklist for your dry run.

Streaming resume pattern:
- The SDK exposes chunked resume IDs for long-running responses. On an unexpected disconnect the client should reopen the stream and include header X-RW-Resume: <resume-id>. The server will respond with the next token index to resend. For HTTP clients that can't use that header, use idempotency keys for short-generation replays (note: repeated tokens count towards quota).

Quota fallback best-practice:
1) Local smoothing: priority #1 — smooth at client ingress to avoid hard bursts.
2) If smoothing is insufficient, implement model variant fallback server-side (e.g., rwd-small) for non-critical user tiers.
3) For critical paths, surface a 429->user message with ETA and optionally queue for background completion.

Dry-run checklist (pre-cutover):
- [ ] Run synthetic prefix warmers (top 20 prompts) against canary 5% pool.
- [ ] Validate telemetry dashboards show cache hit ratio > 60% after warmers.
