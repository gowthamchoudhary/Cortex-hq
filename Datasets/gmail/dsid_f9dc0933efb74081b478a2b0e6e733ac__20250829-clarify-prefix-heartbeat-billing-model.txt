Thanks for the demo yesterday — the runtime performance looked great. Before we move to procurement, my finance and infra teams have two specific questions about how billing would look for our use case so we can model costs:

1) Long-lived chat with periodic heartbeats: our product keeps a session open and pings the model every ~30s to keep the KV cache warm (each ping is a very short prompt ~6 tokens on average). How do you bill those heartbeat calls? Are they billed per-call rounded to your minimum quantum, or do you amortize them into an active session bucket?

2) Prefix / KV reuse across requests: we send a 1.5k-token prefix (user settings + context) on first call, then subsequent calls within the session only send 8–12 tokens. Is the 1.5k counted for every request, or do you apply any reuse credit or amortization for prefixes held in KV? Also, how does that interact with minimums/rounding if each follow-up is very small?

We attached a short questionnaire with sample volumes and a sample of our average prompt shapes (attachment). If you can sketch concrete examples (per-100k-session estimate) that would help our finance folks.

Hi Elena — great questions, thanks for the detail and for the attachment — that helps. Below is a concise breakdown with a couple of example calculations. I'll also loop in Ben and Marissa so we can finalize any pilot concession.

Short answers up front:
- Heartbeat calls: billed per-call, rounding to the billing quantum. For pilot discussions we've historically offered a heartbeat concession (see below).
- Prefix/KV reuse: Redwood applies a KV-reuse amortization when the same model instance serves multiple requests within an active session. Practically that means the full prefix is charged on the first request that materializes it; subsequent requests within the same session are billed only for their incremental tokens (subject to the per-call quantum rounding).

Conservative policy (default behavior used in invoicing):
- Token increment quantum: 16 tokens. Every call is rounded up to the nearest 16-token quantum.
- Streaming tokens: billed as generated; rounding applied at request close (so short streams still hit the quantum).
- KV reuse credit: full prefix tokens are billed once per active session/connection. If the session is torn down and reestablished after >30 minutes of inactivity, the prefix will bill again.

Examples (quick math):
1) Heartbeat example (no concession):
- Heartbeat payload: 6 tokens per call
- Rounded to quantum (16) => billed 16 tokens per heartbeat call
- If heartbeats every 30s for 1 hour => 120 calls * 16 tokens = 1,920 billed tokens per hour

2) Long chat with prefix reuse (typical):
- First request includes 1,500-token prefix + 60-token user prompt => billed 1,560 tokens (rounded up to quantum: 1,560 -> 1,568 since we round to 16).
- Subsequent follow-ups (10 tokens) => rounded to 16 tokens each. So the effective amortized cost of the prefix is large on the first call and negligible on subsequent short calls while the session stays warm.

Pilot concession we can offer (preliminary):
- For a 3-month pilot, Redwood can apply a 50% credit on billed tokens attributed to heartbeats (as defined above) for sessions where inter-call gap <= 60s, capped at 250k billed tokens / month.
- KV reuse window for the concession: prefix amortization holds while the session remains open; if the session is re-established later we treat it as a new session.

I attached a simple workbook with the above math and a sample per-100k-session estimate. Let me know which volume band you're targeting and I'll ask Marissa to model discounting/commit tiers.
