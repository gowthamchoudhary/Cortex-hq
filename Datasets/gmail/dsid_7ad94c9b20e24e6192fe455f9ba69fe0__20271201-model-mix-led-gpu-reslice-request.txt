Thanks for the sample, Daniel — reviewed offline with infra team. High level recommendation (model-mix-led reslice):

- Observed pattern: frequent short peaks with high KV-cache churn for the new family; throughput per GPU for that family is lower due to longer context and retrieval overhead.
- Near-term (fast): provision a 10–slot hot-standby tranche sized to ~20% of observed peak concurrency. This is non-disruptive and can be validated in 24–48h.
- Medium-term (preferred): reslice committed fleet to adjust model mix. Specifically: convert ~4 H100 equiv (current reserved) into denser mixed-instance slots optimized for the new family (quantization-friendly kernels + larger KV-cache per slot) and add an incremental 8 H100 equiv to raise peak headroom. That maps to the attached reslice_plan.xlsx with node-level layout and expected p95 improvements.
- SLA impact: with the reslice + added headroom we project p95 latency reductions of ~18–28% during peak and eliminate most breach risk. We recommend a 72-hour canary route with 5–10% traffic before full cutover.
- Risks / ops notes: workloads with long context windows will still see increased token cost; recommend enabling prefix/KV caching where safe. We'll need a short validation run during your next low-traffic window to tune batching parameters.

I've attached the node mapping and a step-by-step change window (reslice_plan.xlsx). Laura — once Daniel confirms, please prepare the amendment redline and a DocuSign wrapper we can present.
