Elena —

Adding technical detail to support Irene's note.

- CMK integration: Redwood Private supports external KMS via the standard KMS-Connect adaptor. We only receive wrapped keys; unwrapping is performed inside the customer-hosted HSM boundary or a customer-controlled KMS gateway. We do not persist unencrypted key material in any Redwood-managed storage. Key rotation can be initiated by AnthroSys; we support automated rewrap and rolling key rotation with zero-downtime options for the inference runtime.

- Operator actions: the only operator flow that would require access to anything encrypted is a disaster recovery snapshot restore where, under existing architecture, the operator would request a temporary key unwrap to validate the integrity of a restored model environment. For the pilot we propose:
  * Scope: explicit to AnthroSys pilot project ids only; no other tenants.
  * Approval: JIT request opened by AnthroSys via our private console (linkable) + email attestation to legalops@anthrosys.com.
  * Access window: max 2 hours per event, single-use signed token tied to operator identity.
  * Audit: live recording of session metadata + collection of operator commands (redacted for secrets), retained for 90 days and exported to AnthroSys on request.

- Telemetry & subprocessors: operational telemetry we collect (CPU, memory, GPU utilization, request latencies, error rates) will be identified as non-content and can be routed to EU-only storage. Content logs (input/outputs) will default to customer-controlled retention and can be disabled. Our infra subprocessors in EU are: OVHcloud (infrastructure), LogEU (log storage provider). Non-EU subprocessors (for backups and vendor-support) will be limited and contractually prohibited from accessing content.
