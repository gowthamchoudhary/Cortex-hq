Hi all — technical note from Redwood on the proposed throughput/validation plan so Seraphim can confirm requirements before the pilot: 

Summary of proposed targets (initial):
- Pilot pool size: 4 x H100 80GB-equivalent GPUs (we can size to A100/H100 depending on model)
- Target sustained aggregate throughput: ~4,000 tokens/sec across the pool for standard 512-token sessions (roughly 1,000 tokens/sec per GPU for the selected 7B-13B family variants in eval)
- P95 latency target: < 120ms for 256-token responses (our continuous-batching + KV cache configs will help for repeated prefixes)
- QPS target: 25–40 concurrent requests depending on batching and prompt length; will refine after we see real prompt distributions

Validation plan:
- Redwood to run baseline throughput tests using the same prompt set (we’ll provide a test harness) and publish per-GPU token/sec numbers to the shared sheet.
- Seraphim to provide a de-identified eval corpus (up to 5k prompts) and acceptance criteria (accuracy/clinical regressions can be simple pass/fail checks).
- We’ll instrument token-level cost reporting and p95/p99 latency dashboards during pilot (visible in Redwood Console).

Notes & constraints:
- If you plan to use larger context lengths (1k+ tokens) we’ll need more GPU memory or smaller batch sizes which will impact qps; please flag if that’s in scope.
- For the pilot we’ll use quantized model variants where appropriate to reduce cost; we’ll document expected quality delta in the MAP eval section.

Let me know if you want a short technical sync (30 min) before the pilot so we can agree on prompts and runbook for regression failures.
