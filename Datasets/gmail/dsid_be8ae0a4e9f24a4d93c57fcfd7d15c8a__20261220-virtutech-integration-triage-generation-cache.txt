Thanks — quick summary from runtime: we shipped a micro-optimization three weeks ago that changes how we flush cached KV segments for prefix-heavy workloads. In most cases it reduces latency, but we introduced a guard that can race with final chunk emission when an upstream cache read returns an EOF-like sentinel. That could explain the deterministic ~580 token cutoff (same buffer size across requests).

Immediate mitigation: temporarily disable the embeddings client-side cache or set cache TTL to 0 for the integration while we triage. Longer term: I'll prepare a small runtime patch to change the sentinel handling and add a safe drain step on the flush path.
