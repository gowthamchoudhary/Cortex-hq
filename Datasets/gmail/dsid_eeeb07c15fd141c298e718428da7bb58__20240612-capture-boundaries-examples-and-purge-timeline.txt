Sam — thanks for the clear ask. Below is a concise, example-driven breakdown you can forward to the compliance team. Attaching a one-page retention matrix and a simple data-flow diagram (see attachments).

Summary (hosted EU region — default behavior):
- Request payloads (user prompts / request bodies): stored by default for 30 days. Example: a chat message and the full prompt text will be retained for 30 days from creation unless the customer enables no-store.
- Model outputs (final responses): stored by default for 30 days. Streaming partials are NOT written to persistent stores by default; we only persist the final response unless the session recording feature is enabled.
- Prompt derivatives / logs (parsed tokens, token counts, generation metadata): retained for 90 days for debugging and quality monitoring; these are aggregated in telemetry dashboards and can be configured to a shorter window.
- KV caches / in-memory session state: ephemeral per session and NOT persisted to disk by default. They are cleared when the session expires (typically within minutes/hours).
- Embeddings / artifacts produced by explicit embedding APIs: stored only if the customer opts-in to embedding storage (default is not to store embeddings unless the API call specifies storage).
- Attachments referenced in requests: we store attachment metadata and the file itself only if the customer uploads assets to our storage; retention follows the same 30-day default unless otherwise configured.

Deletion and purge behavior:
- Customer-initiated deletion (Console/API): immediate soft-delete from active indexes; full irrecoverable purge is scheduled and completed within 30 days of the delete request across the primary stores. Some long-term backups are retained for disaster recovery and are rotated per our backup retention schedule (up to 180 days), but those backups are encrypted and access-controlled and are not used for serving.
- Legal / regulatory holds: if a legal hold is requested, the normal deletion/purge schedule is suspended until the hold is lifted.
- Account-level opt-out/no-store: we support a per-request header (x-redwood-store: false) that prevents a request and its outputs from being written to persistent logs or derivatives; opt-out takes effect immediately for new requests.

Residency specifics (EU region):
- Data stored by the inference path (request/response artifacts) remains in the EU region storage by default for customers who select the EU region.
- Control-plane metadata (billing records, some usage aggregates) are processed in our global control plane and may be stored in the US for operational reasons; we minimize identifiers in control-plane aggregates and provide enterprise customers with options for dedicated control-plane agreements under Private/Dedicated deployments.

Adding a couple of clarifying points on residency and operational controls: 

1) Control plane vs data plane: Kimberly covered this well — for hosted EU customers the data-plane artifacts remain in EU storage. Control-plane signals (billing, high-level usage metrics) are aggregated and might transit through our central control plane. For customers with strict residency requirements we recommend Redwood Private or a Dedicated contract where both control plane and data plane can be constrained to the customer's VPC/region.

2) Backups / snapshots: our snapshots for disaster recovery are region-scoped (EU) by default for EU accounts. There are operational backups that we may retain for up to 180 days; these are encrypted and access-limited.

3) API / technical opt-outs: the x-redwood-store header is the simplest for per-request no-store. We also support account-level retention policies (Console > Data Controls) that change the default windows (e.g., set request retention to 7 days).

4) Example enforcement timeline: if a user triggers an account-level purge today, the data is removed from active stores within minutes and a background job completes the irreversible purge across all replicated stores within 30 days. For EU-residency customers requesting deletion we follow the same timeline but ensure purge jobs run inside EU region data stores.

Happy to explain to your security team in a call and walk through the retention matrix.
