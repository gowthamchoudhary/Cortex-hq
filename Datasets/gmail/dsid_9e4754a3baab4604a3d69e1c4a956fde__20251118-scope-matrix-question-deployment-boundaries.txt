Hi Julie — short, then detail below.

Short answer:
- Redwood SOC 2 Type II (latest report attached) covers Redwood-hosted API endpoints and Dedicated capacity that is provisioned and operated by Redwood (i.e., Redwood-managed reserved GPU pools where we control the host environment, patching, and key management).
- Customer-managed Dedicated instances (where the customer runs the nodes and manages networking or keys) and Private/on-prem deployments are out of scope for Redwood's SOC 2. For those, we provide control descriptions, shared-responsibility matrices, and evidence where Redwood controls services we deliver (for example, software binaries and configuration management), but we cannot extend the auditor's opinion to infrastructure fully managed by the customer.
- We can issue a bridge letter that extends coverage language for Hosted + Redwood-managed Dedicated between the latest report period (ends 2025-06-30) and a target contract start (e.g., 2025-12-01) — the bridge is limited to the same control set and only covers periods where our production controls remained materially unchanged. The bridge cannot opine on customer-managed environments (Private/VPC/on-prem).

Details / suggested wording:
- "Redwood Inference certifies that the controls described in the attached SOC 2 Type II report remained in effect, without material change, from 2025-07-01 through 2025-11-30. This attestation applies to Redwood-hosted API services and Dedicated capacity operated and managed by Redwood. Customer-managed / on-prem environments are outside the scope of this attestation."

What we can provide for Private / VPC / on-prem:
- Deployment-specific control mapping (control owners, evidence paths).
- Configuration and hardening guides, audit logs for Redwood-managed components, and a carve-out list describing controls the customer must own.
- An engineer-signed configuration attestation for the Redwood-delivered artifacts (not a SOC 2 attestation).
