Thanks for the heads-up and the log dump, Tessa. Quick notes from initial triage:

- Reproduced locally on a Dedicated-like dev rig with similar workload: multiple concurrent streaming sessions where underlying KV cache growth plus aggressive batching leads to backend connection churn. We see runtime evictions when memory pressure surpasses the per-connection soft limit.

- Short-term runtime mitigation (can be rolled to a pool-level flag): increase keepalive interval + extend the connection grace window from 30s -> 90s and reduce eviction aggressiveness for warm sessions. This should reduce 1006 closes while we root-cause exact cache growth curve. I can schedule a pool flag flip for GreenFin's dedicated pool — ETA 3 hours with monitoring.

- SDK ask: we support per-request metadata but don't currently provide a first-class 'affinity_key' that signals session stickiness to the router. Implementing that in the SDK and adding a lightweight server-side routing hint would be the clean fix to avoid cross-connection KV cache misses. Implementation estimate: 2 sprints to build + 1 sprint for QA.

- Workaround for this week (what we can tell the customer now):
  * Reduce parallelism to <=8 concurrent streaming sessions where possible.
  * Enable client keepalive pings (JS SDK: manual heartbeat every 20s) — I will draft a short snippet.
  * We'll flip the pool-level grace flag (non-disruptive) and monitor.
