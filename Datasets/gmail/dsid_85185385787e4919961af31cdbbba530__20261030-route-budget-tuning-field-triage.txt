I've pulled the trace — thanks Raj. Quick notes from runtime triage:

- The p99 spikes look like two things combined: (1) large cross-tenant coalesced batches where a long prefix from one request extends kernel execution for others, and (2) occasional preemption when GPU utilization is saturated and weights are swapped for quantized kernels.
- The current runtime uses a dynamic batching window and groups requests by model and sequence length; we don't currently support per-route token budgets.

Short-term options (hours-days):
1) Soft priority header (fast): implement v1 where requests with X-Redwood-Priority: low are placed at the back of the batching queue. No hard guarantees; this requires a small routing change (~1 day dev + 1 day canary).
2) Per-route isolation toggle (medium): pin a specific route to a dedicated batching lane to avoid coalescing with noisy neighbors. This gives stronger isolation but consumes more capacity and needs infra changes (~2-3 sprints).
3) Client-side mitigation (immediate): add a small jitter or split the scheduled job into micro-bursts to reduce instantaneous concurrency.

I've opened a Jira to track the work: SUP-3142 — "Per-route priority/isolation for batching". I've attached the p99 trace and included a short snippet of the kernel timing that shows the long tail (see attachment). For the demo, option 1 (soft header) seems fastest and least disruptive.

Request for Raj: can you share the rate profile for the scheduled job (peak qps, typical request token sizes)? That will help size the lane if we go for isolation.
