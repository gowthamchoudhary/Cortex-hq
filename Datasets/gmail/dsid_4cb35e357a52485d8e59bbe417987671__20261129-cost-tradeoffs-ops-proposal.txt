Samir — quick technical reply to the two asks so procurement has numbers to work with.

1) Cache redaction/hashing approach (short):
- We recommend a two-layer keying scheme: (a) canonicalized prompt fingerprint (normalized whitespace + placeholder tokens for personally-identifying slots), and (b) optional hashed customer identifier for namespace partitioning.
- PII fields (SSN, full card numbers) are replaced with deterministic placeholders at the tokenizer layer and never used as part of the cache key or persisted. For traceability we log the cache key fingerprint and a boolean flag indicating whether a sensitive field was redacted; logs do not contain the raw PII.
- We will provide a one-page technical appendix for the SOW describing the redaction flow, hashing algorithm (HMAC-SHA256 with customer-managed salt available in KMS), and retention/rotation guidance.

2) Batching impact on tail latency — measured numbers (from our A/B perf runs on similar chat workloads):
- 150ms window, mean token latency: ~120ms; 95th token latency: ~360ms; 99th token latency: ~760–820ms depending on sequence length.
- 250ms window, mean token latency: ~160ms; 95th token latency: ~480ms; 99th token latency: ~950ms.
- Practical recommendation: start pilot at 150–200ms window and enable burst bypass for interactive chat requests (route <50ms queueing to a low-latency pool). That keeps 99th p95 within target while still getting ~3–4x batching efficiency for throughput-bound flows.
