Alex / team — dug into our replication telemetry. High level: 

- Replication topology: for private deployments we use a single-primary KMS cluster in-region with asynchronous fan-out to secondary replicas in the standby region. We ship write-ahead events over an encrypted replication channel.

- Observed replication latencies (EU primary → APAC replica, last 90 days): p50 ≈ 120ms, p95 ≈ 420ms, p99 ≈ 1.4s. Under network stress (peering maintenance, 10–30% packet loss windows) we've seen spikes up to ~3.5–4.2s in extreme cases.

- Operational knobs we can expose to Acme: 
  1) Confirm-before-cut: an API call that returns per-tenant replication status (boolean: all-kvs-replicated) so the orchestrator can hold switching ingress until true. Adds ~50–150ms for verification.
  2) Proxy-forward mode (recommended if you need <1s cutovers): we route key unwrap requests through a TLS passthrough to the EU KMS until replica is confirmed; cost is additional hop and tail latency but avoids failed unwraps.
  3) Graceful-degrade policy: if replica lag ≥ 2s we recommend partial traffic hold and notify both sides; full auto-rollback is risky unless you block new session establishment during the window.

- KMS consistency guarantees: not strongly consistent across regions by default. If you require strict cross-region consistency we can discuss a synchronous-ack variant (write-through) for your account; tradeoffs: write latency increases to p50≈400ms, p95≈900ms.
