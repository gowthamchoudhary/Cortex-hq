Hi Hannah — thanks for the detail and the template. Looping in Monica (CS lead), Jordan (solutions/implementation), and Ben (inference/throughput) so we can give grounded recommendations before the kickoff.

At a high level, here are an initial candidate set and a few notes:

Model shortlist (initial recommendations)
- RedSeal-7B-int8 (cost-efficient; good for standard chat, fast latency for short contexts)
- RedForge-13B-q4f16 (balanced quality/cost; wider context handling up to ~8k tokens)
- OpenFast-70B-fp16 (highest-quality fallback for the 1–5% of requests requiring best-in-class summarization or complex reasoning)
- Embeddings: RedEmbed-3B or OpenEmbed-2B (depending on precision needs; RedEmbed cheaper/fast)

Configuration & tradeoffs
- Context windows: recommend planning for two lanes — a 8k lane for most chat and a 16k lane for document/receipt summarization. If you can confirm the max receipt size, we can refine.
- Caching: prefix/KV caching will help recurring conversational turns and templated prompts (expect ~8–12% token savings typically).
- Routing: route short chats to RedSeal-7B-int8 and overflow/higher-quality to RedForge-13B; set an automatic fallback to OpenFast-70B for specific high-value flows.

Thanks — added some concrete math below so the team has a baseline to work from. Quoting Hannah's usage assumptions above for reference.

Summary assumptions (from Hannah):
- MAU 250k, DAU 20k, chat penetration ~3% of DAU => active chat users/day = 600
- Average sessions per active user: 1.2
- Avg prompt length (conservative): 500 tokens; avg response: 200 tokens
- Avg turns per session: 4 turns (2 prompts from user / 2 responses from model)

Per-session token estimate (approx):
- Prompts: 2 * 500 = 1,000 tokens
- Responses: 2 * 200 = 400 tokens
- Overhead (system + metadata): ~200 tokens
- Total/session = 1,600 tokens

Daily chat token volume: 600 active users * 1.2 sessions/day * 1,600 tokens = ~1,152,000 tokens/day (~1.15M)

Embeddings & other flows:
- If 10% of DAU use a search/embedding flow with 3 calls per user at ~512 tokens input each => 20k * 0.10 * 3 * 512 = ~307,200 tokens/day (~0.31M)

Combined estimated tokens/day (baseline): ~1.46M tokens/day

Peak sizing / QPS estimate (worst-case 3 peak hours/day):
- Assume 40% of daily traffic occurs during 3 peak hours => tokens in peak window = 0.40 * 1.46M = ~584k tokens across 3 hours => ~194.6k tokens/hour => ~54 tokens/sec average over peak hours.
- For short chat requests (~700 tokens total/request), that maps to ~0.08 requests/sec average. But spikes may concentrate: plan for 4–6x burst capacity => design for ~0.5 rps sustained during peaks and occasional 2–3 rps bursts.

Serving recommendations (initial):
- Primary lane (short chat, low-latency): RedSeal-7B-int8. Expect sub-500ms token latency on optimized runtime for prompts <=1k tokens.
- Mid lane (context up to 8k): RedForge-13B-q4f16 for 70–80% of complex multi-turn sessions.
- High-quality lane: OpenFast-70B-fp16 as a fallback for receipts/long summarization (1–5% of requests).

Pool sizing (ballpark):
- Host RedSeal-7B-int8 on 2x A10/A100-equivalent nodes (handles short-chat baseline + buffer).
- RedForge-13B-q4f16: start with 2x A100-80GB-equivalent with autoscale policy (target 60% CPU/GPU util).
- OpenFast-70B: consider shared on-demand capacity (not dedicated) unless ClearPay wants guaranteed latency for long summaries.

Operational mitigations to reduce cost/latency:
- Prefix/KV caching for returning conversations (12% savings estimate).
- Minimize model context by extracting relevant receipt sections (we can help design prompt templates).
- Use batching for embeddings calls (saves token overhead and GPU utilization).
