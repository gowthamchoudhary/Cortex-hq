Gina —

Thanks for raising these. Below is a concise, factual summary you can use in your InfoSec packet. If you need us to insert an explicit contractual sentence we'll propose language for the DPA/Service Agreement.

1) Model training / weight updates
- Redwood does not use Customer Content (plain text payloads, attachments, or user prompts) to train, fine-tune, or otherwise update weights on our general-purpose or publicly served models as a matter of default operational practice.
- We differentiate between (A) raw Customer Content and (B) aggregated, de-identified telemetry. Only the latter may be used internally to improve platform reliability/performance (for example, tokenization edge cases, latency histograms). Those telemetry products remove any customer identifiers and do not contain plaintext customer submissions.
- For enterprise customers, we offer an explicit contractual "Model Use" option to prohibit any internal use of even aggregated telemetry. This is typically codified in the DPA or an addendum.

2) Retention windows (defaults for hosted API customers)
- Request/response payloads: retained 30 days by default for debugging and abuse detection.
- Real-time KV/cache (hot memory): ephemeral; data exists in-memory for the request/session and is not persisted by default.
- Snapshotting for operational reasons (pre-warm/debug snapshots): retained 30 days by default if snapshotting is enabled. Snapshots are not used to train models.
- Automated backups and service-level snapshots: retained 90 days by default for disaster recovery.
- Structured telemetry and logs (alerts, request metadata, not payload): retained 365 days by default.

3) Exceptions and options
- Dedicated and Private deployments: retention windows are configurable and can be reduced in contract (including options to disable snapshotting and limit telemetry retention).
- Debugging window: with customer approval we may retain a targeted snapshot up to 72 hours longer to investigate incidents; this is logged and requires an incident request id.

4) Deletion process & evidence
- Deletion request flow: customer opens a support ticket referencing the account and object ids → we schedule deletion in the next maintenance window → deletion actions are recorded in our audit system and the ticket is updated.
- Proof artifacts: we can provide the deletion_action_id (audit log id), a timestamped audit entry, and a signed confirmation letter. For file objects we can optionally provide a SHA256 hash of the object prior to deletion along with the deletion entry.

5) Backups & immutable archives
- Backups are treated separately; backup retention is 90 days by default and backups are rotated. If customers require shorter backup retention or request immediate removal we will engage our ops team and provide the audit evidence.
