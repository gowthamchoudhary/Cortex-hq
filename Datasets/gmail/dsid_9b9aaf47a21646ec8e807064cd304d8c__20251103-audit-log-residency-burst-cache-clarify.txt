Elena — thanks for the clear list. High level answers up front, then I followed with the technical notes and attachments.

High level:
- Audit logs (request metadata, routing events, operator actions) are stored in the region the tenant is pinned to by default. For FinPay (EU pinning option) we can ensure logs are written to EU storage.
- Temporary cache replication for burst scaling is supported but strictly transient: default max TTL is 5 minutes (configurable by customer up to 15 minutes with appropriate controls), never persisted to durable blob storage, and excluded from backups.
- Replicated state contains limited runtime KV cache (model keys and prefixes) and operation metadata; we do not replicate full request/response payloads. PII is redacted by default from caches; request traces are handled per DPA logging controls.

Draft technical commitments:

  - If failover requires writing to ephemeral local disk (only in extreme crash scenarios), such writes are encrypted and scrubbed within 30 minutes and never included in scheduled backups.
  - Backups and retention policies explicitly exclude transient replication buffers."
- Data content: "Transient replicated state excludes full request/response bodies. We replicate model KV entries and routing state; PII is masked/redacted before caching per the customer's configured masking rules. Full request logs remain in the pinned-region audit store only."

Elena — following up with a concise, customer-ready response and next steps.

Customer-ready commitments (summary):
- Audit logs: For customers that choose EU pinning, all inference audit logs (metadata, routing events, operator actions) will be written and retained only in EU storage endpoints. For US-pinned tenants, logs are stored only in US endpoints. We will not replicate audit logs across regions for normal operations.
- Short-lived replication during bursts: We use transient KV cache replication to warm cold workers during burst autoscale.
  - Default TTL for replicated cache: 5 minutes.
  - Maximum configurable TTL with signed addendum: 15 minutes.
  - Persistence: replicated cache is kept in-memory or on ephemeral VM local storage, never written to durable object stores (S3/GCS) for the purpose of caching.
  - Backups/retention: replicated cache explicitly excluded from backups and scheduled retention.
  - Content: replicated state contains model KV entries and routing metadata only; full request/response payloads and raw PII are not part of this replication. Redaction is applied by default.
- Key management: We support customer-managed keys (CMKs) for Dedicated and Private deployments; CMKs can be provisioned in the pinned region (EU options available). Hosted customers may request EU-managed keys as part of an enterprise addendum.
