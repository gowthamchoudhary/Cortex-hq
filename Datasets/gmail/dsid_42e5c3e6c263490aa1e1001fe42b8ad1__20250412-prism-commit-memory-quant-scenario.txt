Summary (three scenarios):

1) Conservative / no quantization (baseline)
- Model: Llama-3-70B FP16 serving footprint (no offload): ~280 GB replica RAM for weights + ~55 GB for 32k KV-cache (per-replica when full 32k KV present) = ~335 GB total replica working set.
- Recommendation: reserved pods sized to host 1 replica per 80 GB GPU using multi-GPU sharding (approx 4 x 80GB GPUs per replica) — pilot recommended commit: 12 GPUs (3 replicas) to support ~15 rps for 32k-heavy mix.

2) Mixed quant (8-bit runtime + FP16 KV)
- 8-bit model quant reduces weight storage to ~150-160 GB; KV-cache kept in FP16 or 8-bit depending on hit-rate; with FP16 KV for 32k context add ~55 GB => ~210-220 GB replica footprint.
- Recommendation: 2 x 80GB GPUs per replica (NCCL sharded) or 1 x 80GB + NVLink pairing depending on topology. Pilot commit: 8-10 GPUs (4 replicas) to hit target throughput with headroom.

3) Aggressive quant (4-bit / QLoRA-style runtime) + KV offload
- 4-bit lowering can push the model storage down to ~90-110 GB. If KV offload to host or tiered NVCache is enabled, per-replica GPU memory requirement can be ~120-140 GB.
- Recommendation: conservative production commit: 10-16 x 80GB GPUs (distributed across 6-8 replicas) with KV offload config.

KV-cache notes (impacters):
- 32k vs 16k: moving from 16k -> 32k increases KV by ~1.8x-2.0x depending on tokenizer and chunking.
- Hit-rate assumptions matter: at 60% KV hit-rate effective GPU memory pressure drops significantly; at <40% you need more replicas to avoid eviction throttling.
