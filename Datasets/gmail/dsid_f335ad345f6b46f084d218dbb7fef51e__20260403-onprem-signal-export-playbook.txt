Per request, attached is a concise playbook outlining the options we support for exporting logs, metrics and traces from a Redwood Private deployment (VPC / on‑prem) into customer SIEMs and observability stacks. This note focuses on pragmatics for air‑gapped or egress‑restricted environments and recommended configurations that preserve PII minimization and SLOs for telemetry delivery.

High‑level options (ranked by simplicity / customer operational burden):

1) Local collector -> Push to customer SIEM (preferred for private cloud)
   - Deploy an OTLP/Fluentd/Vector collector inside the customer VPC (sidecar or daemonset).
   - Collector consumes stdout/files/syslog from Redwood runtime components or accepts OTLP/gRPC directly.
   - Forwarders translate to Splunk HEC, syslog/tcp, or HTTPS endpoints using TLS client auth.
   - Benefits: no egress from customer environment to Redwood; full control of retention and parsing.

2) Encrypted, batched export to a controlled endpoint (hybrid)
   - Collector batches and uploads to a preconfigured private s3 (minio) or SFTP gateway in a DMZ, which the customer’s SIEM pulls from.
   - Use envelope encryption (KMS) to keep logs encrypted at rest.
   - Good fit when direct SIEM ingestion is restricted but outbound is allowed to specific host/port.

3) Controlled egress to Redwood (for customers who want Redwood to perform long‑term retention / analytics)
   - Use an egress proxy with strict allowlist (IP + host) and mTLS.
   - All payloads are encrypted and redacted per customer policy.
   - Not available for air‑gapped; requires contract and network review.

Core security controls we recommend (non‑exhaustive):
- PII redaction: collectors must run configurable redaction rules (regex, jsonpath) before forwarding.
- Sampling & rate limits: implement tail‑sampling for traces and adaptive log sampling to protect downstream SIEM cost budgets.
- Backpressure handling: collectors use bounded queues + local disk spool for short spikes; monitor spool growth.
- Authentication: prefer mTLS client certs or HEC tokens for Splunk, avoid basic auth.
- Key management: integrate with customer KMS/HSM for envelope keys; do not store unencrypted keys in config.

Mapping notes for SIEM parsers (example: Splunk):
- Logs: include metadata fields: service, env, hostname, container_id, request_id, trace_id.
- Traces: export via OTLP -> translate to zipkin/x‑ray style spans if the SIEM requires it.
- Metrics: prefer Prometheus remote_write or pushgateway pattern if pull is not possible.

Quick answers inline:
1) Yes — collector runs as DaemonSet with RBAC that only reads pod logs via the Kubernetes API (or node file socket) and can be scoped to a namespace. We recommend running a dedicated telemetry namespace and limit ServiceAccount privileges to only what is needed.
2) We support OTLP over gRPC with gzip compression and protobuf batching; the OTLP collector config in the attachment shows default batch_settings optimized for bursty traffic.
3) mTLS is preferred for Splunk HEC when possible; if Splunk is behind a reverse proxy that terminates TLS, HEC token + IP allowlist is acceptable. Also consider short‑lived tokens rotated by Vault.

Additional operational notes:
- Trace context: ensure all Redwood runtime components propagate W3C traceparent and baggage headers; include a light instrumentation shim in the ingress layer if customer LB strips headers.
- Metric cardinality: cap labels from user input and high‑cardinality fields; use relabeling rules in Prometheus/collector.
