Triage update / tech notes:

What I see: KV eviction churn on the tenant's priority namespace starting 08:46 PDT (logs attached: kv-config-dump.json). Evictions coincide with a flood of distinct prefix keys from autocomplete, which pushed the working set beyond the reserved capacity. When the KV layer starts evicting, request handlers stall waiting for prefetched keys to populate -> head-of-line for priority lane requests. Batching exacerbates this because several requests in the same batch block on a single missing key fetch.

Immediate actions taken (10:00):
- Disabled tenant-level prefix prefetch for TopSpin (rolling change applied)
- Applied a temporary increase to priority-lane cache reservation + raised eviction threshold for 20 minutes
- Reduced in-flight batch size cap for the priority lane from 64 -> 20

Observed effect: p99 improved from ~1800ms -> ~520ms in the first 6 minutes, 5xx rate down to ~0.6%. Throughput recovering towards baseline but not fully there; still seeing tail jitter tied to a small set of very large prefixes.

Next steps (recommended):
- Keep prefetch disabled and monitor for 30 minutes
- Run a targeted rebalancing job to compact the prefix namespace for TopSpin (requires coordination with customer to limit the autocomplete burst)
- Build a short-term guard in the serving runtime to break batches when a batch contains >2 long-prefix keys to avoid full-batch HOL stalls (short-term knob, medium-term runtime change)

I'll keep this incident on my queue. If we still see >1% 5xx after the 30m window, we escalate to fallback routing.
