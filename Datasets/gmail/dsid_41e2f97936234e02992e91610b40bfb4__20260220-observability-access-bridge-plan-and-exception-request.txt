Hi Jae — thanks for the clear list. Answering inline below and attaching a short evidence packet (SLO_evidence_packet_v1.pdf) and a read-only Grafana invite file.

1) SLO definitions:
- Availability: measured as percent of successful inference responses (HTTP 2xx/3xx) over total API requests, calculated as 1 - (5xx_count / total_requests). Client-side network failures are excluded if they don't reach our edge. 4xx are considered client errors and are excluded from availability SLOs unless caused by server misconfiguration.
- Latency (P99): server-side end-to-end time from request ingress to final token emission for text-gen calls. P99 is computed on the distribution of successful responses (exclude requests that returned 5xx). We publish both P95 and P99 percentiles.

2) Measurement window & sampling:
- Default rolling window: 30-day rolling for SLO calculations; 90-day and 365-day aggregates for trend analysis.
- Sampling: we compute per-request metrics at ingestion and roll up to minute-level aggregates in Prometheus. For extremely high-volume customers we use adaptive sampling for raw traces but keep accurate percentile stats via HDR histograms so percentiles remain stable.
- Cold starts: we flag and exclude container cold-starts from latency SLOs when they are attributable to infra-scale events (documented in the incident metadata).

3) Monitoring & retention:
- Stack: Prometheus for metrics, Grafana for dashboards, Jaeger for traces.
- Retention: minute-level metrics retained 365 days; high-resolution raw traces retained 30 days by default. Longer retention is available as an add-on. Audit logs (API request metadata) can be exported to a customer-controlled S3 bucket for 365 days.

4) Alerting & escalation:
- Default alerting: pages on availability drop >0.5 percentage points sustained for 5m (on high-sensitivity plan) or 1 percentage point for 10m (standard). P99 spike alerts: >2x baseline sustained for 10m.
- Escalation: on-call -> on-call lead -> engineering manager -> platform reliability. For enterprise accounts we add a named TAM and a dedicated Slack channel.
- Maintenance windows: we support scheduled maintenance windows where alerts are suppressed and SLO breaches can be marked as planned (requires documented maintenance window in the console).

5) Customer access:
- We provide read-only Grafana dashboards (link provided in attachment) and a filtered time-series export (CSV/Prometheus remote_read) for audit purposes.
- Raw request logs (redacted for PII) can be delivered to your S3 for the agreed retention period. Access is role-based and audit-logged.

Evidence: attached SLO_evidence_packet_v1.pdf with sample uptime reports, P99 exports and a monitoring architecture diagram. SOC2 report is available under NDA — we can route that to your security team.

Next steps: if BrightHarbor expects a planned migration or maintenance that might impact latency, we can document a temporary SLO waiver (exception) with a fixed window and mitigation steps. If you send dates we can prepare the waiver and the required form.
