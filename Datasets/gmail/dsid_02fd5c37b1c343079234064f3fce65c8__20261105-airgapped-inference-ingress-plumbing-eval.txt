Anya — thanks for the context and SOC2 snippet. High level summary up front: PrivateLink (interface endpoints) is typically the lowest blast radius and simplest from a security posture standpoint for our runtime APIs; S2S VPN is an acceptable fallback for bulk traffic when customers require on-prem-only egress or strict IP controls; VPC Peering often looks attractive for latency but fails hard on transitive routing and scale for multi-account setups.

Key tradeoffs in bullets (more detail below):
- PrivateLink: minimal routing changes, private IP-space isolation, endpoint policies; needs ENIs and subnets; adds per-GB interface data charges; works well w/ mutual TLS.
- S2S VPN: supports strict control, can be IPsec BGP for resilience; public internet exposure for tunnels; watch MTU and throughput caps; simpler for air-gapped datacenter bridges (vendor-managed MPLS/SD-WAN can be used).
- VPC Peering: direct L2/L3 peering inside cloud; excellent latency but no transitive routing and limited cross-account governance; peering across regions is harder/expensive.

Operational gotchas we should call out:
- ENI scaling: interface endpoints create ENIs per AZ — plan subnets and IPs.
- Hairpin/NAT: if your app and endpoints are in the same VPC space, hairpin NAT can appear; avoid asymmetric routing by centralizing NAT gateways or using endpoint-based DNS records.
- MTU: IPsec reduces MTU; for large payloads you may need DF handling or TCP MSS clamping.
- Certificate lifecycle: mutual-TLS recommended; need automated rotation and CRL/OCSP paths that don't break air-gapped constraints.

Recommendation (short): For VaultBank given SOC2 and no public IPs, propose PrivateLink-based interface endpoints for control-plane and short-lived inference calls (low latency), plus a dedicated outbound egress relay (customer-owned VM in their VPC) for model telemetry and larger payloads over a customer-managed S2S if they insist on on-prem-only egress. This hybrid minimizes blast radius while giving you operational control.

Anya — adding the data/ops perspective and a few concrete numbers you can use for capacity planning. Quoting Hannah below where relevant.

PrivateLink (interface endpoints)
- Latency: single-digit ms additional within same region (P95 often dominated by our runtime processing, not the endpoint hop); P95 ~ +5ms measured in similar setups.
- Throughput: each interface endpoint uses ENIs; throughput scales but you can hit per-instance ENI bandwidth limits if you push many concurrent streams from few IPs.
- Ops: endpoint policies allow scoping by principal/service; requires coordination for DNS (private hosted zone) to point your app to the endpoint CNAMEs.

S2S VPN (IPsec)
- Latency: variable due to public internet; if VaultBank has a managed MPLS or dedicated circuit, that improves predictability. We typically see P95 variance of 20–50ms over internet VPNs.
- Throughput caps: cloud-managed VPNs on AWS/GCP have soft limits (e.g., 1–2 Gbps baseline); for higher throughput use virtual appliances or Direct Connect/Partner Interconnect.
- MTU: IPsec overhead ~50–60 bytes; remember to test for fragmentation for large request/response patterns (embeddings payloads can be big).

VPC Peering
- Latency: best for intra-cloud low-latency; no traversal of public internet.
- Governance: cannot do transitive routing (so if you need access to other accounts/partners you must peer each pair), and peering cross-account requires careful IAM/account coordination.

Gotchas & mitigations
- ENI exhaustion: recommend reserving IPs in dedicated endpoint subnets and using /24s per AZ for headroom.
- DNS split-horizon: use Route53 private hosted zones or your internal DNS to ensure correct resolution to interface endpoints.
- Hairpin: avoid designs where traffic egresses the same subnet and returns; central NAT or explicit routing avoids surprises.

Anya — security lens additions. Apologies for the bullet list but this will make approval conversations faster.

PrivateLink pros (security):
- No public IPs on runtime; interface endpoints create ENIs inside your VPC with security groups — easy to tie into NAC rules.
- Endpoint policies limit who can call our service principals; reduces lateral access.
- Auditability: flow logs + endpoint flow logs + our runtime logs provide a clear trail.

PrivateLink cons (security):
- Requires accepting AWS interface endpoints; some audit teams flag ENIs as risk due to AWS-managed components.
- If you need deep packet inspection, interface endpoints may complicate inline appliances — you'd need a tap or mirror setup.

VPN pros/cons (security):
- VPN places crypto boundary on the public internet — acceptable for many banks if tunnels are to their routers; introduces endpoint keying and rotation concerns.
- We recommend mutual TLS on top of IPsec and strong algorithms (AES-GCM, SHA-2) and IKEv2.

Other considerations:
- KMS/HSM: telemetry and logs should be encrypted with customer-managed keys where possible.
- Fail-open vs fail-closed: recommend fail-closed for control-plane auth checks; we can implement exponential backoff for short outages.
- Patch window: PrivateLink minimizes need for inbound firewall exceptions during runtime upgrades.
