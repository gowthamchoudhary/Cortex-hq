Sophia — thanks for the clear list. High-level proposal below; attaching a concise backfill runbook (backfill-runbook-v1.pdf) and a link to the drive plan. Long answer short: we recommend a staged, shard-aware backfill with sampling-based quality gates + a feature-flagged cutover.

Planned sequence (summary):
- Prep: schema validation + small sample run (2k docs) to validate tokenization/embedding mapping.
- Stage 1 (off-peak): incremental backfill by shard / time window at 10% concurrency to warm caches and populate vector DB without heavy compactions. Monitor DB compaction lag and QPS.
- Stage 2 (scale up): increase to 40% concurrency after passing DB health gates for 24h. Run rerank smoke tests after each batch.
- Stage 3 (read-only verification): mirror queries to new embeddings + reranker; compare top-K outputs and MRR.
- Cutover: enable feature flag for a 10% traffic canary, monitor errors and quality metrics for 2 hours, then progressive rollout.
- Rollback: instant disable of feature flag + re-route to legacy embeddings. We also snapshot vector DB before Stage 3.

- Per-batch metrics: documents processed, per-batch token cost estimate, vector DB compaction/flush events, and top-K comparison diffs (sampled).

Adding technical constraints and recommendations from infra: 

1) Vector DB compatibility: Milvus has predictable compaction when writes exceed the memory threshold; we recommend writing with batch_size=5k docs and a 15s pause between batches to avoid triggering large compactions. If you can expose a write-throttle endpoint on your side, we'll coordinate to dynamically slow the backfill when compaction rate climbs.

2) KV cache / prefixing: for rerank we expect to preserve original query prefixes for 48 hours during cutover to avoid cache warmup regressions. We'll instrument TTLs for cached keys and include a 48h warm window in the runbook.

3) Sampling & eval: propose three sampling buckets — smoke (1k queries), regression (5k queries seeded from production slices), and acceptance (10k queries covering high-frequency user segments). For each bucket we'll compute MRR, Recall@K, and a simple semantic-drift score. Acceptance threshold: MRR improvement >= 0 or delta within ±2% for P@5.

4) Data isolation (multi-tenant): to guarantee no cross-tenant leakage, we'll namespace vectors with tenant-id as a prefix in the vector key and keep tenant-scoped snapshots. This requires a one-line change in your ingestion mapping (see attached embed_schema_v2.json).

Operational notes: we'll provide an S3 audit bundle and a CloudWatch-compatible metrics stream. Please confirm any compliance requirements for log retention.
