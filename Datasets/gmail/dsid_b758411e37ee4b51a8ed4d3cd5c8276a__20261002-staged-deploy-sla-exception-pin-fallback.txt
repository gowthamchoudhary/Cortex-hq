Marissa + team,

We can support the behavioural primitives Acme is asking for from the runtime side. High-level capabilities and constraints:

What we support today:
- Route-level version pinning: you can pin a route to an explicit model artifact id (e.g., model-x.y.z) for traffic percentage 0-100. Pinning persists across restarts until unpinned.
- Automatic fallback: we have a policy engine that can swap traffic to a fallback model when alarms fire. The fallback is executed as an atomic traffic shift to a pre-configured model-version.
- Traffic splitting + staged ramps: percentage-based splits with time-based ramps (we support step ramps and linear ramps down to 1% increments).
- Canary health checks: we ingest p50/p95 latency and error-rate windows (configurable 1m/5m) and can trigger rollback.

Recommended defaults (conservative, production-safe):
- Initial canary: 3% traffic for 10 minutes. If health checks pass, ramp to 10% over 20 minutes, then 50% over 1 hour.
- Rollback triggers: if p95 latency > 350ms OR error rate > 0.5% for two consecutive 1-minute windows, automatically shift 100% of the canary traffic back to pinned model-version.
- Pin duration: allow up to 72 hours as requested; we recommend an explicit review at 24/48 hours with SRE.

Operational caveats:
- Cold starts: pinning to an older or quantized model variant may have different latency profiles; we should pre-warm endpoints (we can schedule pre-warm to match canary ramp times).
- KV cache loss: switching model families (different tokenizer or architecture) can invalidate KV caches and temporarily increase latency — avoid cross-family fallbacks unless necessary.
- Observability: need ingestion of the customer's APM traces or at least request IDs to correlate errors; otherwise we only see platform-side metrics.

Implementation notes for contract language: we can promise the mechanisms (pinning, fallback) but cannot guarantee that a fallback will restore the customer's pre-change latencies if the regression is driven by model-internal quality rather than infra. That nuance should be in the amendment.

If useful I can draft a short ops playbook with step-by-step traffic split params and the exact policy YAML we would add.
