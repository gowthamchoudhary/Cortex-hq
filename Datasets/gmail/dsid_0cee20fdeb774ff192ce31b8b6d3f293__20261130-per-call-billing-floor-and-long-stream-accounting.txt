Sanjay — thanks for the clear examples and the spreadsheet. I pulled together succinct rules and two worked examples below. I'm looping in Ben (billing) and Neha (product) in case you want deeper technical detail.

Short answers (TL;DR):
- Per-call minimums: applied at the billing-mediate boundary — that is, each API request (HTTP or a logical websocket invocation) is measured independently unless requests are explicitly grouped by the customer into a single server-side call.
- Streaming sessions: we meter tokens emitted by the model; if the SDK/server makes multiple inference calls under the hood (e.g., chunked decodes), each inference contributes to the token count. There is no special automatic session-level aggregation unless you use our session-aggregation feature (opt-in for enterprise pilots).
- KV/prefix caching: cache hits reduce billed input tokens because we do not re-send cached KV state in requests; however, the model still generates output tokens that are billed as normal.

Worked examples (assume hosted pricing: $0.0008 per token, per-call minimum billed as 5 token floor when a request would bill <5 tokens):

Example A — Single long response (server issues a single inference that returns 3,000 tokens):
- Billed input tokens: 150 (prompt + context sent)
- Billed output tokens: 3,000
- Total billed tokens = 3,150
- Charge = 3,150 * $0.0008 = $2.52

Example B — Same response but server implements chunked decodes: 3 inference calls that return 1,000 tokens each; each call sent the same 150-token prompt (no session aggregation):
- For each call: billed = 150 (input) + 1,000 (output) = 1,150
- Three calls total billed tokens = 3,450
- Charge = 3,450 * $0.0008 = $2.76 (higher because prompt re-sent)

Example C — Many tiny calls pattern (100 requests, each returns 15 tokens):
- Per-request billed tokens before floor = prompt(20) + output(15) = 35 -> above 5-token floor so floor not relevant
- If there were sub-request cases where billed tokens <5, each would be rounded up to 5 before multiplying by price.

Notes / options for pilots:
- For pilot customers we can offer a temporary waiver of the per-call floor for a limited window (e.g., first 90 days) to avoid penalizing tiny-call telemetry. That's a contractual concession — Ben can scope that.
- If you want session-level aggregation (metering across a session/socket and bill the max context used rather than sum of repeated prompts), we have an opt-in feature (Enterprise: session-aggregation) that can be enabled. It requires a short integration change to tag requests as part of the same session.

Internal note — copying Marcus in finance for confirmation:
- Session-aggregation mode: we bill based on the maximum context included in any single attributed inference in the session (i.e., the max input tokens observed during the tagged session), not the sum across multiple calls.
