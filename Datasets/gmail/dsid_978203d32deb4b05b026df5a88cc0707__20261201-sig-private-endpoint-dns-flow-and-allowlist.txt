Alex — technical details below, plus attached artifacts. I'm the technical lead for connectivity; happy to jump on a short call if you want to walk this with your network team.

Summary (short): Private Endpoint = endpoint in your VPC (our service fronted by ENIs / endpoint network interfaces). DNS is split-horizon: your resolver(s) will return the private IPs for the Redwood service FQDNs. VPC peering = layer 3 routing, no endpoint objects provisioned by Redwood.

Detailed points:
1) Private Endpoint (Privatelink-style) behavior:
  - We create a customer-scoped endpoint in our control plane and provide a service name and a set of endpoint IPs mapped into your subnets.
  - DNS: For customers using the provided AWS Route53 private hosted zone (or equivalent in other clouds), the FQDNs we supply resolve to the endpoint IPs in your VPC. We recommend TTL=60s default; you can bump to 300s if you prefer stability over quick failover.
  - Where to allowlist: allow outbound connections from your app to the private endpoint IPs and allow inbound from our endpoint (NAT not required for in-VPC traffic).

2) VPC Peering behavior:
  - Peering requires adding route table entries in both VPCs. Traffic routes over the peering link; egress to the public internet still uses the egress side's NAT. If you peer, you should not need to allowlist Redwood public IPs for internal traffic, but any call that goes out to Redwood's public endpoints will follow public egress and would require allowlisting our published public egress IPs.

3) Egress IPs and static options:
  - Hosted API customers: we publish a stable set of public egress IP CIDRs that are updated quarterly (attached csv: redwood_ip_ranges_v2.csv). For higher stability we offer a Dedicated gateway or Private deployment where we can provide fixed NAT IPs (or place the endpoint inside your VPC).
  - If you require single-digit static IPs, we can provision a dedicated egress NAT for your account under a Dedicated contract; timeline ~2-3 weeks for allocation and testing.

4) SIG evidence and artifacts included:
  - redwood_vpc_private_endpoint_diagram.png — annotated topology showing endpoint ENIs, DNS flow, and route table examples.
  - redwood_ip_ranges_v2.csv — published egress CIDRs for hosted endpoints (timestamped and versioned).
  - sig_allowlist_checklist.pdf — short checklist with example security group and route table entries you can paste into the SIG response.

5) Example route table / SG snippets (paste-ready):
  - Route table entry: Destination: <Redwood-endpoint-prefix> -> Target: VPC endpoint (vpce-xxxx)
  - Security group: Allow outbound TCP/443 to 10.10.0.0/24 (example endpoint IPs), Inbound from our health-check CIDR 10.10.100.0/24 (if using private endpoint monitoring).

6) DNS proofs for SIG: we can provide a sample dig response from a configured test VPC (screenshot or text output) showing the private resolution.
