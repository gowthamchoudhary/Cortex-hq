Alice — thanks for the clear asks. High level answers below; I attached a compact diagram and a CSV mapping of telemetry fields to our internal event names.

Summary answers:
1) Telemetry fields: we expose non-sensitive metadata only — event_type, timestamp (RFC3339), key_id (UUID), operation (encrypt/decrypt/sign/rotate), rotation_phase (init/requested/completed), attestation_digest (SHA256 of attestation blob), operator_present (bool), node_region, request_latency_ms, tokenized_kv_cache_hit (bool). No key material, nonces, seeds, or raw signatures are exported.

2) Authentication & routing: telemetry is signed with a short-lived mTLS client cert issued per-keystore instance by Redwood's controlplane. Optionally, customers can configure an outbound collector URL (HTTPS) to send telemetry to their on-prem collector; when configured, telemetry is TLS-mTLS authenticated to the collector using their mTLS cert. Defaults: telemetry goes to Redwood telemetry ingest (hashed key_id) and we provide webhook relay to customer collector.

3) Tamper-evidence and rotation sequence: each rotation event includes a monotonically increasing rotation_epoch and attestation_digest. We chain rotation events by including previous_event_digest in the new event (SHA256 over canonical event fields) so an auditor can verify no events were dropped. For HSM attestation, we include the HSM-signed attestation blob (or its digest) and the attestation certificate chain.

Adding a few operational constraints from the on-prem side: 

- Telemetry batching: we batch small events (<=1KB) with a deterministic flush every 5s to keep costs bounded; each batch has a batch_id and batch_digest so you can verify integrity across the batch boundary.
- Rotation windows: for operatorless BYOK we require a scheduled maintenance window for live rotations if customers opt for zero-downtime split-rollover; otherwise rotations use a short grace window and atomic swap. We surface expected outage window in the rotation_event.
- Replay prevention: each keystore instance keeps a sliding window of recent event digests; collectors should reject events older than N minutes (configurable).

Hi Alice — quick update and planned deliverables: 

1) Dual-send: supported. We will add a flag in the private-deploy config: telemetry.dual_send = true|false; when true, events are sent to Redwood ingest and an outbound customer collector. Both streams sign events independently with mTLS certs.

2) Attestation blobs vs digests: supported. By default we include attestation_digest only; full blob can be enabled per-customer (attestation_blob = true). We'll provide a redaction policy that strips the blob before outbound to the customer's collector unless explicitly enabled.

3) Server-side retention: we persist canonical chained events (digest+metadata) for retention windows configurable per-tenant; default 90 days, enterprise option up to 3 years. We'll surface an export API /audit/events?start=&end= that returns the canonical chain and proofs (digests). We will also provide a bulk export in NDJSON for your archive requirements.
