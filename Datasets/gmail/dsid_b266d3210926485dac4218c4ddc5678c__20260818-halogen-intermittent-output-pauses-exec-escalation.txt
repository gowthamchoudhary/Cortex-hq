Alex / team,

I pulled the capture and searched server-side logs across the customer’s dedicated pool. Early findings (preliminary):
- We see a pattern of elevated per-connection backpressure around 08:10–08:35 PT; many sessions show multiple short-lived WS reconnects (1006) and chunked transfer close events.
- Token generation latency for that window increased ~3x on average; the runtime is falling back to a synchronous I/O path on ~7% of requests due to fragmented frames from the proxy layer. This correlates with the bursty resumed output you described.
- Error surface: a small but visible bump in 502/504 from the helper proxy during the same minutes. Not a wholesale service outage.

Hypothesis: increased intermediate proxy fragmentation (either at customer edge or our ingress) causing the runtime to reassemble tokens inefficiently; the runtime currently triggers protective sync drains when it detects partial chunk sequences, which raises latency and can produce transient 502s.

Next steps I’m taking now:
1) Capturing packet-level frame boundaries from the ingress for the peak window (attached logs).
2) Temporarily disabling the extra proxy-level chunk coalescing rule on the customer’s route to see if it reduces fragmentation impact (non-disruptive toggle).
3) If toggling reduces the symptom, we’ll propose a longer-term fix: adjust keepalive / frame-size heuristics and add a small buffering window to prevent synchronous drains under fragment patterns.

I’ll report back with the ingress trace in ~30 minutes.
