Hi Jack — great to hear. I've pasted a compact onboarding checklist below (we'll provide the full MAP and an intake spreadsheet in Drive). I'll also flag a few items that commonly cause delays.

Quick onboarding checklist (prereqs we need to validate):

1) Networking
- Egress CIDR list (CSV) and which prefixes will be SNAT'd via TGW/NAT (we need exact /24+/16 granularity).
- Inbound rules: list of service FQDNs/ports that require whitelisting (if any).
- BGP peering: do you plan active peering to Redwood edge? If yes, provide ASN and proposed BGP session parameters.

2) Identity & keys
- Customer-managed KMS key ARN for data-at-rest encrypted volumes (if using CMK).
- Service account email and roles (least privilege IAM policy we provided).

3) Security attestations
- SOC 2 summary (PDF) + contact for compliance follow-up.
- Data residency confirmation (selected region + backups).

4) Access & deployment
- Jumpbox/bastion access window and jump host IP(s) for day-0 debugging.
- SSH public key(s) or SSM role to be configured for access.

5) Operational items
- Expected QPS and average request/seq lengths for sizing.
- Maintenance blackout windows for initial week of testing.

Common delay points:
- Missing exact egress CIDRs (we can't validate NAT SNI rules without these).
- KMS key ownership mismatch (CMKs must allow Redwood service principal).
- Procurement redlines (DocuSign link required for MAP)
