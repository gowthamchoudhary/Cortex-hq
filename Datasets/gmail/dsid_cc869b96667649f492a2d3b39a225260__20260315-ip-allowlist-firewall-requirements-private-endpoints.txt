Hi Sam / team — attaching the short technical spec and some example firewall rules. Summary below; full details in attachments.

1) Modes and high-level implications- Private (VPC) with outbound egress: minimal outbound to Redwood control plane and optional external services (metrics, container registries). Suitable when outbound is allowed and you want managed updates.
- Air-gapped on‑prem: fully self-contained; no external egress required after initial bootstrap if you ship model artifacts and images via secure transfer. This requires our on‑prem bundle + offline license activation and costs additional support.

2) Required outbound endpoints (recommended ordering for allowlist)- Control plane API: control.redwood-inference.com (HTTPS, 443) — used for registration, license checks, config sync. Behaves as server-initiated TLS connections to a small set of IPs (we publish a weekly CIDR set; see attachments).
- Artifacts & model downloads: artifacts.redwood-inference.com (HTTPS, 443) — large downloads at install/upgrade. Optionally pulled from S3-backed endpoints: s3.amazonaws.com (443) or regional S3 endpoints.
- Container registry (if using Redwood-managed images): registry.redwood-inference.com (443) or ghcr.io / docker.pkg.github.com (443).
- Telemetry/metrics: otlp.redwood-inference.com (443) — optional; can be disabled.
- Time & NTP: time.redwood-inference.com (123/UDP) or allow NTP to public stratum servers.
- CRL/OCSP for TLS: ocsp.globalsign.com / crl endpoints — allow outbound 443 for OCSP stapling and certificate validation if firewall performs TLS interception.

Ports: primarily 443/TCP for HTTPS. Where needed: 123/UDP for NTP, 443/TCP for registry and OCSP. Avoid opening wide ephemeral ranges; Redwood uses client-initiated TCP connections to destination ports above.

3) CIDR recommendations and maintenance- We publish a small set of stable CIDR blocks for control and artifacts (see attachments: redwood-ip-allowlist-sample-clauses.pdf). Customers should allow those CIDRs + the DNS names above.
- If your firewall vendor prefers FQDN rules, allow the FQDNs with strict TLS validation. If they require IPs, pin the published CIDR list and automate weekly updates via an API endpoint we provide.

4) NAT / Gateway guidance- Use a NAT Gateway or egress proxy for nodes that do not have direct internet routes. For PrivateLink/PrivateEndpoint options, Redwood supports VPC peering and PrivateLink for control-plane traffic — eliminates public egress for control plane (requires configuration in the private deployment order).

5) TLS inspection and certificate validation- We recommend not doing full MITM TLS interception on Redwood control-plane endpoints. If you must perform TLS inspection, ensure OCSP/CRL access is allowed and that CT logs/OCSP responses are not blocked. Certificate pinning is unsupported for customer-managed roots, so maintain visibility into CA infrastructure.

6) Example firewall rules (simplified)
- Allow tcp dst=443 to control.redwood-inference.com (or CIDR 203.0.113.0/26) from subnets: 10.100.0.0/24
- Allow tcp dst=443 to artifacts.redwood-inference.com (or CIDR 198.51.100.0/24) from 10.100.0.0/24
- Allow udp dst=123 to NTP pool from 10.100.0.0/24
- Deny all outbound except above + your internal management systems

7) On-prem / air-gapped considerations- For fully air-gapped installs we provide an offline bundle (images, model weights, install scripts) and an offline license activation flow. Customers must import container images into their private registry. Note: automatic model updates and hosted telemetry will be disabled. See attachment fw-rule-examples.txt for checklist.

8) Operational notes and rollback- If your firewall vendor performs DNS caching aggressively, prefer CIDR rules with weekly updates. For upgrades that require large downloads, schedule maintenance windows and allow temporary higher throughput.

9) Contact/automation- We can supply: (a) a signed current CIDR list via HTTPS to poll; (b) a single-dotfile manifest listing all FQDNs and ports; (c) a DocuSign packet for air-gap license activation.

Marta — quick answers inline:
1) PrivateLink: yes, when configured for control-plane traffic and peered correctly, PrivateLink removes the need for public egress to control.redwood-inference.com. You will still need outbound for artifacts unless you mirror artifacts into your internal registry or S3.
2) Air-gapped checklist & SLA: attached in the PDF (redwood-ip-allowlist-sample-clauses.pdf) — includes offline license activation steps and support SLAs for air-gapped installs.
3) OCSP/CRL via egress proxy: supported — as long as the proxy preserves TLS server identity for OCSP stapling and allows outbound 443 to OCSP endpoints on behalf of hosts. If your proxy performs full TLS MITM, make sure the proxy can validate remote OCSP/CRL entries and not block CT/OCSP.

If helpful, we can produce a vendor-facing one-page firewall rule set formatted for Palo Alto, Check Point, and Fortinet. Happy to set up a technical call with your network team.
