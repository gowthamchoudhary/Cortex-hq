Jeff / Jasmine — adding the technical details requested below. Quoting Jasmine's message above for context.

1) SAML / SSO
- We support SAML 2.0 and can publish an SP metadata file (attached: saml_metadata.xml).
- Typical NameID is persistent (email) but we support transient if required.
- Assertion example (sanitized) shows attributes: email, name, groups, sub (opaque id). We can redact pII for shared logs.
- Sessions: Redwood issues session cookies tied to IdP assertions; session duration configurable per-customer, default 8 hours.

2) SCIM provisioning
- We implement SCIM 2.0 endpoints supporting: Users (GET/POST/PUT/PATCH/DELETE), Groups (GET/POST/PUT/PATCH/DELETE).
- Provisioning scope: attribute-level mapping is configurable; our default mapping includes: userName, givenName, familyName, emails[0].value, active, groups. See attached scim_scope_matrix.csv.
- We support incremental sync via /Users?filter and PATCH for partial updates.

3) RBAC and least privilege
- Role set: Admin (full org/usage config), Engineer (deploy models, manage routes), ReadOnly (view only).
- Role enforcement: authorization checks at API gateway and control plane; role bindings stored in our metadata DB with audit entries on changes.
- Separation of duties: Admin cannot perform billing exports without additional billing-role binding; changes to role bindings require two-person approval in our UI (audit trail recorded).

4) MFA and enforcement
- MFA is enforced via the customer's IdP (we require IdP-level MFA for console/API access for enterprise accounts). For hosted API keys, we require owner-level MFA at creation and rotation events are auditable.

Evidence attachments included: saml_metadata.xml, scim_scope_matrix.csv. We can produce sanitized assertion logs on request (example rows only).

Let me know if you need more granular logs or a playbook for onboarding SCIM with your IdP.
