Aisha,

Thanks — please find our consolidated responses below. We've also attached a concise "Sealed Deployment Playbook" and sample evidence files (SBOM export and installer checksums). High-level summary first, followed by question-by-question details.

Executive summary:
- Redwood supports fully offline (air-gapped) Private deployments with a signed offline installer and deterministic SBOM exports.
- Zero-runtime-egress is the default in Sealed mode. All telemetry and control-plane artifacts are optional and gated behind explicit operator actions.
- Key material can be provisioned via local HSM or imported using an offline key-wrapping workflow; we also support customer-managed HSM (PKCS#11).
- Emergency patching is a documented, auditable process that requires an operator push of signed patch bundles; there is a controlled audit trail and optional cross-signed attestation.

Detailed answers (numbered to match your list):

1) Installer delivery and verification:
- We provide a signed offline installer bundle (tar.gz) for all Private releases. Each bundle has an SHA-256 checksum and an OpenPGP signature generated by Redwood's build signing key.
- Verification options: local checksum comparison, OpenPGP signature verification, and an offline notarization token that can be validated against a signed footprint we include in the bundle.
- Evidence included: installer_checksum.txt (SHA-256), installer-signing-certificate.pem (public key), verification steps in sealed_deploy_playbook_v1.2.pdf.

2) SBOM and supply-chain attestations:
- We export a CycloneDX-compatible SBOM for each release and provide a signed attestation (timestamped) describing build provenance. SBOM includes transitive dependencies and cryptographic hashes.
- Evidence included: sbom_redwood_20260913.csv (CSV of SBOM entries) and a signed attestation (referenced in playbook).

3) Key management and rotation:
- Supported options: (a) Customer-managed HSM (PKCS#11 or Cloud HSM with no outbound connectivity required during normal ops), (b) Local HSM appliance integration (FIPS 140-2 validated devices), (c) Offline key import using a key-wrapping envelope (we accept wrapped keys delivered on removable media).
- Rotation: rotation is operator-driven; we provide an offline rotation utility that composes a new key-wrapping envelope and outputs change audit logs. We also support scripted rotation via your on-prem automation.

4) Network and egress controls:
- Sealed mode enforces a firewall policy with no external egress by default. All external endpoints are disabled in the runtime by default; configuration is stored locally and only changed via signed operator actions.
- Outbound access for telemetry or model updates is opt-in and requires explicit operator enablement with two-person approval recommended.
- Emergency egress path: we support a controlled, auditable patch bundle push mechanism. The operator stages the signed patch bundle on a jump host inside the sealed network; the bundle is validated locally and applied. This workflow leaves an immutable audit record and creates a tamper-evident manifest. Details and flow diagram in offline_patch_process_flow.svg.

5) Patch and vulnerability workflow for air-gapped sites:
- Typical cadence: security advisories are triaged within 24 hours; critical patches are prepared and delivered as signed offline bundles. Customer acceptance testing window is configurable; we recommend a 5-business-day staging window for non-critical updates and a 48-hour window for high-severity fixes.
- We supply a dry-run mode so you can validate patch application without changing runtime state. Rollback is supported via snapshot restore; our playbook enumerates steps.

6) Operational playbook for upgrades and incident response:
- The attached playbook includes pre-checks, acceptance criteria, rollback steps, test checklist, and operational runbook templates for incident response. Runbooks include steps for forensic evidence collection, log export for offline review, and a post-mortem template.
