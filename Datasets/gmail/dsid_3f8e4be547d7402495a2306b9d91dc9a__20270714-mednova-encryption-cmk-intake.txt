Evelyn / Aditya —

Draft answers and attachments below. High level: Redwood supports all three patterns; we typically recommend envelope encryption with customer root CMKs (CMEK) for the best balance of security and latency. Notes: 

1) Architecture options (short):
- Redwood-managed keys (managed CMK): simplest operationally, lowest procurement friction. Data keys are generated and stored encrypted by Redwood KMS; good for POCs and non-PHI workloads. Latency impact: negligible per-request with caching; cold-starts minimal.
- AWS KMS BYOK (imported CMKs): customer retains root CMK control; envelope encryption in the runtime; key unwrap operations happen at customer KMS on key lifecycle events, not every token generation. Latency impact: <5% on tail latency when using prefix/KV caches; additional egress to KMS only for key rotations or rewraps.
- Dedicated HSM in VPC (customer appliance): strongest custody model and suitable for strict compliance. Can be integrated via TLS- and attested key wrapping. Operational cost and complexity higher; small additional tail latency for initial session handshake; steady-state token generation unaffected due to envelope caching.

2) HSM vs software KMS: HSM required if audit/regulator demands FIPS-140-2/140-3 Level 2+ for root operations. We support HSM-backed keys via standard KMS providers and customer-hosted appliances.

3) Rotation and audit: Recommend monthly rotation of data-encryption-keys, with CMK rotation annual or per customer policy. We can surface key rotation events in audit logs (available for legal/procurement review).

4) Artifacts for procurement: attached diagram and a short deployment playbook you can share (includes BAA language snippet and roles/responsibilities matrix).
