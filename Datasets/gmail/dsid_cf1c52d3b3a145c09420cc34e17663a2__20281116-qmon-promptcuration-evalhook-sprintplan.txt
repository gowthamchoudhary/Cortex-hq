Dana — thanks for the clear list. I sketched a focused sprint plan below that balances fast wins and safety rails. Attaching three artifacts: (1) prompt inventory template, (2) evalhook integration guide, (3) canary schedule template.

Sprint plan (2-week):
- Day 0–2: Prompt ingestion and canonicalization. We’ll import your CSV, normalize templates (we keep both raw and canonicalized) and tag prompts by intent + risk (low/medium/high) so we can prioritize sentinel tests.
- Day 3–5: Eval harness bootstrapping. We’ll deploy a lightweight evalhook container that runs locally and exposes a webhook for your Jenkins jobs. It supports the Redwood eval API and returns a JSON pass/fail summary for each prompt test.
- Day 6–9: Build baseline metrics. Run batch evaluations to capture baseline BLEU/ROUGE/Embed-sim/Custom heuristics and set alert thresholds (automated suggestions + manual review).
- Day 10–12: Canary configuration & dry-run. We’ll template a canary schedule (percent traffic ramp) and a rollback trigger (e.g., drop of avg embed-sim > 4 points or N failed sentinel tests in 15 minutes).
- Day 13–14: Validation + handoff docs + invite for ops drill.

Key asks from you before Day 0:
- Confirm a CSV with current prompt variants and a small golden set (50 examples) you want used for baseline.
- Provide a Jenkins runner with network access to the evalhook endpoint (we can proxy through a signed URL if needed).
- Slack channel to post alerts (we can post to a webhook).

I recommend the following preliminary rollback policy (we can refine):
- Canary levels: 1% -> 5% -> 20% -> 50% over 48 hours (adjust for traffic), hold at each step for 2 hours.
- Auto-rollback triggers: sustained increase in error rate (>1% for generation errors) OR avg embed-sim drop > 4 points from baseline OR >3 sentinel test failures in a rolling 15-min window.

For your peak, I recommend the time-based ramp but shorten the lower-percentage holds to 30–60 minutes overnight.
