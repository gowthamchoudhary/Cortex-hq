What I see (initial):
- Short windows where request queue depth for QuickCart tenant spikes 4-5x baseline coincident with a surge of ~80% HTTP/1 streaming requests.
- Concurrency cap for the serving pool for that tenant is being hit briefly; when the cap locks new requests they wait in the request queue and some clients time out.

Suspect root cause (hypothesis):

Status update and post-mortem summary:

What we did (2026-04-19):
- Applied temporary concurrency cap reduction for QuickCart from 120->55 for the serving pool; observed immediate reduction in request queue depth and elimination of 10-25s tail spikes.
- Enabled KV prefix caching for the personalization keyspace (TTL 30s, hot-key only) which cut repeated backend lookups by ~68%.
- Added queue-depth alerting and a short-lived tracing window to INF-9823; captured multiple fan-out bursts that correlate with frontend parallelism.

Root cause (final):
- Client-side change introduced higher parallelism for personalization/price-check calls. Combined with a small set of hot keys, this caused repeated KV lookups that amplified queue pressure. The serving runtime's concurrency cap protected model workers but allowed queue growth which produced long-tail latency and a small number of timeouts.

Longer-term fixes (owner + ETA):
- Rishi: implement server-side request coalescing for identical personalization keys (Q3 2026 prototype).
- SRE: add automatic tenant-adaptive concurrency throttling (Priyom, Q2 2026 roadmap item).
