Hi Heidi — thanks for the diagram and probes. Quick summary up front: PrivateLink (interface endpoints) + optional active-passive S2S VPN for out-of-band admin access gives the best balance for your compliance needs and address-space isolation. VPC peering looks attractive for latency but it hits two blockers for your environment: (1) overlapping CIDR ranges across your VPCs and partners and (2) cross-account route propagation that makes audit attribution harder.

I'll outline the tradeoffs below and propose a lean pilot plan.

Key tradeoffs (short):
- PrivateLink (recommended):
  • Pros: no route-table sharing; interface endpoints present a stable ENI-based egress IP space per AZ (helpful for allowlisting), per-flow logging via VPC Flow Logs + ENI tags, supports mutual TLS between your clients and Redwood service endpoints. Avoids IP overlap issues since traffic is NAT'ed to the endpoint's ENI.
  • Cons: slightly higher p95 (~5–12ms overhead depending on AZ) vs peering due to extra hop; per-GB data processing charges on both sides; requires NACL/security-group discipline.
- VPC Peering:
  • Pros: lowest network hop latency, predictable throughput (no interface endpoint throttles), simple for flat-mesh VPCs.
  • Cons: breaks isolation (route-table changes cross accounts), requires unique non-overlapping CIDR across participants, harder to audit per-tenant flows, and longer ops blast radius for peering misconfigurations.
- Site-to-Site VPN (IPsec):
  • Pros: encrypted tunnel, clear ingress/egress point, useful as fallback or DR path.
  • Cons: variable latency and jitter (depends on public internet), requires NAT/firewall configs, more operationally heavy (IKE lifecycle), not ideal as primary path for low-latency interactive inference.

Compliance notes: PrivateLink + strict ENI tagging + centralized Flow Log ingestion into your SIEM gives cleaner audit trails than peering. If you need explicit per-connection client identity in logs, we can propose a short header-level mutual auth or mTLS overlay on top of PrivateLink traffic.

Pilot proposal (2 weeks):
1) Create an interface endpoint in your staging VPC (us-west-2) pointed at Redwood's staging service.
2) Run synthetic latency/throughput tests (we'll provide a load container) and collect p50/p95/p99.
3) Validate Flow Logs, ENI IPs for allowlisting, and the end-to-end auth flow.
4) Stand up a second S2S VPN (minor config) as a failover; validate failover and routing.

Irene / Ben — adding a few technical datapoints to support the recommendation and a couple of questions for Heidi (cc'd in the thread).

Observations from Redwood internal tests (us-west-2):
- Measured additional RTT for PrivateLink vs peering: median +4ms, p95 +9–14ms depending on AZ pairing. For interactive completions that target <30ms p95, PrivateLink is usually OK if compute is co-located in the same AZ and client app keeps connection reuse (keepalives, long-lived TLS).
- MTU: PrivateLink interface endpoints may reduce path MTU (common MSS negotiation). If you have large-batch payloads (>1MB), enable TCP MSS clamping on the client side or test fragment behavior — otherwise you'll see increased retransmits.
- Egress stability: We can provide a small set of stable ENI IPs per AZ for allowlisting. If you require single static IP per region, we can offer an egress NAT proxy in a dedicated subnet (adds a hop and cost).

Questions for Elevate:
1) Do any of your downstream partners require static IPs for egress from Redwood?
2) Are you comfortable with per-AZ allowlisting (ENI IPs), or do you need a single region-wide egress IP?
3) Any regulatory rule that forbids NAT or ephemeral IP translation?

If they confirm per-AZ allowlist is fine, PrivateLink + optional NAT-proxy is simplest. If they need predictable sub-ms latency for synchronous use-cases, peering becomes more attractive but only if CIDR collisions are resolved.

Heidi / team — thanks for the clarifications. Final recommendation and next steps below.

Recommendation (concise):
- Primary path: PrivateLink (interface endpoints) in each AZ with keepalive-enabled clients and connection pooling.
- Egress for partner-facing traffic: regional NAT egress proxy (small set of stable elastic IPs) to satisfy partner allowlists. This proxy will be in a dedicated subnet we operate for you; cost estimate below.
- Secondary/DR: S2S IPsec tunnel(s) as active-passive failover with automated route-preference change.

Why this combination? It preserves your auditability (Flow Logs + ENI tagging), removes the need to modify route tables across accounts (no peering), and gives you the stable IPs required for legacy partners. Latency impact is modest if we co-locate in same AZ and use connection reuse; our internal estimates for your topology (based on your probe) show p95 expected ~22–28ms for mixed workloads.
