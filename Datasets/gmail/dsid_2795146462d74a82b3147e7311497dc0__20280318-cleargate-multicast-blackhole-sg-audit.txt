Thanks Amelia — I dug through the pcap. Key observations (excerpted):

- Many large UDP datagrams (payload ~4200 bytes) for 239.10.10.10:5000 arriving fragmented (frag offsets present). I see occasional ICMP type 3 code 4 (Fragmentation needed) from the border router.
- IGMP reports/queries are present; membership looks steady but the timing of queries aligns with the gaps.
- No evidence of SSM/PIM state churn inside the Redwood appliance logs, but the border device shows some interface counters incrementing (frag/reassembly failures).

Hypothesis: Path MTU is lower than sender's packet size and the router in the path is sending ICMP fragmentation-needed either to the source or dropping fragments — for multicast this can be especially bad because some network devices don't reassemble multicast fragments reliably. Another plausible factor: SNAT applied to multicast source addresses — if egress SNAT rewrites source to a single IP, IGMP/forwarding behavior can change (some switches/routers tie group state to source).

Immediate checks I want from Cleargate:
1) On the multicast source host: "ip link show" and "ip -s -s neigh flush" is not necessary but confirm send buffer size and MTU (if MTU>1500).
2) On the border router: output of "show interface <egress-if>" and "show ip route" and any NAT rules that touch 224.0.0.0/4.
3) On the ToR/agg: whether IGMP snooping is on and if there are any rate-limits or storm-control parameters affecting multicast.

Proposed mitigations (quick):
- If SNAT is applied to multicast ranges, add an exemption: do not NAT 224.0.0.0/4.
- Reduce sender UDP packet size to fit 1500 (or enable DF-clear/PMTU discovery fix) as a short-term workaround.
- Temporarily disable IGMP snooping on the aggs to force layer-2 flood (to test whether snooping is causing forwarding gaps).

I'll prepare a short playbook with commands once we have the requested outputs.

Amelia / team — thanks for the clear repro steps and the attachments. Summarizing next steps and recommended permanent changes: 

1) Root cause: MTU mismatch + edge SNAT. Sender NICs and ToR were on jumbo frames (9000) but border egress is 1500. Large UDP multicast packets (DF cleared or fragmented depending on sender) were being fragmented and then dropped / not reassembled consistently by the egress device; because SNAT rewrote source addresses at the border, multicast forwarding entries did not behave consistently for fragments. Net effect: intermittent multicast blackholing during high rate bursts.

2) Short-term mitigations (we recommend doing immediately during your next maintenance window):
   - Add an explicit NAT exemption for multicast: iptables/nat rule to skip SNAT for 224.0.0.0/4. Example: "-A POSTROUTING -d 224.0.0.0/4 -j ACCEPT" on the NAT table (device-dependent).
   - Force sender to MTU-safe packet size (<= 1400) as an aggressive short-term workaround while we remediate path MTU.
   - Temporarily disable IGMP snooping on the agg pair if you can tolerate broadcast flood to validate whether snooping state churn is amplifying gaps.

3) Long-term remediation (recommended plan):
   - Normalize MTU across path for multicast flows or enable tunneling that preserves fragmentation semantics (avoid fragmenting multicast if possible).
   - Adjust egress device to not generate SNAT for multicast ranges; ensure any middleboxes that rewrite addresses are configured to keep multicast source intact.
   - Add monitoring/alerting for ICMP type 3 code 4 messages from the border with source-destination correlation for known multicast groups.
   - Add a regression test in our private deployment checklist: run a 5-min 4200B UDP flood on a cluster every deploy to verify MTU homogeneity.
