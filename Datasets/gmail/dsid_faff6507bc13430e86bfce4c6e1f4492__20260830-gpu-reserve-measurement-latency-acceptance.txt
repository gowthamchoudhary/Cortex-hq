Beth — thanks, and appreciate the traffic profile detail. High level summary (attachment: redwood-throughput-spec.xlsx):

- Measurements to run:
  * Tokens-per-second (aggregate, measured at the model ingress across the GPU pool) — this is the primary commit metric. We report both sustained tokens/s and 1-minute peak tokens/s.
  * Requests-per-second (RPS) — measured at the API gateway; useful when request sizes are consistent.
  * Latency percentiles at the API surface (p50, p95, p99) and model step-level latency for long generations (time-to-first-token and token-rate).

- Test methodology: two parallel tracks to reflect your workload mix:
  1) Synthetic load (controlled): run a sequence of synthetic requests derived from your sample-prompt-set.jsonl. These emulate short and long flows with the same concurrency and sequence-length distributions you provided. Synthetic runs are executed by Redwood's load harness against the Dedicated endpoint behind the customer VPC egress (if applicable).
  2) Production-sampled validation: we'll sample a 48-hour window of your real traffic (safe-guarded, no payload storage) and replay at scale in a shadow environment to validate real-world KV cache effects and prompt diversity.

- Acceptance windows: propose a three-stage window to reduce flakiness and warm caches:
  * Warmup: 2 hours steady traffic at 30% target to populate KV caches.
  * Baseline run: 6-hour sustained run at commit target (e.g., 1,000,000 tokens/s aggregate); calculate median across rolling 15-minute windows.
  * Peak sampling: three 1-hour peak runs (consecutive days or within 72 hours) using burst profile to validate autoscale and tail latency.

- Latency targets (examples; we can tighten on request):
  * Short requests (<= 256 tokens): p50 < 60 ms, p95 < 220 ms, p99 < 400 ms
  * Long flows (> 1,000 tokens): time-to-first-token < 350 ms; steady-state token-rate within 10% of model's baseline kernel throughput; end-to-end p95 for full generation depends on length but we report per-token latencies to avoid length skew.

- Measurement specifics:
  * Aggregation windows: report tokens/s as the 95th-percentile of per-minute aggregates during the 6-hour baseline.
  * Failure definition: a sustained interval where tokens/s falls below 90% of the committed rate for more than two consecutive 15-minute windows triggers a failure event for that run.
  * Credits: for acceptance failure we propose a one-time credit equal to 10% of one month’s committed reservation for the first failure, escalating per contract language if repeated. (We can move to a finer SLA credit ladder if you prefer.)

- Tooling and deliverables:
  * We will share the runbook and load harness (measurement-runbook.pdf) and a script to validate results locally. You’ll provide sample-prompt-set.jsonl and a representative traffic histogram.
