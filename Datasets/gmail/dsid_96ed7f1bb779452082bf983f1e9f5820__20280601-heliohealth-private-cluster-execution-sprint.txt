Alex — thanks for the inventory. This is helpful; I pulled a few initial gaps (missing switch uplink mapping and exact NVMe bay counts) and flagged them inline.

Summary: we recommend a 3-week execution sprint split into two phases (Preflight + Build & Validation). Deliverables and owners (high level):

- Week 1 (Preflight): site inventory validation (Helio infra), CIDR allocation & firewall rules (Redwood network owner: Ben), storage class decisions (Onsite vs. SAN) and KMS plan (Neha).
- Week 2 (Build): cluster provisioning (control plane HA 3 nodes, kubeadm-based or RKE2 per preference), nodepool rollout (control, inference/gpu, worker-ssd, worker-block), private registry cache deployment, and initial monitoring/alerting config (Marissa).
- Week 3 (Validation & Handover): perf smoke tests (latency & token throughput), failover exercises, backup and restore validation, and runbook handover.

Minimum cluster sizing (starting point, adjustable after inventory):
- Control plane: 3 x mCPU-heavy nodes (16 vCPU, 64GB RAM) with local boot SSDs.
- Inference/GPU pool: 2-4 nodes depending on model footprint (A100/RTX-class); we can accommodate heterogenous GPUs but prefer uniform instance types for predictable scheduling.
- Worker-ssd: 3 nodes with local NVMe (for KV cache and ephemeral logs) — use local NVMe for prefix/KV caching to keep token latency low.
- Worker-block: 3 nodes attaching to SAN/CSI block storage for persistent volumes (model weights, embeddings DB).

Storage guidance:
- KV/prefix cache: local NVMe (ephemeral) with replication at app layer.
- PVs (models, DBs): block CSI (encrypted) backed by SAN or cloud-connected NVMe. Use ReclaimPolicy=Retain for model volumes to avoid accidental data loss during node deletion.
- Shared artifacts/backups: S3-compatible object store or NFS gateway depending on Helio ops preference (we tend to recommend object store for durability).

Networking notes:
- CIDR plan: we suggest a /22 pod CIDR and a /24 service CIDR per cluster to avoid overlap with Helio WAN. See attached network_cidr_plan.png for proposed allocations.
- Egress: prefer routed VPC peering with forced-tunnel for egress to Helio firewall; BGP-managed peer for multi-homing if Helio has multiple uplinks.
- Private registry: recommended (pull-through cache) to improve reliability; we can run an on-prem cache in the cluster or use a pre-approved registry behind Helio firewall.
- KMS/HSM: Redwood integrates with external KMS via standard PKCS#11 or cloud KMS endpoints. If Helio prefers an HSM appliance, note that will add an on-site hardware requirement and a short window for key provisioning and testing.

Security & operational controls:
- Node taints and tolerations to isolate GPU workloads.
- ResourceQuota per namespace and LimitRanges for token-heavy workloads.
- Admission controls: PodSecurity, ImagePolicyWebhook for registry allowlist, and network policies (default deny).
- Audit logs: we will ship audit events to your SIEM (TLS+mutual auth).
