Sara —

Appreciate the clear list. Quick replies inline and action items at the bottom.

1) Role mapping / SAML attributes:
- Required assertion attributes: subject (NameID), email, and one of: groups OR roles. We support both boxed and multi-valued group claims. For our role engine we look for either the `roles` claim (preferred) as an array of strings, or the `groups` claim if you prefer AD groups.
- Nested groups: Redwood evaluates membership based on the flattened effective membership your IdP emits. If your IdP does not flatten, we recommend emitting a `roles` claim derived from group resolution.

2) SCIM provisioning semantics:
- We support SCIM 2.0 PATCH (incremental) and bulk import. PATCH will update attributes in place; we match users by `externalId` if provided, falling back to `userName` (email). Avoid changing userName/email frequently — use `externalId` for stable identity.

3) Service accounts / credentials:
- Strong recommendation: short-lived JWTs from your IdP or a short-lived certificate for the control plane agent. We provide an agent token exchange flow (OIDC client_credentials with rotating client_secret) — avoids long-lived API keys. Dev has a short runbook attached.

4) Auditing:
- We can export audit logs to your S3 or GCS bucket and include identity fields. Default retention is 90 days; enterprise retention add-on supports 13 months. We can provide an export sample.

Sara / Javier —

Adding a few technical clarifications from the runtime side:

- SCIM PATCH example (we support SCIM JSON Patch):
  PATCH /scim/v2/Users/2819-...
  [
    {
      "op": "replace",
      "path": "name.familyName",
      "value": "Holden"
    },
    {
      "op": "add",
      "path": "roles[-]",
      "value": "redwood-deployer"
    }
  ]

- User matching: prefer `externalId` set to your internal UUID. If not available, we match on `userName` (email) but treat that as mutable — changing email will create an alias record unless `externalId` is present.

- SAML nameid-format: we accept `emailAddress` or `persistent`. If you plan to allow federation across accounts, use `persistent` and populate `externalId` via SCIM.

- Service account token exchange (short summary):
  1) IdP issues short-lived client assertion for a registered OIDC client (control-plane-agent).
  2) Agent exchanges assertion for a Redwood session token via our token-exchange endpoint (exp 5m).
  3) Token used for agent registration over mTLS channel.
