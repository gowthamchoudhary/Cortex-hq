Nick / Jordan — I reviewed the draft and ran it by the infra team. Technical notes below; inline suggested language follows.

1) Measurement scope: we recommend measuring latency at the Redwood API edge (closest point to client) for fairness across regions. If StellarMed requires measurements strictly from within a private VPC egress path, numbers will vary based on customer network.

2) Model baseline: the P50/P95 numbers need a baseline prompt/response size. Our tests use a 1k token generation baseline on the Llama-3-medium class models. If StellarMed intends to use larger models or longer contexts, we should adjust expectations or include an explicit performance tier.

3) Proposed text (short):
"Redwood will use commercially reasonable efforts to provide 99.95% Monthly Uptime for Dedicated Capacity as defined in this Addendum. Latency SLOs for API requests measured at Redwood's API edge: P50 <= 120ms, P95 <= 450ms for requests matching the 1,000-token generation baseline on specified model variants. Downtime, latency measurement windows, and exclusions (maintenance, force majeure, degraded third-party connectivity) will be described in an appendix to this Addendum."

4) Credits & severity: We can support an escalated response (1 hour initial response) for Sev1 with a capped credit table. I propose a 10% monthly service credit for breach of the uptime metric per occurrence, with a maximum of 100% of the monthly fees for that product in any billing month. That cap is a policy ask from finance/legal.

I attached an internal MSA redline that highlights where the addendum would link into the main order form. If this looks reasonable to you, Jordan, I can produce a clean v2 of the addendum for StellarMed to review.
