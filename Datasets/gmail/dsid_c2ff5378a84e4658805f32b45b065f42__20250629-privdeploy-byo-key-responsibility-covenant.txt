Hi Elena — thanks for the clear list. See responses inline and a proposed next step below. Attaching a short BYOK "handshake" draft and our SOC2 summary for evidence.

- CMK custody: Yes — the customer retains the CMK in their KMS (BYOK). Redwood will never persist the unwrapped CMK. We use customer-managed wrapping keys for any short-lived per-instance keys. We can add explicit DPA language: "Customer retains sole custody of CMK; Redwood may only receive cryptographic artifacts (wrapped keys, ephemeral tokens) necessary for runtime operations and never plaintext keys."

- Operator/debug access: Redwood operators do not have privileges to directly unwrap customer CMKs. Debug workflows are limited to: instance-level process dumps, runtime logs, and start/stop/diagnostic controls that operate on encrypted artifacts. Any diagnostic that could expose request payloads requires breakglass (2-person approval) and is executed in an isolated session with recorded session logs. We will include this as an annex describing permitted operator actions.

- Breakglass / audit evidence: Breakglass requires two authorized Redwood signatories and written justification; the action is logged with timestamps, actor IDs, and a snapshot of what was accessed. We can provide: (a) a Breakglass Incident Report (template); (b) an on-demand Key Access Report listing all wrap/unwrap events interacting with your CMK; and (c) periodic attestation (quarterly) that no unauthorized unwrapping occurred.

- Telemetry / logs: We collect minimal operational telemetry (instance health, perf metrics, encrypted cache hit/miss counts) and high-level request metadata (timestamp, model variant, token counts). We do not persist request payloads or embeddings in plaintext in the hosted runtime for private deployments. If you require additional redaction/pseudonymization we can add a config toggle to suppress request metadata fields and reduce retention to 30 days.

- Subprocessors: For private deployments the runtime is operated by Redwood personnel (listed in DPA annex) and our primary cloud infra vendor (if deployment uses cloud-controlled networking). If the deployment is fully on-prem under your network, no third-party infra subprocessors are used. We'll provide a filtered subprocessor list tailored to the deployment model.

- Data transfers: By default, backups and telemetry for private deployments are kept in-region (US). Any cross-border transfers would require Customer consent and will be captured in an export control clause.

Proposed next step: we suggest a short annex to the DPA (BYOK Annex + Operator Access Annex). I'll have our legal draft those two short clauses and share by EOD Tue. Can we schedule a 30-minute call Wed (7/2) to walk procurement/legal through it?

- Instance metrics: CPU/memory/disk utilization (no request content)
